# Task Manager — Local Claude Agent Orchestrator

## Context

Greenfield internal tool (started from an empty directory). A local web app to collect tasks for the user's projects (repos registered by local path + role note) and automate their implementation by spawning Claude Code agents (`claude` CLI, opus) inside the target repo directories — each run is a hidden but fully interactive PTY terminal, attachable from the browser. Reference aesthetic: "Foreman"-like open-source tool. Design validated by an adversarial review pass (3 blockers + 7 majors found and folded in below).

Environment verified: Node v24.15, `claude` CLI 2.1.241 (`--settings` inline JSON, `--permission-mode`, `--json-schema`, hooks all confirmed), `claude-opus-5` valid model id (the worker default moved to `claude-opus-5-5` on 2026-09-23).

## Locked decisions

- Node + TypeScript server (Fastify 5), React 19 + Vite SPA, npm-workspaces monorepo
- Storage: SQLite (better-sqlite3) default ↔ PostgreSQL (`pg`, works with a Supabase connection string — free tier confirmed) via `server/data/config.json` driver switch; **fixed** `tm_` table prefix in both dialects (identical SQL strings; payloads TEXT in both)
- Worker sessions: full interactive `claude` in node-pty; completion via lifecycle hooks
- Concurrency: **2 worker sessions max** (user-mandated default); each worker instructed (prompt template) to spawn **max 3 subagents** — no CLI flag exists for this, so it's a standing instruction in every worker prompt
- Sentry: stub only (source enum + `source_ref` + config fields + "create from Sentry ref" manual form; no API pull)
- First `Stop` hook → task goes to **`review`** by default (config toggle `orchestrator.autoComplete` → `done`), because turn-end ≠ task-done (agent may have asked a question)
- **Publish** (`docs/publish.md`): from `review`, the task's OWN claude session is reopened (`claude --resume`) and told to `git add`/`commit`/`push` — same terminal, no new agent. The landing status is decided by `verifyPublished` (git), never by the agent's own report: `published` when the tree is clean and nothing is ahead of the upstream, back to `review` with the reason otherwise. Per-task `auto_publish` runs that turn automatically at the end of the work, bypassing both the human review gate and the adversarial review round
- No auto-retry (dangerous on half-edited repos) — manual Retry button only. No tsup: prod runs `tsx` directly; only the SPA gets a build.
- Project rules: document all work in `docs/` (per-phase updates are an exit criterion), `CLAUDE.md` at root, `.claude/settings.local.json` with concise output style

## Data model (all tables `tm_`-prefixed, both dialects)

- `tm_config(key PK, value TEXT)` — runtime-tunable settings as JSON values
- `tm_repos(id, name, path /*absolute, ~ expanded*/, role /*"backend"/"frontend" note*/, preview_url /*nullable http(s) dev-server URL for the mobile emulator*/, created_at)`
- `tm_tasks(id, title, description, repo_id, parent_id, group_id, group_path, group_name, group_color, status, source /*manual|sentry|auto*/, source_ref, priority, auto_publish /*commit+push instead of stopping at review*/, custom_queue_at /*nullable: set = member of the custom queue, value = FIFO position (docs/queue.md)*/, result_summary, review_summary, review_diff_hash, review_state /*pending|reviewing|fixing|passed|flagged|skipped|error|NULL — § Adversarial review*/, review_rounds /*JSON ReviewRound[]*/, wake_at, error, created_at, updated_at)`
  - status: `draft | queued | running | waiting | blocked | review | published | done | failed | cancelled` — `waiting` is a live session between two of its own turns (§ Waiting)
  - terminal statuses (`TERMINAL_TASK_STATUSES`): `published | done | failed | cancelled` — the one list both drivers read for split-parent and feature-phase resolution
  - source: `manual | sentry | auto | feature`
  - group: `group_id` is the root ancestor (a task with no parent is its own group), `group_path` the ancestor ids root-first (`/rootId/midId/`); `group_name`/`group_color` are root-row only; `sort_order` (migration 26) is the manual position among siblings and the claim tiebreaker after priority. Invariants, ordering, drag and drop and the board rendering: `docs/grouping.md`
- `tm_runs(id, task_id, repo_id, mode /*worker|analyze*/, status /*running|exited|killed*/, pid, exit_code, started_at, ended_at, session_id, transcript_path, stats TEXT/*JSON*/, resumed_from /*run whose claude session this one continued*/, stats_baseline TEXT/*JSON: cumulative transcript totals inherited at resume*/)`
- `tm_proposals(id, run_id, repo_id, task_id, kind /*rewrite|split|new_task|solution_options*/, payload TEXT/*JSON*/, status /*pending|accepted|rejected*/, created_at)`
- `tm_features(id, repo_id /*nullable: repo deletion detaches*/, title, request TEXT, status /*draft|analyzing|proposed|approved|running|paused|review|done|failed|cancelled*/, analysis TEXT/*JSON plan*/, review TEXT/*JSON review rounds*/, analysis_rounds, error, created_at, updated_at)` — a big request decomposed into ordered phases of tasks (`docs/features.md`); `tm_tasks` carries `feature_id` + `feature_phase` and the `feature` source value
- `tm_dispatches(id, from_task_id, from_run_id, to_task_id, message, status /*pending|delivered|failed|cancelled*/, note, created_at, delivered_at)` — agent-to-agent messages delivered by resuming the target task's own claude session (`docs/dispatch.md`); FK-less like `tm_events` so a dispatch outlives task deletion
- `tm_migrations`

Scrollback is NOT stored in DB (in-memory ring buffer per session).

## Storage adapter

`config.json`: `{ "storage": { "driver": "sqlite" | "postgres", "sqlite": {"file": "data/taskman.db"}, "postgres": {"connectionString": "postgres://…"} } }` — switching = edit driver + paste conn string. No configurable prefix (hardcoded `tm_`).

Interface: async CRUD methods per entity **plus first-class composite methods instead of a generic `transaction(fn)`** (better-sqlite3's `.transaction()` is sync-only; an async facade would commit before awaited work runs — adversarial-review blocker B1):
- `claimNextQueuedTask()` — `UPDATE … SET status='running' WHERE id=(SELECT id FROM tm_tasks WHERE status='queued' AND custom_queue_at IS NULL ORDER BY priority DESC, created_at LIMIT 1) RETURNING *`; in better-sqlite3 run via `stmt.get()` (`.run()` discards RETURNING). If PTY spawn then throws → revert task to `queued`.
- `peekCustomQueue()` / `claimNextCustomQueuedTask()` — the custom queue (`docs/queue.md`): head = oldest `custom_queue_at` among queued members (feature gate applied); the claim adds `AND NOT EXISTS (running member)` in the same statement so the queue is strictly serial. SQL fragments shared verbatim by both drivers in `storage/queue-sql.ts`.
- `acceptProposal(id, chosenOption?)` — atomic per driver (sync `db.transaction()` / pg `BEGIN..COMMIT` on one client): rewrite→patch task; split→create `queued` children (`source:'auto'`, `parent_id`) + parent→`blocked`; new_task→`draft` task; solution_options→append chosen approach to description.
- `approveFeature(id)` / `resolveFeatureCompletion(featureId)` / `cancelFeature(id)` — the Feature composites: materialise the approved plan as `draft` tasks (standing caps injected server-side), then pump phases (pause on any failure, enqueue the lowest unresolved phase, roll up to `review` when nothing is left). Phase eligibility is one shared SQL fragment spliced into `claimNextQueuedTask` in both drivers, with a JS twin used by the pump — see `storage/feature-sql.ts`.
- `resolveChildCompletion(childId)` — recompute parent: all children done (cancelled counts as resolved) → parent `queued`-again? No: parent → `review`; any failed → parent stays `blocked` with error surfaced. Manual **Unblock** / **Fail parent** actions exist in UI (review finding M5 — no dead-end states).

Both drivers share SQL strings with `?` placeholders; pg driver rewrites to `$n` once per statement (comment the "no `?` in string literals" constraint).

## PTY sessions (`session-manager.ts`)

`Map<runId, Session{pty, ringBuffer(2MiB raw bytes), clients:Set<WS>, cols:120, rows:32, exit?}>`
- Spawn with **args array** (never a shell string — quoting hazard m8): `pty.spawn('claude', args, {cwd: repo.path, env: {...process.env, TERM:'xterm-256color', TM_RUN_ID, TM_TOKEN, TM_CALLBACK_URL}})`
- onData → ring buffer + fanout; onExit → finalize run, notify orchestrator, broadcast exit; idle/exited sessions kept for `pty.sessionTtlMinutes` (default 30, **0 = never evict on age**), cap 10 live PTYs (LRU-kill unwatched exited, then unwatched idle). The cap eviction is independent of the TTL, so an infinite TTL can never wedge spawning. The TTL and scrollback size are re-read from settings every 30s — no restart needed.
- Attach: send `{type:'history', data: base64}` first, then live frames. Client decodes base64 → `Uint8Array` → `xterm.write()` in 64KiB chunks (string decode corrupts UTF-8 — m2); fit/resize AFTER history replay (SIGWINCH redraw self-heals seam artifacts)
- Input/resize/kill (SIGHUP → SIGKILL after 5s)

### Every claude is a terminal: the aux pool (`claude/aux.ts`)

There is no headless `claude -p` left in the server (decision 2026-09-24, `docs/decisions.md`). Besides the workers, the server spawns eight kinds of claude, and each one is an interactive `claude` in a PTY of a **third** `SessionManager` pool (after the agents' pool and the repo-commands pool). Each has a `tm_runs` row and shows in the runs list with a kind badge. It can be attached over `/ws/terminal/:runId` exactly like a worker, typed into, and killed.

| kind | spawned by | subject (`tm_runs.subject_id`) | tools (`--tools`) | denials / permission |
|---|---|---|---|---|
| `review` | `review.ts` (`runReviewRound`, Review now) | task | Read Glob Grep Agent TodoWrite | Edit Write NotebookEdit Bash · `dontAsk` |
| `plan` / `plan-review` | `feature-analysis.ts` | feature | the same + Bash | Edit Write NotebookEdit · `dontAsk` (unchanged from `-p`) |
| `analysis` | `analyze.ts` (`POST /api/analyze`) | repo | Read Glob Grep Agent TodoWrite | Edit Write NotebookEdit Bash · `dontAsk` |
| `compact` | `compact.ts` (resume gate) | task | Read | Edit Write NotebookEdit Bash · `dontAsk` |
| `report` | `reports/service.ts` | report | none (`--tools=`) | Edit Write NotebookEdit Bash · `dontAsk` |
| `commit` | `git.ts` `commitRepo` | repo | none (`--tools=`) | Edit Write NotebookEdit Bash · `dontAsk` |
| `chat` | `chat/service.ts` | chat | CLI default | read: the four + `dontAsk`; write: `--dangerously-skip-permissions`; both deny AskUserQuestion/plan mode |

**The row.** `mode = 'aux'`, `kind`, `subject_id`, `label` (migration 28). `task_id` stays **NULL** on purpose. Every worker rule reads `tm_runs.task_id` as "this task's agent": the Stop hook's newer-run guard, `findResumableRun`, the task panel's latest run, per-task cost. A reviewer must never be taken for the task's agent. The SPA links an aux run to its task through `subject_id` (`RunKind.tsx`). The legacy `analyze` mode rows were migrated to `aux`/`analysis`.

**No worker slot.** The pool is separate, so `orchestrator.concurrency` (2), `activeWorkers()` and the worker PTY cap never see an aux session; the pool has its own cap of 10 live PTYs. `status()` reports them as `aux` beside `running`. The restart guard blocks on both, `/killall` and shutdown call `aux().stopAll()`, and the web Kill button reaches them through `killRun`. Callers keep their own bounds: `chat.concurrency`, and reports' `MAX_CONCURRENT` 1.

**Completion comes from hooks, never from process exit.** `buildAuxArgs` injects SessionStart, Stop, **StopFailure**, SessionEnd and Notification hooks through `--settings`, posting to the same token-guarded `/api/internal/runs/:id/*` routes as a worker's. Those routes hand any `mode = 'aux'` run to the runner before any worker logic runs.
- **Stop**: the final text goes to the caller's `accept`.
- **StopFailure**: the API refused the turn. This is how an unavailable model shows up (`model_not_found`) and how the Fable→Opus fallbacks still fire (`modelUnavailable`). The runner keeps the hook's `error` code on the outcome (`AuxOutcome.code`), and that code is all `modelUnavailable` reads (§ Adversarial review, "A failure is recorded as itself").
- **SessionEnd** without a result is a failure. Process exit is only the backstop.
- The Notification hook raises the run's needs-attention flag for a real prompt. It ignores the CLI's 60-second "waiting for your input" idle notice, except in a compaction, where that notice means it is over.

**Structured results.** An interactive session has no `-p` envelope and no `--json-schema`. The replacement:
1. The prompt ends with `resultInstruction(schema)`: return ONE fenced ```` ```json ```` block at the end of the final message, validating against the same JSON Schema `--json-schema` used to receive.
2. The Stop hook's own `last_assistant_message` is parsed (`extractJson`: the last `json` fence, then the last bare fence, then the whole text). The transcript is only the fallback for an older CLI.
3. The block is validated by the caller's existing zod schema (`acceptJson`).
4. A block that does not validate is answered by **typing a correction into the same live session** (bounded by `maxRetries`, default 2). This is never a fresh process, so it never re-buys context.

This path was measured end to end. A reviewer told to answer `PING` first got the typed correction and answered with a valid block in the same session.

**Ending.** Once a result is accepted, or a stop, timeout or failure is decided, the runner kills the PTY. `done` resolves only after the process has exited (at most 8 s later). That makes "one live process per session id" true by construction for the two kinds that `--resume` a session someone else will resume next: a chat's next turn, and the worker a compaction ran for. The terminal's ring buffer stays attachable until the pool's TTL disposes it. `aborted` means WE stopped it (Kill, a caller's `AbortSignal`, `stopAll`), and the row closes as `killed`. `timeout` is the session's own deadline.

**Crash recovery** needs nothing new. An aux row is a `tm_runs` row, so `recoverOnBoot` closes a stranded `running` one and kills its pid behind `pidLooksLikeOurs`. In practice the PTY's claude dies with the server anyway, because the master side closes; this was measured with a SIGKILL mid chat turn. Each caller's own domain recovery is unchanged: `chat.recoverOnBoot`, `recoverReportsOnBoot`, and review state `pending|reviewing` re-run as forced.

**Security (blocker B3):** Fastify listens on `127.0.0.1` only; WS upgrade validates `Origin` against the app's own origin; `/ws/terminal/:runId` requires the per-boot session token (query param). Internal routes token-guarded, localhost-only.

## Worker invocation + completion detection

Interactive session (hard requirement: real usable terminal), completion via hooks injected with `--settings '<json>'`:

- `Stop` hook + `SessionEnd` hook + **`Notification` hook** (blocker B2: fires on permission prompts/idle → task gets `needs attention — attach` badge instead of silently deadlocking) — each: `curl -s --max-time 5 -X POST -H "x-tm-token: $TM_TOKEN" "$TM_CALLBACK_URL/…" || true` (`|| true` so a flaky curl can't block stopping; callback URL injected via env, never hardcoded port)
- Args: `--model claude-opus-5-5 --permission-mode acceptEdits --settings <hooksJson> <prompt>`; prompt = title + description + standing instructions (max 3 subagents; summarize when finished)
- Config `agent.permissionMode`: `acceptEdits` (default) | `bypassPermissions` (`--dangerously-skip-permissions`, red warning; NOTE: shows a one-time interactive acceptance dialog — attach to accept, documented) + optional `agent.allowedTools` list (e.g. `Bash(git *)`, `Bash(npm *)`) as middle ground
- **Needs attention is cleared when the agent moves on, not only on Stop.** The Notification hook raises `tm_runs.needs_attention`; the human answers the prompt in the attached terminal, and nothing used to clear the flag until the next Stop, so the board, `/status` and the reports said "needs attention" for the rest of the turn. The orchestrator now stamps the time the flag was raised (`attentionFlagged`, in-memory — a restart clears the flags anyway) and the activity watcher, which already tails every live transcript, reports every new assistant line with its own timestamp (`progressed`); a line NEWER than the flag means the prompt was answered (approved: the tool ran and the agent went on; denied: it was told and went on) and `attentionProgress` clears the flag, audits `run.attention { cleared: 'agent-resumed' }` and broadcasts `run.needs-attention` with the cleared run. An OLDER line is the one that caused the prompt, still being caught up on. Consumers of `run.needs-attention` must therefore read `run.needsAttention` from the event rather than treat the event as a raise.
- Status machine: first `Stop` after spawn → `review` (or `done` if autoComplete); later Stops no-op; exit-before-Stop nonzero → `failed`; kill → `cancelled`. Run terminal at SessionEnd/exit. Exit-driven transitions are skipped for a run that was deliberately `killed` or that a NEWER run of the same task has superseded — whoever killed it already decided the task's fate (twin of the Stop-hook stale guard).
- **Session continuity ("proceed")**: a respawn may CONTINUE the previous run's claude session — `claude --resume <session_id>` with the same model/effort/hooks/permission args, and a prompt carrying only the new instruction (the session already holds the task, the standing rules and everything it did). `followUp()` does this by default (`agent.resumeSessions`); `proceed()` requires it and refuses otherwise. Resumability = newest worker run of the task with a `session_id`, the same repo (sessions live under their project dir), and its transcript still on disk — a missing transcript degrades to a fresh spawn instead of a `claude` that exits instantly and fails the task. Before reusing a session the old PTY is killed AND awaited (up to 5s): `--resume` on a session another process still holds fails, and startWorker's live-session guard would otherwise refuse its own respawn. Both runs then append to ONE transcript, so the resumed run stores `stats_baseline` (the cumulative totals at resume time) and every stats read subtracts it — otherwise each proceed would re-bill the whole session (`claude/stats.ts: netStats`/`summarizeRun`).
- Known first-run friction: per-repo workspace-trust dialog appears in the hidden terminal → visible via Notification hook/attach; happens once per repo.

## Live activity (`server/src/claude/activity.ts`)

`ActivityWatcher` tails the `transcript_path` of every live, non-idle run and emits a one-line "what is it doing right now" for the Board. It re-reads the live-run set from storage every 4s (self-healing: a dropped `SessionStart` hook or a mid-run restart cannot leave the Board blank) gated on `sessions.liveCount() > 0 || tails.size > 0`, and polls the files every 1.2s. Each assistant record yields its LAST renderable block — a `tool_use` rendered as the terminal narrates it (`describeTool`) or the assistant's own text, cut to 110 chars; sidechain records are skipped. Reads are incremental and bounded (first read seeks to the last 512KiB, truncation resets, an over-large jump re-seeks, a half-flushed trailing line is carried over). Nothing is persisted: `RunActivity` rides the `run.activity` WS event, `GET /api/runs/activity` is the reconnect snapshot, and `text: null` tells the client to delete the entry when the run stops being live.

## Orchestrator

Singleton; `orchestrator.enabled` persisted in `tm_config`. Event-driven `maybeSchedule()` (on start/enqueue/exit/stop-hook + 10s safety tick): first `pumpCustomQueue()` — the custom queue (`docs/queue.md`) claims at most one member per pass, only while no member is `running`/held and the head's repo is free, and does so even with `orchestrator.enabled` off — then, only when enabled, claim global tasks while activeWorkers < 2. Boot recovery (M4): for each `running` run row, verify pid's command line is `claude` (or `codex`, the Codex preset), kill it, then mark task `failed('server restarted')` — never leave orphaned agents editing repos. Start/Stop = stop picking new tasks (live sessions continue); separate "Stop & kill all". Untouched by Features except for claim eligibility: a task with `feature_id` is claimable only while its feature is `running` and every task in a lower phase is resolved. `resolveCompletion(task)` (formerly `resolveParent`) re-evaluates both the split parent and the feature phase gate whenever a task reaches a terminal status.

A third `.unref()`'d tick (30s) is the **auto wake-up** sweep (`docs/wake.md`): a turn stopped by the 5h usage window rather than by its work is parked with the window's reset time in `tm_tasks.wake_at` and resumed there through `proceed()` — its own claude session, one per pass, under the same switch and cap as everything else. The banner that proves it is terminal chrome, so detection reads the PTY ring buffer (the first server-side read of one) rather than the transcript, which never sees it.

## Analyze

An aux terminal per repo/task selection (kind `analysis`, § PTY sessions): `analysis.model`, `agent.effort`, `--permission-mode dontAsk`, Edit/Write/NotebookEdit/Bash denied, `--tools=Read,Glob,Grep,Agent,TodoWrite`. The prompt (repo role/path, open tasks JSON, instructions) is the positional argument after `--`, and it ends with the fenced-JSON result instruction. It does NOT use plan mode, which fights structured output (M2). The result is the fenced block validated by the same zod `proposalSchema` → `tm_proposals` rows → UI accept/reject (accept paths in the Storage composites above). `POST /api/analyze` answers with the run id as soon as the PTY is up. One analysis per repo at a time (`listRuns({ kind: 'analysis', status: 'running' })`). **Folder trust**: unlike `-p`, an interactive session in a folder the CLI has never trusted opens on the trust dialog. Registered repos are where the workers already run, so this normally never shows. When it does, the terminal is attachable and one Enter answers it (measured on a fresh scratch repo).

## Adversarial review

Every worker change is reviewed before it lands in the human queue by a reviewer that is **a terminal of its own**: aux kind `review`, subject = the task (§ PTY sessions; `claude/review.ts`, orchestrated from `orchestrator.reviewCompletedRun`). It shows in the runs list, it can be attached from the task panel, and on the board and in the panel the `auto-review` badge opens it while it is live. It is read-only exactly as the `-p` reviewer was: `dontAsk`, and `Edit`/`Write`/`NotebookEdit`/`Bash` denied. `--tools` only trims the schemas, and typing into the terminal cannot widen what it may do. Findings come back as a fenced JSON block validated by the same zod schema that used to check `--json-schema` output, Fable with an Opus 5.5 xhigh fallback cached per process (`FALLBACK_MODEL` in `review.ts`). Blocker/major findings are fed back into the SAME live worker session (`followUp`), bounded by `review.maxRounds`.

**Who reviews is per task.** `tm_tasks.review_model` / `review_effort` (migration 25, both nullable) sit beside the worker's `model`/`effort` and the `review` on/off override, with the same null rule: `reviewModel ?? settings['review.model']`, resolved in `Orchestrator.runReviewRound` and handed to `reviewWorkerChange` as `{ model, effort }`. There is no global reviewer effort setting, so `reviewEffort: null` means what it always did: no `--effort`, and `xhigh` on the Opus fallback. The fallback is kept, and it narrows in one way. Any unavailable model still retries on `FALLBACK_MODEL` (`claude-opus-5-5`), at the task's `reviewEffort` if it set one and at `xhigh` otherwise, but **only a Fable failure is cached** (`fableUnavailable`). Before, the cache swapped Opus in for whatever was asked, which would silently override a task that picked Sonnet. The `model`/`effort` written into each `ReviewRound` (and `run.reviewed`) are what **actually ran**, fallback included, so the history never claims a reviewer that did not run. **A failure is recorded as itself (2026-09-24).** Only StopFailure `model_not_found` counts as "model unavailable". `modelUnavailable` in `claude/aux.ts` reads the CLI's own code (`AuxOutcome.code`) and nothing else, and it never looks at free text. The old test matched `model|unavailable|access|not.*found` against the whole error. Under `-p` that was the `execFile` message, which echoes `--model` from the argv, so every failure matched. Under the aux runner it still took a `server_error` "Service Unavailable" or a `rate_limit` that names the model. Each such hit cost a second run and set the Fable cache until restart. A `timeout` (the reviewer's own 10-minute deadline) and an `aborted` session never fall back and never touch the cache. The one fallback is `withModelFallback` (`aux.ts`), shared by review, plan/plan-review and reports, with one process-wide Fable cache, because availability is a fact about the account. Only a failed Fable request sets that cache. Before this change, the feature and report copies also set it when some other model failed. A round's `error` is `model <m> — ` followed by the runner's reason, up to 500 characters. That reason is one of four things:
- the StopFailure code and text (`rate_limit: …`);
- `timed out after 10 min`;
- `invalid result: …`;
- for a session that quits with no hook naming the cause, the exit code or signal plus the terminal's last readable words (`readableTail`: ANSI stripped, the `Resume this session with:` epilogue dropped, at most 300 characters). That covers a refused flag or a bad `--resume`: the CLI's stderr lands in the PTY and nowhere else.

The SPA shows the reviewer dropdowns (one `MODEL_OPTIONS` array, `ReviewerPicker.tsx`) only while review is effectively on for the task, and a `reviewer <model>` chip on the board row when the pick differs from `review.model`. The Config row is labelled as the default tasks can override. Presets carry no reviewer: `matchTaskPreset` still keys on model + effort + review alone, and applying a preset leaves the reviewer as it was.

**What the reviewer reads: the change THIS task made, committed or not (2026-09-24).** It used to read `git diff HEAD` in the repo's checkout, but workers in several repos commit as part of the task (and `18 - neko-frontend` works in a `git worktree` and merges at the end), so by the Stop the tree was clean: 24 of 42 review attempts since 2026-09-10 were `empty-diff` skips, 22 of them with 1–4 commits landed in the run's window. The reviewer cannot look for itself (`Bash` is denied). Now `workerDiff(repo, scope)` (`claude/review.ts`, scope from `Orchestrator.changeScope`) builds the change from three inputs:
- **The base.** `tm_tasks.base_sha` / `base_ref` / `base_at` (migration 29, `Task.baseSha|baseRef|baseAt`) are HEAD's sha and branch at the task's FIRST worker spawn (`Orchestrator.ensureBase`, called from `startWorker` before the run row exists). Once set they never move, so retries, fix rounds and follow-ups keep the original. A task that ran before migration 29 gets its base at its next review: the first-parent commit HEAD stood on at its first run's `started_at` (`headAt`, committer dates). It never gets HEAD-now, which would hide everything it committed.
- **The task's commits.** The first choice is **by trailer**. Every worker turn carries `commitTrailerRule(task.id)` (`claude/worker.ts`, beside the standing rules, the publish turn included), which asks for `Task: <id>` on every commit. The reviewer collects commits with `git log --all --no-merges -F --grep="Task: <id>"`, so a worktree or branch commit counts before it is merged, and a second worker's commits in the same repo never do. **Fallback: base..HEAD.** When no commit carries the trailer (pre-trailer tasks, or an agent that forgot), it takes `git log --no-merges --until=<window end> <base>..HEAD`, but only when no other task's worker run in the repo overlapped the task's window `[base_at, window end]` (`soleWorker`). The window ends at the task's latest `task.transition` out of `running|waiting`, the Stop that produced the change, or now while it still runs. So a Review now days later never picks up a LATER task's commits. Merge commits are left out because the commits they bring in are listed on their own.
- **The uncommitted rest**: the old `git add -N` + `git diff HEAD`. It is read only while no other task's worker has started in this checkout after the window (`includeUncommitted`), so a Review now of an older task does not judge a later task's edits as its own.

The committed half is ONE net diff (`git diff <first>^ <last>`) when the commits form a linear chain, which is the usual case, so the reviewer judges the result and not each intermediate state. Commits spread over branches get one patch each, in order. Both halves keep `--ignore-submodules=dirty` and the `.claude/worktrees` exclusion. The prompt lists the commits (short sha + subject, and which attribution found them) above the diff, and the diff has `--- committed ---` / `--- uncommitted ---` sections. With no commits the diff is exactly the old raw `git diff HEAD`, so hashes stored before this change still match. `run.reviewed` rows carry `commits` and `attribution` (`trailer|base|none`); an `empty-diff` skip carries the `base` it used. Limits: a squash-merge whose source branch still exists shows the change twice, since both carry the trailer. A trailer-less commit made while another task worked in the repo is not attributed, and the reviewer sees only the uncommitted rest. And while two workers share one checkout, its uncommitted diff is still shared, as before.

**Each diff is reviewed once.** The change used to be `git diff HEAD` (with `--ignore-submodules=dirty` and `.claude/worktrees` excluded — see § Waiting for why), which carries every uncommitted change in the repo — so any Stop after the first saw a non-empty diff and paid for a full run that re-read work already judged. `workerDiff` now returns the diff plus its **sha256, hashed before the 60k prompt truncation** (today over the commit shas + the combined diff above, so a talk-only turn still hashes the same and a new commit does not), and the hash is stored on the task (`tm_tasks.review_diff_hash`, migration 17). `reviewCompletedRun` decides before spawning anything:

| diff | decision | `run.reviewed` row |
|---|---|---|
| empty (no commits of its own and a clean tree: the task changed nothing) | no review | `{ skipped: 'empty-diff' }` |
| hash equals `review_diff_hash` | no review; the previous verdict stands and the task stays in `review` | `{ skipped: 'unchanged-diff' }` |
| new or never reviewed | review runs; `reviewSummary` + `review_diff_hash` written together | `{ model, verdict, findings }` |

This is what stops **dispatch-reply turns from being reviewed**: a dispatch delivery resumes the target's own session (`docs/dispatch.md`) and usually only answers a question, so it Stops with a byte-identical diff and hashes the same — no reviewer session, no tokens. Nothing in the code special-cases dispatch; the hash is the whole test, which also covers answered questions, human follow-ups that only talked, and a re-entry after a failed publish. A skip settles the fix loop (`reviewRounds` cleared) exactly as a clean verdict does. Both skips are audited rather than silent, so a missing review is a decision in the log and not a gap; the Telegram report counts them on their own line and excludes them from "review rounds" (`telegram/report.ts`). A skipped round has no verdict event, so the Telegram review ping arrives bare — deliberately, since re-showing the previous round's badge next to live Publish buttons invites shipping on a stale verdict.

**One round at a time per task.** A round takes minutes and only stamps the hash when it returns, so two Stops for one task can overlap — and the likeliest producer is the very case above: `deliverDispatches` holds a target that is `running`/`queued`/`blocked` but NOT one sitting in `review`, so a pending dispatch can resume the task seconds after its Stop, the agent answers without editing, and that second Stop reaches `reviewCompletedRun` while round #1 is still running and the hash is still null. `pendingReviews` is therefore a map of in-flight promises: an overlapping call adds the task to `reviewRecheck` and **returns the in-flight promise** (the stop-hook route releases its custom-queue hold in a `.finally` on what this returns, and that hold must outlive the round that is actually running, not the call that merely joined it). When the round settles, one more pass runs — free if the diff is unchanged, a real review if that late turn did edit something, so a remembered Stop is never a swallowed one. The extra pass is skipped when the task is no longer in `review`: a fix round already moved it back to `running` and its own Stop will come through here.

**The review has a persisted state and a persisted history (2026-09-06).** `tm_tasks.review_state` (migration 22, `Task.reviewState`) says where the review of the CURRENT change stands, and it is written in the same row write as the status it qualifies, so no surface can read `review` without knowing whether the reviewer has spoken: the Stop route's transition carries `pending` when a review will run and `null` when one will not (publish turn, auto-publish, review off); `runReviewRound` moves it to `reviewing` before the diff is read, then to `fixing` (findings handed back, task `running` on them), `passed` (no blocker/major open), `flagged` (blocker/major open and the loop ended — cap, no live session, human took over), `skipped` (clean tree) or `error` (the reviewer could not run). An unchanged-hash skip settles on the state the last round implies (`settledReviewState`), never on a fresh one. Every real review is appended to `tm_tasks.review_rounds` (`Task.reviewRounds`: model, effort, verdict, findings, the reviewer's **summary**, the fix round that produced the diff, its hash, the failure reason); skips stay audit-only. The reviewer's structured output gained that `summary` — an overall reading of the work as it stands, written for the human who decides — because after a fix round the worker's own last message is "fixed 1 and 2", and a second review of a fix round quotes the previous findings and is asked to say which are resolved rather than rediscover them. The worker's `resultSummary` is no longer overwritten by a fix-round Stop: the fix message is appended as a "Fix round N" section under the original account (`appendFixNote`, oldest fix notes give way first, bounded at 12k). The fix-round BUDGET (`Orchestrator.fixRounds`) stays in memory and separate from the history — it is reset whenever the loop settles or a human re-arms it with Apply review fixes, which the history is not.

What reads the state: the SPA renders `review` + `pending|reviewing` as a synthetic **auto-review** badge and `running` + `fixing` as **fixing** (`StatusBadge`, no new `TaskStatus` — the same pattern as the needs-attention badge), and the task panel's review section (`ReviewPanel`) opens with "Reviewed by <model>" / "Review flagged N issue(s)" / "Auto-review in progress…", the latest round's summary, and the rounds as collapsible entries (latest open, any one selectable). The Telegram review ping waits for the state to settle and reads the verdict and model from the row (`docs/telegram.md` § Notifications). Boot recovery re-runs the review of any task left `pending|reviewing` on a `review`/`done`/`blocked`/`failed` row (the reviewer died with the server; the hash makes it free when nothing changed) and settles a `fixing` that is no longer running on its last round. A persisted `pending|reviewing` is a decision already taken — by the Stop route or by a human's Review now — so the re-run is `forced` (below): `review.enabled` is not re-checked. A round that throws mid-way settles its row on `error` instead of stranding `reviewing` until the next boot, and a pass that finds the task on a status it will not review releases a `pending|reviewing` mark back to the last verdict.

**Review now — the reviewer on demand, per task (2026-09-16).** `POST /api/tasks/:id/review` (service `reviewTask` in `task-actions.ts`, actor-parameterised; the SPA's **Review now** button beside Apply review fixes, Telegram `/review <id>` and the 🔍 Review card button) runs the SAME round as the automatic one — `Orchestrator.reviewNow` → `reviewLoop` → `runReviewRound`, the same `pendingReviews` lock, state steps, `review_rounds` append and `run.reviewed` rows — where Apply review fixes only resumes the worker and never runs the reviewer. Unlike the automatic round it is **forced**:

| | automatic round (after a Stop) | Review now |
|---|---|---|
| accepted statuses | `review`, `done` | `review`, `done`, `blocked`, `failed` — anything else 409 with the reason; no repo 409 |
| `review.enabled` / per-task `review` | honoured | not consulted — the human asked |
| unchanged-diff gate | skips on an equal hash | **bypassed**: `review_diff_hash` is cleared in the same write that marks `pending`, so the round (and a restart's re-run of it) reviews for real; the new hash is stamped when it returns |
| empty diff | `skipped` | `skipped` (nothing to judge is still nothing) |
| round in flight | joins it (`reviewRecheck`) | **409 `review already in progress`** — the lock is checked and taken synchronously |
| fix-loop budget | as left | reset (`fixRounds` cleared) — a fresh `review.maxRounds` |
| audit | `run.reviewed` (`actor: system`) | a `task.review-requested` row with the requester, then `run.reviewed` rows carrying `requestedBy`; the round records `ReviewRound.requestedBy` |

**What the verdict does depends on where the task is, and only there**: a task in `review` with a live session gets blocker/major findings fed back exactly as an automatic round would (fix round, bounded by `review.maxRounds`, task `running` + `fixing`); a `done`/`failed`/`blocked` task, or one in `review` whose session is gone, only gets the verdict and summary written on the row — **the status is never changed by a requested review**. The route answers at once with the row marked `pending`; the verdict arrives as `task.updated`. The SPA disables the button while `reviewState` is `pending|reviewing|fixing`, and the Telegram card hides it. The button deliberately does **not** `refresh()` the task list after the POST (2026-09-24): an empty or unchanged diff settles the round within milliseconds, and a full list read in flight across that write arrived after the WS `skipped` row and pinned a stale **auto-review** badge on a task nothing was reviewing — the two `task.updated` broadcasts carry both steps, in order. Review now reads the same task-scoped change as the automatic round (*What the reviewer reads*, above), so work the worker already **committed** is reviewed too. That gap closed on 2026-09-24. The requester is held in memory only (`requestedReviews`, beside the lock): a requested round a restart re-runs completes, but records no `requestedBy` and pings nothing for a non-`review` task. Not special-cased: a request that loses a race with a status change (e.g. a Proceed in the milliseconds between check and write) finds a status it will not review, releases its mark, and leaves the hash cleared — the next automatic round then reviews rather than skips.

**Review before ship** (2026-09-24). The round runs at the worker's Stop, but some repos' CLAUDE.md make the worker's own turn commit, push to `origin/main`, deploy (Vercel/ECS) and verify live, so a blocker the reviewer found was already in production and the fix round shipped a second commit after the fact. So a task whose change WILL be reviewed — `shipHeldForReview(task, settings)` in `claude/worker.ts`: `!autoPublish && (task.review ?? review.enabled)`, the same test the Stop hook uses to write `reviewState: 'pending'`, so the prompt never promises a review that will not run — carries `SHIP_GATE_RULE` on every worker turn: the fresh prompt (after the standing rules) and every resumed turn (after the reminder), so fix rounds, Proceed, follow-ups and dispatch turns are covered as well. **The publish turn is the one exception**, because lifting the gate is what that turn is for. The rule overrides the repo's CLAUDE.md for that session: no `git push`, no deploy, no production verification. Committing locally is fine, because the reviewer reads the task's commits as well as the working tree. The ship happens in the publish turn: `PUBLISH_INSTRUCTION` step 5 runs the post-push deploy/verify steps the repo's own instructions require, only after the push succeeded, and `verifyPublished()` still judges the git side. What does not change: review-off tasks (the Small/Routine presets, or `review: false`) get no rule and keep the repo's own push behaviour; auto-publish skips review as before, so it gets no rule either; Publish is offered from `review` whatever the verdict, so the human can still ship past a `flagged` review. It is a prompt rule, not a hook (`docs/decisions.md`). Limits: an agent that ignores it still pushes, and the in-process fallback `publishRepo()` (no resumable session) only commits and pushes, with no deploy step.

## Waiting

**A turn's end is not always the work's end (2026-09-07).** The Stop hook fires whenever the main agent finishes responding — including when it ends a turn with a **background subagent** of its own still running, because the CLI re-invokes the session with the child's result when it returns. The Stop route could not tell that turn from a finished one: every worker Stop went `running → review` + `reviewState: pending` and the reviewer ran over a half-done tree, found "nothing implemented", returned a blocker, and the fix round resumed an agent that was mid-wait — while the board said **review** about a task whose own summary said "the exploration agent is still running". The user's ask was a status that tells the truth, and the cause of the premature review.

**`waiting` is a real `TaskStatus`**, the first one added since `blocked` and against the standing preference for synthetic badges (`docs/wake.md` § The state; `docs/questions.md` § Deliberately not). A badge would not do here because the row must NOT read `review`: `reviewCompletedRun`, the Telegram review ping, the custom-queue hold and `deliverDispatches` all key off that status, and each of them would act on a turn that is not over. `waiting` means: the agent's PTY is live and **not idle** (it keeps its worker slot and its repo — `liveCount`, `repoBusy` and the dispatch `busy` test all read `!idle`, so no second agent enters that tree), no review runs, `reviewState` is `null`, and `resultSummary` carries the agent's last words so the panel says what it waits for.

**How the server knows.** Two more hooks are injected beside Stop (`claude/worker.ts`): `SubagentStart` and `SubagentStop`, both firing for background subagents as well as foreground ones, both fire-and-forget like the rest, POSTing to `/api/internal/runs/:id/subagent-start|stop` with the child's `agent_id`. The orchestrator keeps the set of children still out per run (`childrenInFlight`; an id-less hook is counted rather than dropped). The Stop route asks `waitDecision(runId)` **after** its transcript-flush sleep, so a child that returned during it counts as returned; with children out the task goes `waiting` (conditional from `running|waiting`, audited `task.waiting { children }`) and the route returns without idling the session or touching the review. The wait ends through either of two channels, both `waiting → running` (`endWait`, audited `task.waiting { resumed }`): the **last child's `SubagentStop`** — the CLI is about to re-invoke the session — or a **transcript line newer than the park** from the activity watcher (`attentionProgress`, the same test that retires a needs-attention flag: the Stop's own last line is older), which covers the re-invocation the watcher sees first and a human typing into the attached terminal. The next Stop then lands the ordinary way; it accepts `waiting` as well as `running` because a turn shorter than the watcher's poll can end before the row has moved.

**The CLI's own ledger beats the hook count (2026-09-14).** The count alone was still landing tasks mid-wait: measured on CLI 2.1.266, the CLI fires `SubagentStop` for its **own helper agents** (`agent_type: ''`) that never fired a `SubagentStart`, and `subagentStopped` let an unknown id "stand for any one child" — so a helper's stop erased the Explore agent the task was waiting on, the next Stop saw zero children, and the reviewer judged a tree with nothing in it ("nothing implemented", blocker, fix round resuming the session). The same measurement showed the way out: every `Stop` and `SubagentStop` payload carries `background_tasks: [{ id, type, status, … }]`, the CLI's list of what is still out at that moment. `runningSubagents()` (`routes/internal.ts`) reads the `type: 'subagent'` entries with status `running|pending` — a background shell (a dev server) is deliberately not a child — and, when the payload has the list, `waitDecision`/`subagentStopped` **replace** the run's set with it, less every id whose `SubagentStop` was already seen (`returned`, kept for the life of the run, so a Stop payload captured before a child's stop hook landed — the route sleeps 1.5s first — does not count it again; a `SubagentStart` for the same id, a child continued with SendMessage, takes it back out). An unknown id's `SubagentStop` now touches nothing but `returned`. The hook count remains only as the fallback for a CLI that sends no list.

**Guards.** On the hook-count fallback, a Stop that arrives while the task is STILL parked on exactly the same children snapshot means neither channel fired and yet the agent spoke — most likely a lost `SubagentStop` curl — so that turn is landed rather than re-parked, audited `task.waiting { stale: true }`: a lost hook degrades to the old behaviour, never to a task held forever. When the payload carries `background_tasks` there is no `stale`: that list is not rebuilt from hooks, so it cannot have lost one, and two Stops seconds apart on the same live child ("Launched." then "Waiting for the Explore agent…", both before the watcher polls either line — measured) is the ordinary case the guard used to misread. `handleExit` (the session died while waiting), `cancel`, `killRun`, the boot orphan sweep and the stranded sweep all treat `waiting` as they treat `running`. `deliverDispatches` holds a `waiting` target (a resume would kill the session the child is about to return to); the custom queue counts it in flight (`queue-sql.ts` + `CUSTOM_QUEUE_IN_FLIGHT_STATUSES`); the feature claim gate already blocks on anything non-terminal. `followUp` does not list `waiting` on purpose: its live-session check refuses first with the honest reason, and Proceed on a session that is about to speak on its own is not a thing to offer. A publish turn is never parked — git settles it.

**The other half of "too fast": the diff had noise.** `workerDiff` ran `git add -N .; git diff HEAD` with no filter. The CLI's own `.claude/worktrees/<name>` is a nested git repo: `add -N` records it as a gitlink (`+Subproject commit …`), and once tracked, every read renders it `-Subproject commit X` / `+Subproject commit X-dirty` — bytes that differ from the previous hash on every Stop, so the "reviewed once" gate never fired and a real `claude -p` judged a diff with no work in it (the blocker in the report). Now `git add -N -- . ':!.claude/worktrees'; git diff HEAD --ignore-submodules=dirty -- . ':!.claude/worktrees'` (`DIFF_EXCLUDES`): a submodule pointer moved to a different commit still shows; a merely dirty one and the worktree directory never do. `verifyPublished()` and the repo status count apply the same `--ignore-submodules=dirty`, because that dirt is nothing the superproject could ever commit and it was failing the clean-tree check with "1 uncommitted change".

**Background shells hold the park too — for a bounded time (2026-09-15).** This section used to leave background **Bash** (`run_in_background`) out, and on the premise that "the transcript-progress channel at least keeps the later turn from being swallowed" — which was false: a landed turn idles its run, the watcher tails only non-idle runs, and the Stop route drops every Stop of an idle session, so the agent's later turn was invisible. The incident (S3-T3, a frontend task): the worker started a 10-minute Lighthouse pass in the background and ended its turn with "Lighthouse is 6 of 20 runs in … I'm waiting for it to finish". That Stop landed `review`, the reviewer ran over the half-finished close-out (blocker), and the fix round's `--resume` killed the PTY — and the Lighthouse shell with it — then paid a ~300k-token compaction. The same thing happened again on the fix round's own "holding until it completes". Measured on the real CLI: the Stop payload's `background_tasks` lists such a command as `{ id, type: 'shell', status: 'running', command, description }`. `runningShells()` reads those entries (status `running|pending`) and `waitDecision` counts each one — but only for **`agent.shellWaitMinutes`** (default 30, 0 = shells never hold a task) from the **first** Stop that listed it (`shellsSeen`, per run, so a dev server does not earn a fresh budget every turn). That bound is the whole answer to why shells were excluded before: a shell the agent waits on and a dev server it left running look identical at the Stop, and only the former ever re-invokes the session. The park is audited `task.waiting { children, shells }`. A park that shells help hold arms a timer at the earliest counting shell's deadline (`armShellWait`); when it fires, the orchestrator hands the park's own payload back to the route (`onShellWaitExpired` → `settleStop(…, replayOf)`), which takes the same decision again. If something still counts (a later shell, a child still out), the same park goes on (`rearmShellWait` keeps its `at`). Otherwise the turn lands the ordinary way — `review` and the reviewer — audited `task.waiting { expired: 'shell-wait', waitedMs }`. A replay skips the flush sleep and the attention/question sweep (nothing about the turn is new), does nothing on a run flagged `needsAttention` (the session is mid-turn, blocked on a human), lands only from `waiting` and only for the park that armed it (`parkedAt(runId) === replayOf`), so a session that started talking meanwhile is never landed under its feet. While shells hold a park, the last child's `SubagentStop` does not end it (the CLI's helper agents fire those at any time, and ending the park would drop the timer and leave an idle session reading `running`); the re-invocation is seen as a newer transcript line anyway. `endWait`, a landing and `handleExit` all clear the timer (`dropWait`).

**Not covered, deliberately.** An agent that ends its turn to wait on a **task it filed** (instruction sheet rule 5) is a real end of turn with nothing to re-invoke it, so it lands in `review` as before; the human reconciles, and dispatch is the tool for the reply. A background shell that outlives its budget lands the same way, and its later re-invocation of an idled session is still not seen — the budget exists so that case stays rare. Both are readable from the row: `waiting` never claims either.

`review.maxRounds` defaults to **1**. Each round resumes a 300–500k-token session before it does any work, and the token audit (2026-08-31..09-01: 36 reviews for 17 tasks) found the second round almost never actionable. Still configurable 0–5 in Config; `feature.analysisMaxRounds` is a separate budget for plan review and stays at 2.

**Feature analysis** reuses the same envelope, `dontAsk` + disallowed write tools, and zod validation, but runs the loop shape of the diff review instead: a plan run decomposes the request into phases, a SECOND independent run reviews that plan adversarially, and a `blocker` verdict folds the findings into a re-analysis, bounded by `feature.analysisMaxRounds` (default 2). One run row spans the whole pipeline; each child registers with `trackHeadlessChild` so Kill always reaches the live process. Full design + as-built notes: `docs/features.md`.

## API

REST `/api`: repos CRUD; tasks CRUD + `/enqueue|run-now|cancel|retry|unblock|complete|follow-up|proceed|review|apply-review|stop-agent` + `/queue|unqueue` (custom queue, `docs/queue.md`) + `GET /tasks/:id/resumable`; runs list + `/kill` + `GET /runs/activity` (current live-narration line per live run — the snapshot behind the Board's activity captions); `/analyze {repoId, taskIds?}`; proposals list + `/accept|reject`; features CRUD + `/analyze|plan|approve|start|pause|resume|cancel|complete`; dispatches list + `/cancel` (agent side: `POST /api/agent/dispatch`, `GET /api/agent/dispatches/:id` — `docs/dispatch.md`); config get/put; orchestrator get + `/start|stop|stop-and-kill`; `/usage` (session + weekly + weekly-fable windows, each `{pct,source,resetsAt,tokens,budget}` — real account figures from the CLI's `~/.claude.json` cache, local-transcript estimate as fallback); internal `/internal/runs/:id/{stop,session-start,session-end,needs-attention,question,subagent-start,subagent-stop}`; `/health`.
WS: `/ws/terminal/:runId?token=…` (history/data/exit ↔ input/resize, base64-in-JSON) and `/ws/events` (task.updated, run.started/exited, run.needs-attention, run.activity, proposal.created, dispatch.updated, feature.updated/deleted, orchestrator.status) — frontend fully event-driven, no polling.

## Frontend

The task panel's **Follow-up** block has two buttons: *Send follow-up* (continues the previous session when one exists, else respawns fresh) and **Proceed** (`POST /tasks/:id/proceed`), which only ever continues — enabled from `GET /tasks/:id/resumable`, which is re-checked whenever one of the task's runs gains a session id or ends. Empty follow-up text = a plain "carry on from where you left off".

**Presets** (`PresetPicker`/`PresetChip`, `useTaskPresets()`): the built-in `TASK_PRESETS` plus the user's `presets.custom` setting (Config → Presets, `PresetEditor`), merged by `taskPresets(settings)`; a custom preset is drawn with a group palette slot (`.preset-color-N` → `--tm-group-N`), the built-ins keep their `--tm-preset-*` tokens. The list rules (`customPresetProblem`: ≤12, unique names and ids, no repeated model/effort/review) are shared by the settings route's zod validator and the editor's inline warning. Sidebar (Board, Queue, Features, Repos, Config) + header (prominent Start/Stop switch, `running N/2`, usage pill `5h % · wk % · fable % · routed model`, server uptime/restart, **mobile emulator** toggle, theme toggle). Board: status columns, cards with per-row quick actions (terminal glyph before the title → attaches to the task's live/most-recent run; run-now + mark-as-ready after the status badge — the check means **mark done** (`complete`) on a task in review, `enqueue` elsewhere — disabled with a reason when the server would reject them, including the client mirror of `hasLiveSession()` — `components/TaskRow.tsx`, shared with Queue's queued list), **preset chip** (Small green / Routine blue / Complex violet — `PresetChip`, derived from the task's model+effort+review, absent when they match no preset)/source chip/repo tag/parent indent/needs-attention badge → TaskSlideOver (edit, proposals accept/reject, Enqueue/Run now/Open terminal/Analyze/Unblock). Above everything sits **active** — every `running` + `review` task in the current filter (running first, each newest-touch first, never capped), which under `group: status` REPLACES the now-suppressed `running`/`review` groups; under `group: category`/`repo` it is a pin and the rows stay in their groups too. Directly below it sits **drafts** — the inbox, capped at 7 rows behind a `show all N` toggle — while **recent** (the 10 most recently updated tasks, whatever their status) closes the page instead of opening it; under `group: status` both the active and draft buckets are suppressed from the grouped lists below, under the other groupings they are cross-cutting pins. Every section header is a fold button (`Section` + `.section-fold`, `aria-expanded`), `status:done`/`status:cancelled` start folded, and a **sort** select (last touched / newest filed / oldest filed / title A–Z / **queue order**) orders every list except `recent`, which is last-touched by definition; members inside a group are always in manual order. Rows (except `recent`) carry a drag grip — drop above/below to reorder, onto a task to join its group, onto a group header to append — and group headers fold and rename inline (`docs/grouping.md` § Drag and drop). While a task's run is live, its row carries a dimmed mono **activity caption** under the title — what the agent is doing right now (`Write notes.md`, `Read runs routes and api client`, `Subagent · Explore codebase`, or the sentence it just said), with a pulsing accent dot; it disappears the moment the run goes idle. Each row ends with an **age** — the timestamp the current sort uses (created for drafts, updated for recent), tooltip carrying both absolute times — dimmed past 14 days; a task filed in the last 24h gets an accent edge on the row (`.task-row.fresh`) plus an accent age with "new" in its tooltip. The **essentials** toggle strips the board to titles + status badges (no chips, no ages, no `recent`, no done/cancelled). The **+ New task** form ends in an **On create** row — Draft (file only) / Queue (`enqueue`) / **Run now** (`run-now`), the same endpoints the row actions use, disabled without a repo — and its primary button renames itself accordingly. Sort, essentials, the folded set and the filters (repo, source, category, group, dispatches, group-by) persist in `localStorage['tm.board']` (validated on read, storage failures ignored; a filter naming a repo/group/category that no longer exists reads as `all`). On a phone the whole Board is a different arrangement — filter sheet, two-line rows with ⋯ actions, a pinned task-panel action bar and a full-screen terminal with a compose bar (`docs/mobile.md` § Board, § Task panel, § The terminal). Queue: active runs (elapsed, Open terminal, Kill) + queued list. Features: list + intake form per repo, then a Feature page — request, analysis summary/considerations, adversarial plan-review verdict, and the plan as horizontal **phase columns of editable task cards** (edit/exclude/reorder/move/add pre-approval, Save plan → Approve). After approval the same columns become the execution dashboard: cards are the real tasks, live over `/ws/events`, current phase highlighted. Repos: path+role+**dev URL** table (the dev URL is edited inline, saved on blur/Enter, and re-rendered from the server's normalised value), add form with server-side path validation, per-repo Analyze. Config: Storage / Agent (permission mode with warning, allowedTools) / Orchestrator / Sentry-stub groups. TerminalDrawer: xterm + fit, **StrictMode-safe effect cleanup (close WS + `terminal.dispose()`)**; a click outside the drawer **compacts** it by default (`terminal.clickOutside`, Config → Terminal: `close | compact | nothing`) to a full-width footer bar — status dot (green running / yellow review / grey ended), terminal name (task title, command name, or session id), the live activity line beneath it, chevron-up to reopen — with the WS and xterm buffer kept alive (the body is only hidden, refit on expand), and any "open terminal" click re-expands it (`expandSignal` nonce). Theme: CSS variables `:root` (light) + `[data-theme="dark"]`, localStorage + `prefers-color-scheme` default; 13–14px system font, ui-monospace for paths, 1px borders, subtle radii.

### Mobile shell (`docs/mobile.md`)

Below 768px `useIsMobile()` (`components/Layout.tsx`) swaps the sidebar for a five-slot bottom tab bar (Dashboard · Board · Queue · Features · **More**) and moves every header control the compact top bar cannot hold into the More sheet, which also carries the whole nav so the four slots are a shortcut rather than the only route. It is a JS branch, not a `display:none` pair, because a control rendered in both parents is *mounted* twice. The CSS keys off the `.app.mobile` class that hook sets — one source of truth for the breakpoint. New tokens: `--tm-tabbar-h` / `--tm-tabbar-clear` (0px on desktop, so `.main`'s bottom padding and `.term-drawer`'s `bottom` read it unconditionally), `--tm-tap` / `--tm-tap-dense`, `--tm-text-input`; `.app.mobile` also sets `--tm-sidebar-w: 0px`, which repairs `.term-drawer` and `.cmd-pop` for free. Queue/Features/Repos tables stack into labelled blocks (`.stack-tbl` + `data-label`) rather than scrolling, because the actions column is the one that would go off-screen. **The emulator is not mounted on mobile** — a phone framing a phone is noise.

### Mobile emulator (`components/Emulator.tsx`)

A floating, draggable phone window that frames a repo's own dev server, so a change an agent just made is visible without leaving the board. `EmulatorLauncher` (header phone button) owns the open flag and the window; the window is `position: fixed`, z-index 28 — above the terminal drawer (25), below the task slide-over and its overlay (30/31), which are a deliberate focus change.

- **Source**: `repo.preview_url`, set per repo on the Repos page. Bare `localhost:5173` is accepted and normalised server-side; the scheme is pinned to http/https **twice** — once in `routes/repos.ts` (`normalizePreviewUrl`, the only write path) and again in `frameSrc()` before the string ever reaches an iframe `src`, so a row that predates the validation or was edited straight in the DB still cannot inject a `javascript:` URL.
- **Mobile only, on purpose**: the browser tab already is the desktop viewport. Presets are iPhone SE / 14 / 14 Max / Pixel 7 / Galaxy S8; the iframe is laid out at the true device pixel width and `transform: scale()`d down, so the framed page reports the real mobile viewport (verified: a 430-wide preset reports `innerWidth === 430`) instead of being resized into a desktop breakpoint.
- **Auto-fit**: on open and on device change the zoom drops to the largest preset that fits the viewport (a 932px phone at 100% does not fit a laptop). It only ever shrinks — an explicit zoom choice is never overridden.
- **Drag** uses pointer capture on the two header rows (controls keep their own clicks) and the iframe goes `pointer-events: none` mid-drag so the framed page cannot swallow the gesture. The position is clamped into the viewport on drag, on device/zoom change and on window resize.
- **Path box** re-points the frame (`new URL(path, previewUrl)`); Enter on an unchanged path means reload. The frame is cross-origin, so this is where the page was *sent*, not where it navigated to — the reload button remounts the iframe by key rather than touching `contentWindow`.
- Repo choice, device, zoom, path, position and the open flag persist in `localStorage['tm.emulator']` (validated on read). If the remembered repo loses its dev URL or is deleted, the window falls back to the first repo that has one and resets the path; with none set it shows a pointer to the Repos page.
- Live-reload comes from the framed dev server's own HMR — the emulator neither polls nor injects anything into it. A dev server that sends `X-Frame-Options: DENY` / restrictive `frame-ancestors` cannot be framed at all; the open-in-new-tab button is the escape hatch.

## Commands

- `npm run dev` — concurrently: the front door (`tsx server/src/host.ts`, which spawns the API as a `tsx watch` child on 127.0.0.1:5175) + `vite` (5173, proxy `/api` + `/ws` to the API and `/host` to the front door). Open **:5173**.
- `npm run build` — `vite build` (SPA only)
- `npm start` — `tsx server/src/host.ts`: the front door serves `web/dist` at `http://localhost:5176` and proxies to the API it supervises on 5175
- `npm run dev:server` / `npm run dev:web` / `npm run start:api` — each half on its own; `start:api` is the old single-process behaviour (the API still serves `web/dist` at :5175 as a fallback)
- `npm run dev:lan` / `npm run start:lan` — the same, with `TM_LAN=1`: every half binds dual-stack `::` and the Host/Origin allowlists widen to private addresses only, so a phone on the same Wi-Fi can open the board (`docs/mobile.md`). Off by default; the terminal WS is a code-execution surface.

## Front door (`docs/host.md`)

`server/src/host.ts` is a separate process that serves the SPA, reverse-proxies
`/api` + `/ws` to the API, and supervises the API as a child (`/host/status`,
`/host/start`, `/host/stop`, `/host/restart`). The point is that the page and
the server stop sharing a lifetime: the API can stop, crash or restart while the
page stays up, and the page has something alive to start it again. A proxy
rather than a second origin, deliberately — the SPA stays same-origin, so no
CORS and no loosening of the `Host`-port equality check that is the
DNS-rebinding guard. `TM_SUPERVISED=1` makes the API's own restart route exit
instead of detaching a replacement, so there is never more than one supervisor.

## Repo commands (`docs/commands.md`)

Saved per-repo command lines (`tm_commands`, migration 13) run in their own
`SessionManager` pool: one-shot scripts and long-running dev servers, attachable
at `/ws/terminal/cmd-<uuid>`, with a running-state indicator in the header. The
command text is tokenized and spawned as argv — never through a shell. Runs are
in-memory by design (a PTY dies with the server, and `tm_runs` means "agent").
Restarting the server is refused while agents are working.

## Terminals (`docs/terminals.md`)

Plain login shells per repo (`/terminals` page): `$SHELL -l` with cwd = the repo,
1–4 per click, at most 10 open, in a FOURTH `SessionManager` pool so they never
touch agent concurrency. In memory only (`ShellRunner`), attachable at
`/ws/terminal/sh-<uuid>`, killed on restart/shutdown but never blocking it.
