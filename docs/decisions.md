- **2026-08-25 — "Proceed": follow-ups continue the agent's own claude session**: a worker whose terminal dies mid-task (usage at 100%, dropped connection, server restart, TTL eviction) used to be recoverable only by starting a fresh agent from the task text plus a summary — throwing away everything it had worked out. A respawn now reuses the previous run's session via `claude --resume <session_id>` (same model/effort/hooks/permission args; the prompt carries ONLY the new instruction, because the session already holds the task, the standing rules and its whole history). `POST /api/tasks/:id/proceed` is the explicit form behind the **Proceed** button and refuses when there is nothing to continue; plain follow-ups do the same continuation by default via `agent.resumeSessions` (on), which also gives the adversarial review→fix loop and *Apply review fixes* their context back. **Run now** deliberately still starts clean.

  Resumability is server-side truth (`GET /api/tasks/:id/resumable`): newest worker run with a `session_id`, same repo (sessions live under their project directory), and the transcript still on disk — a missing transcript degrades to a fresh spawn rather than a `claude --resume` that exits immediately and fails the task (verified: an unknown session id prints "No conversation found" and exits). PTY-injecting text into the idle session was rejected for the reason already in the code: a session sitting at the prompt does not reliably submit injected input.

  Two correctness consequences, both handled. (1) Both runs append to ONE transcript, so a resumed run stores `stats_baseline` — the cumulative totals at resume time — and every stats read subtracts it (`netStats`/`summarizeRun`); without this each proceed would re-bill the entire session in run stats AND in the `run.stats-final` events behind the dashboard. `contextPct` passes through untouched (it is a last-turn measure, not a total). (2) Reusing a session means killing its PTY first, so the kill is now AWAITED (≤5s) — `--resume` on a session another process still holds fails, and `startWorker`'s live-session guard was rejecting its own respawn with "previous session is still live" (a pre-existing race, observed as a 500 on a follow-up to a task with a live idle session). Exit handling gained the matching guard: a run that was deliberately `killed`, or that a NEWER run of the same task has superseded, no longer drives the task's status — whoever killed it already decided.

- **2026-08-25 — Terminal keep-alive is configurable, 0 = forever** (`pty.sessionTtlMinutes`, default 30): the 30-minute idle/exited TTL was hardcoded. Keeping terminals forever is safe because the two evictions are independent — the age GC is what the setting disables, while the `MAX_LIVE_SESSIONS` (10) pressure eviction still reclaims the oldest unwatched session on every spawn, so an infinite TTL cannot wedge the cap. `pty.scrollbackBytes` and the TTL are now re-read from settings every 30s instead of only at boot, so both take effect without a restart. Proceed makes the TTL much less load-bearing anyway: continuing a session reads it from disk, so an evicted terminal is no longer a lost session.

- **2026-08-25 — The Board says what each agent is doing right now**: a running row said `running` and nothing else, so the only way to know whether an agent was reading files, waiting, or writing the wrong thing was to open its terminal. Every task row now carries a dimmed mono caption under the title — the live narration line — with a pulsing accent dot.

  **The line comes from the transcript, not the PTY.** Extracting it from the terminal stream was the obvious route and was rejected: the CLI renders through Ink, which repaints its bottom region with cursor moves and erase-line sequences, so "the last line on screen" is only recoverable by emulating a terminal (a headless xterm per session) and every heuristic short of that is a guess against a repainting frame. The transcript already carries exactly the two things the terminal prints — the tool the agent invoked and the text it said — as structured records, which is why `stats.ts` already reads it. `describeTool` renders a `tool_use` the way the terminal narrates it (Bash → the agent's own `description`, falling back to `$ command`; Read/Write/Edit → basename; `Task` → `Subagent · <description>`; `mcp__server__tool` → the tool alone), and the last renderable block of an assistant record wins, so a message that says something and then calls a tool shows the tool — the same order the terminal prints. Sidechain records are skipped: a subagent's turns are not this session's narration, and the parent's `Subagent · …` line already says one is running.

  **It is a live signal, not history — so nothing is persisted.** No column, no migration, no write per tool call. `RunActivity` rides a new `run.activity` `ServerEvent` and lives in an in-memory map; `GET /api/runs/activity` is the snapshot a fresh page or a WS reconnect starts from. `text: null` is the server saying "this run is no longer live", which the client turns into a delete — so a task that lands in `review` drops its line instead of freezing on whatever the agent last did.

  **The watcher pulls the live-run set rather than being pushed at.** Wiring `track`/`stop` into the spawn and Stop paths would have been less code, but the transcript path only exists once the `SessionStart` hook's curl lands, and a hook that fails (or a server restarted mid-run) would leave the Board permanently blank with no way back. Re-reading `listRuns({status:'running'})` every 4s is self-healing, and it is gated on `sessions.liveCount() > 0 || tails.size > 0` so an idle server never issues the query. Tailing is incremental and bounded — first read seeks to the last 512KiB (a resumed run shares the earlier session's entire transcript, and only the newest line matters), truncation resets the offset, an over-large jump re-seeks, and a half-flushed trailing line is carried to the next read; a mid-line seek simply fails to parse and is dropped, which is the correct outcome. Unchanged text emits nothing, so a stalled agent costs zero traffic.


- **2026-08-26 — Task groups: a tree is one nameable, colourable, filterable thing** (`docs/grouping.md`): parent/child links existed but nothing made the *tree* addressable — a child knew its parent and no more, so the Board nested exactly one level (`withChildren` walked roots + direct children) and a split's pieces could not be filtered, named or coloured together. `tm_tasks` now carries `group_id` (root ancestor; a task with no parent is its own group, so the column is never null) and `group_path` (ancestor ids root-first, `/rootId/midId/` — the literal path to the first parent), plus root-row-only `group_name` and `group_color`.

  **Denormalized rather than recursive.** The board wants a whole tree per query and it has to run on both drivers — better-sqlite3 is sync-only, Postgres is a second dialect — so `group_id` answers "the tree" with an indexed equality and the path answers "the ancestors" and "the subtree" (a `LIKE` prefix range) with no join and no CTE. The consequence is stated rather than hidden — deleting a root loses the name, which is correct, because the group it named no longer exists.

  **The shell branches in JS, not in CSS.** `useIsMobile()` reads one query — `(max-width: 768px)` — and `Layout` builds one tree for one shape. The tempting alternative, rendering both arrangements and hiding one with `display: none`, **mounts every header control twice**: two `EmulatorLauncher`s owning two emulator windows, two `UsagePill`s polling, two `CommandsLauncher`s. A control cannot be in two parents at once, so re-parenting is a JS decision. The CSS then keys off the `.app.mobile` class *that hook sets* rather than repeating the media query, which is what stops the styles from ever disagreeing with the tree they are styling. Only the two rules that answer to the viewport alone (hiding the brand under 430px, `-webkit-text-size-adjust`) are real `@media` blocks.

  **`--tm-tabbar-clear` is the mechanism, and it exists on desktop too.** It is `0px` in `:root` and `calc(var(--tm-tabbar-h) + env(safe-area-inset-bottom))` on `.app.mobile`, so `.main`'s bottom padding and `.term-drawer`'s `bottom` read it **unconditionally** and one token move relocates everything that must sit above the bar. `.app.mobile` setting `--tm-sidebar-w: 0px` was free money: `.term-drawer { left }` and `.cmd-pop { max-width }` were already written against that token and repaired themselves. The mobile type scale is a step down of the same `--tm-text-*` tokens, not a new set.

  **Tables stack instead of scrolling — except the ones that cannot.** Queue, Features and Repos got `.stack-tbl` plus a `data-label` per cell, so a row becomes a block and each cell prints its lost column header. A horizontal scroller was the cheaper answer and the wrong one: the column that goes off-screen is *actions*, which is where Remove, Analyze and Kill live. The Handbook's markdown tables genuinely cannot be re-authored, so those scroll — and `white-space: nowrap` is load-bearing there, because a `display: block` table without it squeezes every column to one character rather than overflowing. Config's ~30 inline `width:` controls are overridden with one `!important` rule instead of editing a page this work does not otherwise touch.

  **LAN access widens two allowlists and nothing else.** "Binds 127.0.0.1 only" is a standing rule, and the reason is `GET /api/session`: it hands the per-boot token — the terminal WS's only credential — to anyone who can reach the port. So LAN mode is `TM_LAN=1` (or `lan.enabled` in `data/config.json`; the env var can only turn it **on**), default off, and when on it changes the bind host and admits *private* hosts and origins only — RFC1918, link-local, loopback, `*.local`. A routable host or origin is refused in both modes, so the DNS-rebinding guard is intact: a hostile page that re-resolves to a LAN address still arrives with its own `Origin` and gets a 403. The token requirement on the WS is untouched.

  **The Vite proxy's `changeOrigin` was not enough, and the comment in `vite.config.ts` now says why.** It rewrites `Host` to the target, which is what makes the dev proxy pass the allowlist today — but it does **not** rewrite `Origin`. A phone's GETs would have worked and every POST and every WS upgrade would have 403'd, which reads as "the app is broken" rather than "the server is not in LAN mode". Both halves take the same flag for that reason.

  **Verified against a real server, not a mock.** Restarting this repo's own server would kill the session doing the work (and the app refuses it while agents are running), so LAN mode was exercised on an isolated copy of `server/` with its own empty database on port 5407: LAN and `*.local` GET/POST pass, foreign `Origin` 403, forged public `Host` 403, and on the events WebSocket a LAN origin stays open while a foreign origin, a missing origin and a bad token each close 4403. The layout was measured over CDP at 360/390/430 CSS px because headless Chromium's `--window-size` floors at 500 and would have reported a phone layout nobody can reach.

- **2026-08-27 — LAN mode listens on `::`, and a missing `web/dist` now says so**: two follow-ups from actually running `npm run start:lan`.

  **`0.0.0.0` is IPv4-only.** `localhost` resolves to `::1` first on macOS, so a browser that does not fall back to IPv4 gets a refused connection on a server that is plainly running — a failure mode that reads as "the flag broke it". LAN mode binds `::` instead, which is dual-stack everywhere IPv6 exists, and falls back to `0.0.0.0` on `EAFNOSUPPORT`/`EADDRNOTAVAIL` rather than assuming. The loopback default is untouched at `127.0.0.1`: changing it is a different decision with a different blast radius, and the pre-existing `localhost` → `::1` → IPv4 fallback has always worked there. Verified on one process: `127.0.0.1`, `localhost`, `[::1]`, the LAN IPv4 and the `.local` name all 200, forged public `Host` and foreign `Origin` still 403.

  **A missing `web/dist` was a silent 404.** `npm start` *serves* the SPA; it has never *built* it. When the directory was absent the server registered no static root and no not-found handler, so `/` fell through to Fastify's default `{"message":"Route GET:/ not found"}` — an apparently dead server with nothing in the log to say why, and the obvious suspect is whatever flag you just added. It now warns on boot and answers any non-`/api`, non-`/ws` path with a 503 carrying the two commands that fix it (`npm run build`, or `npm run dev` and use port 5173). The existence check moved from the directory to `index.html` inside it, because an empty `web/dist` left over from a cleaned build passed the old test.

- **2026-08-27 — The mobile terminal gets an on-screen key row, and the sticky Ctrl lives in the one input path**: a phone soft keyboard has no Esc, no Tab, no Ctrl and no arrows, which is the entire control surface of an interactive `claude` — Esc to interrupt, Tab to accept, arrows for history, Ctrl-C to kill. Typing worked after the mobile pass; steering did not.

  **One channel, not two.** The row does not open a socket or reach for the PTY API. `TerminalDrawer`'s xterm effect now publishes its `send` through a `sendRef` — the same escape-hatch pattern `refitRef` already used — and `term.onData` is wired to *that same function*. Every byte, from the soft keyboard or from the row, goes out as the existing `{type:'input'}` frame through the existing socket. The alternative, a REST route that writes to the session, would have been a second write path into a PTY whose only authenticated channel is deliberately the WebSocket.

  **The sticky Ctrl is applied at the send, which is why it works on keys the row does not have.** Ctrl-C needs a `c`, and the `c` comes from the soft keyboard, not from the row. So the modifier cannot be a property of the buttons: it is a `ctrlRef` read inside `send`, mapping a single character with `c & 0x1f` (covering `@ A-Z [ \ ] ^ _` and `a-z`, with `?` → DEL) and passing everything else — a digit, an escape sequence, a paste — through untouched. A ref, not the state, because reading the state inside the xterm effect would put it in the dependency array and **tear down the WebSocket on every Ctrl tap**; the `useState` copy exists only to paint the armed pip.

  **A modifier clears after exactly one keypress, mapped or not.** Ctrl-then-Tab spends the Ctrl even though nothing maps, because the failure mode of the other rule is a modifier that stays armed invisibly and turns the *next* letter into a control code the user never asked for. It also clears when the drawer compacts, when the viewport leaves mobile and when the run changes — an armed modifier on a terminal you can no longer see would fire into whichever one you open next.

  **`onMouseDown` `preventDefault()` is load-bearing.** Without it the tap moves focus to the button, iOS dismisses the keyboard, and every single keypress costs a re-tap on the terminal. The handler holds focus and then re-focuses xterm explicitly.

  **The row is a sibling above `.term-body`, inside the drawer.** That way it takes its height from the terminal rather than from `--tm-tabbar-clear`, and the drawer's bottom edge is unchanged. Since no window resize fires when it mounts, an effect on `[mobile, compact]` calls the existing refit — verified live: the same drawer, same socket, going 1440 → 390 remounts the row and the PTY moves from 161×19 to 50×22, and back again on the return trip. It is hidden in the compact bar alongside `.term-head`/`.term-body`.

  **Verified against a real PTY, not a mock.** An isolated copy on port 5411 with its own database ran `cat -v` and a python `os.get_terminal_size()` loop as repo commands. Outgoing frames were decoded off the socket: Esc `\x1b`, Tab `\x09`, arrows `\x1b[A/B/D/C`, Ctrl+`c` `\x03`, Ctrl+`a` `\x01`, Ctrl+`D` `\x04` (case-insensitive), Ctrl+`5` `\x35` (unmapped, and the Ctrl still spent). Ctrl-C killed `cat -v` outright. Keys measure 38px at 320/360/390/430 with no page overflow, and `.term-keys` is absent from the DOM entirely at 1440.

- **2026-08-27 — The page and the server stop sharing a lifetime: a front door process, and the restart race it exposed**: `npm start` was one process. Fastify served `web/dist` *and* the API on :5175, so the button that restarts the server was being served by the server it restarts. That is only a problem if the restart can fail — and it could.

  **The restart button really did leave nothing running, and the cause was an ordering bug.** `POST /api/server/restart` spawned the replacement 250ms after replying and exited 400ms after *that*, so for those 400ms two processes wanted :5175 and the child was the one that lost. Whenever the child booted in under 400ms it died on `EADDRINUSE` — `stdio: 'ignore'` swallowed the stack trace, the parent exited on schedule, and the port went quiet. It reproduced first try against an isolated copy with an empty database and no repos to recover; on the real install boot recovery is slow enough that the parent usually wins, which is exactly the shape of bug that survives for months. The fix is to make the handoff ordered rather than hopeful: close Fastify and the storage **first** (capped at 4s — a wedged close must not turn a restart into a permanent stop), then spawn, then exit. `listenOrRetry` then retries `EADDRINUSE` for 8s on boot as belt and braces; every other listen error is still fatal on the first try, because a retry loop that hides a real bind failure is worse than a crash.

  **A reverse proxy, not a second origin.** The obvious split — Vite/static on one port, API on another, talking cross-origin — costs a CORS layer *and* a hole in `isAllowedHost`, which pins the `Host` header's port to the server's own and is the DNS-rebinding guard on a server whose terminal WebSocket is a code-execution surface. Nothing about the SPA needed changing either: it addresses `/api/...` relative and builds WS URLs from `location.host`. So `server/src/host.ts` proxies instead, rewriting **`Host`** so the API's allowlist passes and passing **`Origin`** through so the API still judges it — precisely what Vite's `changeOrigin` already does in dev. Verified end to end through the proxy: a good token on `/ws/events` opens and carries events both ways (a client ping is answered, an orchestrator toggle arrives as two frames), while a bad token, a foreign `Origin` and a missing `Origin` each still close 4403, and a forged `Host` still 403s. `node:http` + `node:net`, no new dependency: this is the process that has to still be running when nothing else is.

  **`TM_SUPERVISED=1` exists because two supervisors racing for one port is the same bug again.** Under the front door the API's restart route no longer detaches a replacement — it exits, and the process watching it respawns. A self-respawn there would be a server the front door does not know about and cannot stop, and the front door's own replacement would then lose the bind. One flag, one branch, and the supervised path is deterministic: stop the child, wait for the port to be **free** rather than for a guess, then spawn.

  **The front door adopts rather than fights.** If something is already listening on :5175 — a `npm run dev:server` in another terminal — it is reported `managed: false` and left alone: proxied to, allowed to restart *itself*, but never respawned and never stopped (`/host/stop` answers 409 and says where to stop it instead). Killing or shadowing another terminal's server would be a genuinely surprising thing for a process whose whole job is to be boring.

  **The guard is not restated, it is forwarded.** `/host/stop` and `/host/restart` `GET /api/server/restart-check` and return the API's own `{blocked, error, running, headless, services}` verbatim, because the alternative — a second copy of the "agents are working" wording living in the supervisor — is how two answers drift apart. An API that is not answering cannot be killing anything, so a down server is never blocked. `{"force": true}` overrides both, same as before.

  **Two failures the UI used to call the same thing.** `offline` meant both "the socket dropped" and "there is no server", and only one of those has an action. The header now reads `stopped` when the front door answers and says the API is not running, swaps Restart for **Start server**, and puts the last exit or spawn error in the tooltip; `/host/status` is polled every 3s only while the socket is down. A page with no front door in front of it gets `host: null` and no new controls, so `npm run dev:web` alone still works. And `state.tsx` now retries `/api/session` until it succeeds — the bootstrap fetched the token exactly once, so a page loaded while the API was down never opened a socket and never recovered without a reload. "Load the page, start the server second" is an ordinary sequence now.

  **In dev the child is `tsx watch`, which means killing a pid is not enough.** The real server is a *grandchild*; signalling the handle we hold leaves an orphan on :5175 and the next spawn loses to it. So the child is spawned `detached` (its own process group) and signalled with `kill(-pid)`, SIGTERM escalating to SIGKILL after 8s — and because detached also means it does not die with us, every exit path stops it explicitly. Verified: a source edit hot-reloads the API without the supervisor counting a restart, and a SIGTERM to the front door leaves zero processes and zero held ports.

  **Verified on an isolated copy, because this repo's own server is the one running the agent.** `server/` copied to a scratch tree with its own empty SQLite DB on 5401/5402: static + SPA fallback + `assets/` immutable caching + `index.html` `no-cache`; four flavours of path traversal (`..`, `%2e%2e`, `..%2f`, and one through `assets/`) all landing on the SPA fallback rather than `/etc/passwd`; `/host/stop` dropping the API while `GET /` still answers 200 and `/api/*` answers a `503 {"apiDown": true}` instead of a dead socket; `/host/start` bringing it back; `kill -9` auto-restarting it; a restart through the proxy cycling the pid, rotating the session token and leaving exactly **one** listener; a stub API forcing the blocked path to 409 on both routes and `force` through it; adoption of an externally started server; `web/dist` removed → 503 with the two commands that fix it, then created → served with no restart, because the check is per request rather than once at boot. LAN mode binds `::` like the API and admits private hosts only; with LAN off the LAN address is refused at the socket and a private `Host` over loopback still 403s. `npm run typecheck` and `npm run build` clean. Not verified against the live install: running the front door over the user's own server needed a permission this session did not have, and it is the one thing that has to be exercised by hand.
