- **2026-08-25 — Feature interface (big request → analysis → adversarial plan review → visual approval)**: new per-repo `tm_features` entity (migration 9) plus `tasks.feature_id`/`feature_phase` and a `feature` source value. - **2026-08-25 — "Proceed": follow-ups continue the agent's own claude session**: a worker whose terminal dies mid-task (usage at 100%, dropped connection, server restart, TTL eviction) used to be recoverable only by starting a fresh agent from the task text plus a summary — throwing away everything it had worked out. A respawn now reuses the previous run's session via `claude --resume <session_id>` (same model/effort/hooks/permission args; the prompt carries ONLY the new instruction, because the session already holds the task, the standing rules and its whole history). `POST /api/tasks/:id/proceed` is the explicit form behind the **Proceed** button and refuses when there is nothing to continue; plain follow-ups do the same continuation by default via `agent.resumeSessions` (on), which also gives the adversarial review→fix loop and *Apply review fixes* their context back. **Run now** deliberately still starts clean.

  Resumability is server-side truth (`GET /api/tasks/:id/resumable`): newest worker run with a `session_id`, same repo (sessions live under their project directory), and the transcript still on disk — a missing transcript degrades to a fresh spawn rather than a `claude --resume` that exits immediately and fails the task (verified: an unknown session id prints "No conversation found" and exits). PTY-injecting text into the idle session was rejected for the reason already in the code: a session sitting at the prompt does not reliably submit injected input.

  Two correctness consequences, both handled. (1) Both runs append to ONE transcript, so a resumed run stores `stats_baseline` — the cumulative totals at resume time — and every stats read subtracts it (`netStats`/`summarizeRun`); without this each proceed would re-bill the entire session in run stats AND in the `run.stats-final` events behind the dashboard. `contextPct` passes through untouched (it is a last-turn measure, not a total). (2) Reusing a session means killing its PTY first, so the kill is now AWAITED (≤5s) — `--resume` on a session another process still holds fails, and `startWorker`'s live-session guard was rejecting its own respawn with "previous session is still live" (a pre-existing race, observed as a 500 on a follow-up to a task with a live idle session). Exit handling gained the matching guard: a run that was deliberately `killed`, or that a NEWER run of the same task has superseded, no longer drives the task's status — whoever killed it already decided.

- **2026-08-25 — Terminal keep-alive is configurable, 0 = forever** (`pty.sessionTtlMinutes`, default 30): the 30-minute idle/exited TTL was hardcoded. Keeping terminals forever is safe because the two evictions are independent — the age GC is what the setting disables, while the `MAX_LIVE_SESSIONS` (10) pressure eviction still reclaims the oldest unwatched session on every spawn, so an infinite TTL cannot wedge the cap. `pty.scrollbackBytes` and the TTL are now re-read from settings every 30s instead of only at boot, so both take effect without a restart. Proceed makes the TTL much less load-bearing anyway: continuing a session reads it from disk, so an evicted terminal is no longer a lost session.

(1) **Age on every row** — relative (`9m`, `5h`, `3d`, `6w`), tooltip naming which timestamp it is plus both absolute times. Drafts show `createdAt` (a draft has never run, so its updated time says nothing), `recent` shows `updatedAt`, everything else shows whatever the current sort orders by, so the column always explains the order it is in. One module-level 30s clock drives every row — dozens of independent intervals ticking the same second was the alternative. Past 14 days the age dims instead. That call was made when the only toggle was "done is hidden"; a *sort order* and a *view mode* that reset on every navigation are worse than one you might forget you set, and the fold state is visible in the header (a folded section still shows its label and count, so nothing is silently missing). Reads are validated and every storage access is wrapped — a corrupt value or blocked storage falls back to defaults instead of blanking the board. - **2026-08-25 — The Board says what each agent is doing right now**: a running row said `running` and nothing else, so the only way to know whether an agent was reading files, waiting, or writing the wrong thing was to open its terminal. Every task row now carries a dimmed mono caption under the title — the live narration line — with a pulsing accent dot.

  **The line comes from the transcript, not the PTY.** Extracting it from the terminal stream was the obvious route and was rejected: the CLI renders through Ink, which repaints its bottom region with cursor moves and erase-line sequences, so "the last line on screen" is only recoverable by emulating a terminal (a headless xterm per session) and every heuristic short of that is a guess against a repainting frame. The transcript already carries exactly the two things the terminal prints — the tool the agent invoked and the text it said — as structured records, which is why `stats.ts` already reads it. `describeTool` renders a `tool_use` the way the terminal narrates it (Bash → the agent's own `description`, falling back to `$ command`; Read/Write/Edit → basename; `Task` → `Subagent · <description>`; `mcp__server__tool` → the tool alone), and the last renderable block of an assistant record wins, so a message that says something and then calls a tool shows the tool — the same order the terminal prints. Sidechain records are skipped: a subagent's turns are not this session's narration, and the parent's `Subagent · …` line already says one is running.

  **It is a live signal, not history — so nothing is persisted.** No column, no migration, no write per tool call. `RunActivity` rides a new `run.activity` `ServerEvent` and lives in an in-memory map; `GET /api/runs/activity` is the snapshot a fresh page or a WS reconnect starts from. `text: null` is the server saying "this run is no longer live", which the client turns into a delete — so a task that lands in `review` drops its line instead of freezing on whatever the agent last did.

  **The watcher pulls the live-run set rather than being pushed at.** Wiring `track`/`stop` into the spawn and Stop paths would have been less code, but the transcript path only exists once the `SessionStart` hook's curl lands, and a hook that fails (or a server restarted mid-run) would leave the Board permanently blank with no way back. Re-reading `listRuns({status:'running'})` every 4s is self-healing, and it is gated on `sessions.liveCount() > 0 || tails.size > 0` so an idle server never issues the query. Tailing is incremental and bounded — first read seeks to the last 512KiB (a resumed run shares the earlier session's entire transcript, and only the newest line matters), truncation resets the offset, an over-large jump re-seeks, and a half-flushed trailing line is carried to the next read; a mid-line seek simply fails to parse and is dropped, which is the correct outcome. Unchanged text emits nothing, so a stalled agent costs zero traffic.


- **2026-08-26 — Task groups: a tree is one nameable, colourable, filterable thing** (`docs/grouping.md`): parent/child links existed but nothing made the *tree* addressable — a child knew its parent and no more, so the Board nested exactly one level (`withChildren` walked roots + direct children) and a split's pieces could not be filtered, named or coloured together. `tm_tasks` now carries `group_id` (root ancestor; a task with no parent is its own group, so the column is never null) and `group_path` (ancestor ids root-first, `/rootId/midId/` — the literal path to the first parent), plus root-row-only `group_name` and `group_color`.

  **Denormalized rather than recursive.** The board wants a whole tree per query and it has to run on both drivers — better-sqlite3 is sync-only, Postgres is a second dialect — so `group_id` answers "the tree" with an indexed equality and the path answers "the ancestors" and "the subtree" (a `LIKE` prefix range) with no join and no CTE. The price is bookkeeping on three write paths, which lives in one file both drivers import verbatim (`storage/group.ts`, same arrangement as `feature-sql.ts`): insert derives the pair from the parent row; a re-parent re-bases the moved node's descendants in one statement and then places the node, in one transaction, refusing a self/descendant parent; a delete promotes orphaned children to roots carrying their own subtrees (so deleting a middle node *splits* a group); and a task that gains a parent drops the group name/colour, since only a root may carry them. The backfill sweeps generation by generation (8 rounds, then "anything left is its own root") instead of `WITH RECURSIVE` — nothing before this migration rejected a 2-cycle, and a recursive CTE over one never terminates.

  **The name lives on the root row, not in a `tm_task_groups` table.** A group has no identity of its own: it is created and destroyed implicitly by parenting, and it always has exactly one row that exists for as long as it does. A side table would need the same create/promote/delete choreography plus its own FK and cleanup to hold two nullable columns. The consequence is stated rather than hidden — deleting a root loses the name, which is correct, because the group it named no longer exists.

  **On the Board.** Rows nest at any depth (indent via `--tm-depth`, children under the deepest ancestor *present in that list*), roots of one group are kept adjacent so a group renders as one bordered block, and the block header says how many of the group's tasks are in *this* section (`2 of 4` when a filter or the drafts cap hides the rest) and filters the board to the group when clicked. A fourth grouping mode, `group: task group`, gives each tree its own section (headers suppressed inside — the section already names it); `recent` stays flat and carries a coloured group chip instead, because it is a lookup list, not a worklist. The task panel shows the ancestor breadcrumb (each crumb opens that task) and, on a root, the name/colour fields.

  **Colour** is seven token slots (`--tm-group-1..7` + `--tm-group-tint`, `-5` hues dark / `-7` light), deliberately excluding teal (the accent — a group must not read as "active") and red (failure). A group's slot is its explicit `group_color`, else one hashed from the group id (FNV-1a), so an untouched group is stably coloured with nothing stored. `board.groupColors` (Config → Board, default on) simply stops setting `--tm-group`; every rule already reads `var(--tm-group, <neutral>)`, so the blocks, names and counts survive with the grey fallback. Grouping is structure; colour is only how it is drawn.

- **2026-08-26 — Repo commands: dev servers and scripts are first-class, and a restart will not kill working agents** (`docs/commands.md`): a registered repo told the app where agents work but gave you no way to run anything there yourself — `pnpm start:dev` lived in another terminal window, and nothing in the app knew whether a dev server was up. `tm_commands` (migration 13) stores a named command line per repo with a `kind` (`task` = one-shot, `service` = long-running), an optional in-repo `cwd` and a launcher order; a scanner reads the repo's `package.json` scripts (root plus `workspaces`/`pnpm-workspace.yaml` packages, `dir/*` only) and offers them in a dropdown, guessing `service` from the script name/body and letting one click correct the guess.

  **Stored as text, spawned as argv.** The command never reaches a shell — it is tokenized and spawned as an args array, the same rule the worker spawn follows, so an *unquoted* `| & ; < > \` $(` is rejected at the API boundary rather than becoming a literal argument that silently does nothing. Quoted operators survive, because `node -e 'a > b'` means a literal `>` to a real shell too. The binary is resolved before spawning — explicit path, then every `node_modules/.bin` up to the repo root, then `PATH` — so a missing `pnpm` is a 400 with a reason instead of a terminal that flashes ENOENT and vanishes, and a repo-local `vite` works with no global install.

  **Runs are in-memory, and get their own PTY pool.** No `tm_runs` row: a PTY dies with the server, so a persisted "running" command could only ever be a lie after a restart — and boot recovery reads that table on the assumption that every row is an agent. `CommandRunner` holds a second `SessionManager` instance, because a dev server alive for hours would otherwise consume the orchestrator's `liveCount()` accounting and the `MAX_LIVE_SESSIONS` cap that agent spawns are checked against. `/ws/terminal/:id` resolves the id against both pools (command ids are `cmd-`-prefixed), so the existing drawer works unchanged. One live run per definition (a second start is a 409, not two dev servers on one port); shutdown and restart kill them deliberately so ports are released; deleting a definition whose run is live *detaches* the run instead of killing it.

  **Restart is refused while agents are working** (user rule): it kills every PTY, and boot recovery then sweeps those tasks to `failed`. `POST /api/server/restart` answers 409 while any non-idle agent session is live, the header button says *Agents working* and is disabled, and `{"force": true}` is the explicit override. Running commands never block it — they are stopped first and the confirm says how many. Testing that path surfaced two bugs that had made the button destructive: the self-restart called `require()` in an ESM module (`require is not defined` — the process exited and never came back), and once fixed it respawned `process.argv`, which under `tsx` is already rewritten to `[node, /abs/index.ts]` — a bare node that dies on the first type annotation. The respawn now carries `process.execArgv` (tsx's loader flags; empty for a plain `node file.js`). `orchestrator.status` is also broadcast on *spawn* now, not only on toggle and exit, so the header's `running n/2` and the new guard reflect reality instead of the last exit.

  **Both kinds of agent count** (review round 1): gating on `sessions.liveCount()` alone saw only interactive PTY workers, so a restart still killed an in-flight analysis, adversarial review or feature plan — headless `claude -p` children that own no PTY, and whose run rows boot recovery then sweeps. `server/src/claude/headless.ts` registers every headless child with a label, keyed by the process rather than a run id (a feature analysis runs several children under one run row, and the reviewer has no run row at all); `OrchestratorStatus.headless` carries the count, the registry notifies on change so the header follows without polling, and a forced restart signals those children on the way out instead of leaving them burning tokens for a server that is gone. The commit-message `claude` in `git.ts` is deliberately excluded: no run row, no agent work destroyed, seconds long.

  **Repos table**, same change: name and path are one stacked cell instead of two columns that squeezed every other cell into wrapping; the row ends in one **Actions** cluster (commands dropdown · Analyze · Remove) rather than three columns drifting apart, the git cell shows the change count without the word "changed", and the table scrolls inside its own panel so a wide row never scrolls the page sideways.

- **2026-08-26 — Task presets: the three per-task knobs get three named answers**: model, effort and adversarial review are independent dropdowns, which is right for the rare case and wrong for the common one — filing a task meant three decisions where the honest input is "this is small" or "this one is hairy". `TASK_PRESETS` (in `shared/`, so the create form and the task panel read the same list) names the three combinations actually in use: Small `opus-5 · medium`, Routine `opus-5 · high`, Complex `fable-5 · high · review` — all three pin review (off / off / on), and the hint says so only when it is *on* (see the 2026-08-26 revision below).

  **A shortcut, not a mode.** The preset writes the three values and then has no further existence: nothing stores which preset was picked, and the highlighted button is *computed* from the current values (`matchTaskPreset`). That is deliberate — a stored `preset` column would be a fourth piece of state able to contradict the three it summarises, and it would have to be migrated, defaulted for 76 existing rows, and kept honest on every write path that touches model/effort/review (the agent API sets `review`, analysis sets `model`). Derived state cannot go stale, and editing a dropdown after clicking a preset simply stops matching, which is exactly the intended meaning.

  **Small deliberately leaves review on the config default** rather than forcing it off. The brief pinned review for Routine (off) and Complex (on) and said nothing for Small; a preset that silently disabled review would be a policy decision hiding inside a convenience, and `review.enabled` is already the place that policy lives. `review: null` is a first-class value in this schema (the dropdown's "default (config)"), not a missing one. *(Revised the same day — see below.)*

- **2026-08-26 — The Dev URL moves into the repo cell**: the Repos table had already collapsed name + path into one stacked cell; the dev URL stayed a column of its own, which meant a text input sitting in the middle of the row, stretching the row height for every repo whether or not it had a URL.
