# Decision log

- **2026-08-25 — Agent task-filing cap is a setting (`agent.taskCreationCap`, default 15)**: the per-run creation cap in the agent API was a hardcoded 5, which cut off honest decomposition work on big tasks. It is now a settings key with a Config row (1–100, validated server-side and re-clamped at read time so a hand-edited `tm_config` row can't disable the guard). `GET /api/agent/context` reports `taskCreationCap`/`tasksCreated`/`tasksRemaining`, and `GET /api/agent/instructions` interpolates the live value into the served sheet (`{{taskCreationCap}}`) so the instructions can never drift from the setting. The global queued-agent ceiling (10) stays hardcoded and independent: it degrades honored enqueues to drafts rather than erroring, so raising the per-run cap widens what an agent may *file*, never what it can auto-start.

- **2026-08-25 — Feature interface (big request → analysis → adversarial plan review → visual approval)**: new per-repo `tm_features` entity (migration 9) plus `tasks.feature_id`/`feature_phase` and a `feature` source value. A user writes a paragraph-to-page request; a headless `claude -p` planning run (analysis model, write tools disallowed, `--json-schema`) decomposes it into ORDERED phases of worker-grade tasks, and a SECOND independent headless run reviews that plan adversarially — the work→review→work loop applied to planning instead of diffs, bounded by the new `feature.analysisMaxRounds` (default 2, mirrors `review.maxRounds`). The plan is shown as horizontal phase columns of editable cards; nothing exists as a task row until the human approves. Approval is one transactional composite per driver (`approveFeature`) that materialises the non-excluded cards as **draft** tasks — approved ≠ started — with the standing caps (max 3 subagents, concurrency stays 2, docs-update exit criterion) injected SERVER-SIDE as a marker-delimited block, never trusted to the plan. Execution is the existing orchestrator: the only change is claim eligibility, one SQL fragment (`storage/feature-sql.ts`) spliced into `claimNextQueuedTask` in BOTH drivers so SQLite and Postgres cannot drift — a feature task is claimable only while its feature is `running` and every lower phase is resolved. Any task failure pauses the feature (no barreling into phase N+1 on a half-done phase N); all phases resolved → feature `review` roll-up → human marks it done. Full design + as-built deltas: `docs/features.md`.

  Judgement calls worth recording: (a) `analysis-review` is not a persisted status — one run row spans plan+review+re-analysis, with each `claude -p` child registered so Kill always reaches the live process; (b) the phase gate has a JS twin (`isFeatureTaskBlocking`) used by the phase pump, and the two are one policy edited together — a mismatch between them wedged a phase during the build and is now covered by the test suite; (c) a worker-filed DRAFT inside a feature does not hold its phase open (it is a human-triage item, not phase work), while queued split children do; (d) the agent-API overflow claim applies only a cancelled-feature gate, because the full phase gate would deadlock a live session the moment a sibling failure paused the feature; (e) `resolveParent` became `resolveCompletion` and now re-evaluates the split parent AND the feature gate, so no call site can forget one; (f) deleting a repo NULLs its features' `repo_id` exactly as it does for tasks, rather than a NOT NULL FK that would make repo deletion fail.

- **2026-08-24 — Restart button + follow-up injection fix**: header shows a server status pill (green up+uptime / amber restarting/offline, driven by the /ws/events connection) + a ⟳ Restart button (POST /api/server/restart spawns a detached copy of the process and exits — self-supervising one hop; warns if workers are running since restart fails them). FIX: followUp/review-fix/apply-review no longer INJECT into a finished (idle) interactive claude prompt — injected text does not reliably submit there, which wedged a task at running with a dead terminal. Idle sessions are now KILLED and the task RESPAWNED with the message+prior-summary in the prompt (reliable). A genuinely mid-turn session rejects follow-ups (wait for review).

- **2026-08-24 — Apply review fixes (backfill)**: `POST /api/tasks/:id/apply-review` + drawer button on review/done/failed tasks. Respawns a worker (via followUp) with the stored review findings to apply, or — if the task was never reviewed — instructs a self-review-and-fix; the result then goes through the normal review-fix loop. Lets old tasks (pre-loop, or reviewed-but-unfixed) be brought up to standard.

- **2026-08-24 — work → review → work loop**: the adversarial review no longer just attaches findings and ends. When it finds blocker/major issues AND the worker session is still live AND the task is still in review (human hasn't taken over), the orchestrator feeds the findings back into the SAME live worker session (via followUp → reactivate idle → running); the worker fixes them, Stops, and is RE-reviewed. Bounded by `review.maxRounds` (default 2) so an unfixable finding can't loop forever; clean/minor-only/cap/human-takeover settles into the human review queue as before. review.ts now returns structured {verdict, findings}. Note: review diffs `git diff HEAD`, so it sees ALL uncommitted changes in the repo, not only this worker's — fine when the worker dominates the diff, noisy on an already-dirty tree.

- **2026-08-24 — Sentry tags + scope diagnosis**: the sourcemap-upload token (sntryu_, org:read only) 403s on issues — sync needs an auth token with project:read + event:read; the error now says so exactly. Import pulls per-issue TAGS (environment/release/transaction/level + custom, best-effort via /issues/:id/tags/) into the task description, and sets the task CATEGORY from a configurable Sentry tag key (sentry.categoryTag; blank = issue level like Error/Warning). Degrades silently if the tags endpoint is unpermitted.

- **2026-08-24 — Per-task review override**: tasks get a nullable `review` field — null = use the global `review.enabled` setting, true = force review, false = skip (for small/trivial tasks). Selector in the create form + drawer ("default / review this / skip"); agents can pass `review:false` on create. Migration 8. `reviewCompletedRun` gates on `task.review ?? settings[review.enabled]`.

- **2026-08-24 — Worker self-review + file I/O**: (1) Every worker change gets an ADVERSARIAL REVIEW pass before landing in review — server-orchestrated headless `claude -p` on the git diff (Fable, falling back to Opus 5 xhigh when Fable is unavailable, cached), structured findings shown in the task drawer. Config `review.enabled` (default on) / `review.model`. server/src/claude/review.ts. Chosen over a worker-spawned subagent because model+effort cannot be pinned reliably from inside a spawned session. (2) Per-task file space (`TM_ARTIFACTS_DIR`) is now BIDIRECTIONAL: users drag-drop uploads (screenshots/data) into the drawer as agent INPUTS, and agents save deliverables there as OUTPUTS — one folder, listed/downloadable/removable in the drawer. @fastify/multipart, 25MB/file. Files deleted with the task.

- **2026-08-24 — Per-repo git buttons**: Repos page has a git status chip (branch, N changed, ↑ahead) plus **Commit** (`git add -A` then commit — message written by `claude-opus-5` from the staged diff via headless `-p`, read-only tools; Co-Authored-By Opus 5 trailer) and **Push** (`git push`, sets upstream on first push). One op per repo at a time; endpoints `/api/repos/:id/{git,commit,push}`, audited as repo.changed. server/src/git.ts.

- **2026-08-24 — Task categories + Board filtering/grouping**: free-text `category` on tasks ("UI", "Estimator", "Auth"…). AGENTS invent and fill them — via `category` on agent-create, `POST /api/agent/tasks/:id/category`, and Analyze runs assign one per task (top-level `categories` in the structured output, applied server-side, never clobbering a human/worker value). - **2026-08-24 — Role model split** (user policy): workers = `claude-opus-5` (heavy implementation), analysis = `claude-fable-5`, orchestrator-tier agents = `claude-fable-5` ("opus does, fable tells and reviews"). Usage-based router kept but default OFF; per-task overrides always win.
- **2026-08-24 — Agent Task API**: workers file follow-ups + coordinate cross-repo via `/api/agent/*` with per-run tokens. Full design + review verdict: `docs/agent-api-design.md`; agent-facing sheet: `docs/agent-instructions.md` (served at `/api/agent/instructions`).

- **2026-08-24 — Real-time UI**: everything flows over `/ws/events` (token-gated). The client refetches `/api/session` before every reconnect (per-boot token rotates on server restart) and calls `refresh()` on every WS open to close missed-event gaps. Live worker runs broadcast `run.updated` with fresh transcript stats every 20s; a `SessionStart` hook reports session/transcript identity at spawn so stats stream from the first tick.

- **2026-08-24 — Stack**: Node 24 + TS + Fastify 5 server, React 19 + Vite SPA, npm-workspaces monorepo. `tsx` in dev AND prod (no server build step); only the SPA is built.
- **2026-08-24 — Storage switch**: file-based (`server/data/config.json`), `sqlite` (better-sqlite3) default, `postgres` (pg) for external sync — Supabase works via its Postgres connection string (free tier: 500MB, pauses after ~1wk idle). - **2026-08-25 — Three usage windows in the header, sourced from the account**: the pill now reports `5h · wk · fable`, mirroring the CLI's `/usage` panel (current session, weekly all-models, weekly cap scoped to Fable). The percentages are the REAL plan figures: the claude CLI caches its last usage fetch in `~/.claude.json` under `cachedUsageUtilization` (`utilization.limits[]`, kinds `session`/`weekly_all`/`weekly_scoped`+`scope.model.display_name`), and `server/src/claude/account-usage.ts` reads it (cached on mtime:size + a 30s TTL). Verified there is NO way to refresh that cache from here — no `claude usage` subcommand, and a `claude -p` probe left `fetchedAtMs` untouched; only an interactive TUI refreshes it. So each window carries its `resetsAt`, a window whose reset has passed is treated as EXPIRED (never shown as a stale percentage — the cached session read 100% nine hours after it reset), and the pill falls back to the local-transcript estimate for it, rendered dimmed with a `~`. Reading the OAuth token out of the Keychain to call the usage endpoint directly was rejected: undocumented and indistinguishable from credential exfiltration.

  The estimate fallback now covers all three windows (trailing 5h / 7d, `fable` filtered on `message.model`), each against a tunable budget (`router.budgetWeekTokens` 20M, `router.budgetWeekFableTokens` 5M alongside the 2M 5h default — same input+output undercounting metric, so retune together). Reading a week of transcripts on every poll is ~180MB, so `usage.ts` caches parsed files by `mtime:size` as minute buckets (≤10080/file), re-filters them against the moving cutoff, evicts vanished/aged-out files, and shares one in-flight scan between the claim loop and the pill — cold 549ms, cached 0ms. Model routing keys on the session window ALONE (`sessionUsagePct`: account figure when live, else the estimate); the weekly pair is reporting only. The pill degrades to the old single-figure render when `/api/usage` lacks the new fields, so a rebuilt SPA can't break against a server that hasn't restarted yet.
