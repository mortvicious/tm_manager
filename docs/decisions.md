- **2026-09-29 — Web Push for the Home Screen PWA, hand-rolled on `node:crypto`, per-device kinds, beside the Telegram bot (`docs/push.md`)**: user request ("allow notifications, push notifications for status updates and all other stuff like questions, etc on mobile PWA").

- **2026-09-29 — Remote access phase 1: the tailnet identity gate lives in the front door, and it rewrites the verified Origin instead of teaching `net.ts` a remote origin (`docs/remote-access.md` § Phase 1, `docs/host.md` § The remote gate)**: the SPA is now usable from the iPhone over `tailscale serve` → front door, and nothing else changed about who can reach the app.

  **Where the gate is.** In `server/src/host.ts`, applying `checkRemote()` from `server/src/remote.ts`, because the front door rewrites `Host` to `127.0.0.1:5175` and after that the API cannot tell a remote request from a local one. A remote request (see the round-1 note below: one that arrived on the remote listener) needs its `Host` to be EXACTLY `remote.hostname`, port-less or `:443`, and never a `.ts.net` suffix match. It also needs `remote.enabled`, a loopback TCP peer, an allowlisted `Tailscale-User-Login`, and an exact `https://<hostname>` Origin on writes and WS. Every `tailscale-*` header is stripped before proxying. `remote` lives in `data/config.json` (not `tm_config`) and refuses to boot together with LAN mode.

  **Round 1 blocker: remote is a LISTENER, not a Host.** The first build called a request remote when its `Host` was the remote name and judged everything else by the local rules. serve forwards the client's `Host` verbatim, so `curl -H 'Host: 127.0.0.1:5176' https://tm-m…/api/session` through serve counted as local and returned the session token, which leads to the terminal WS. Anything reaching serve at the network layer could do it: a tagged node, an ACL mistake, or Funnel. **Fixed with a dedicated loopback listener** `remote.port` (default 5177). It is the only thing serve points at, and every request on it is gated whatever its Host; a non-matching Host is refused. The alternative was to treat any request with serve's `X-Forwarded-*` as remote on the shared port. That keeps one port but hangs the decision on headers a proxy chooses to add. It is kept anyway as a **tripwire** on the main listener: a request there carrying `X-Forwarded-*` or `Tailscale-*` headers gets 403, so serve pointed at 5176 by mistake fails closed instead of reopening the bypass. Re-verified through real serve on both ports, and the iPhone was re-tested.

  **Chosen: rewrite the Origin at the gate.** Rejected: add `https://<remote.hostname>` to `net.ts`'s Origin allowlist. Both keep the DNS-rebinding guard. The rewrite keeps every decision about the remote name in the one place that has just verified the identity AND the exact Origin. The API's Origin checks (index.ts `onRequest`, the WS routes) stay loopback/LAN-only and gain no config. So a direct hit on `127.0.0.1:5175` carrying the remote Origin is still refused, where the `net.ts` option would have accepted it. The cost is that the API cannot see "this came from the phone". Phase 2's remote capability profile will need that, and should get it as a header the gate sets and strips, like the identity headers.

  **Audit through the API, token-guarded.** The front door has no storage, and giving it a second storage driver instance for one row a boot is out of proportion. So it POSTs the first request of each login per boot to `POST /api/host/remote-login` (one `remote.login` row, `actor: 'remote'`, login + user agent). The route takes a secret the front door mints at every boot into `data/host.token` (0600). It is a file, not the child's env, so an adopted API works too. Without a secret, the phone could forge sign-in rows through the very proxy that admitted it. Local processes can read the file, which is the same "loopback already owns everything" line as a forged header on `127.0.0.1:5176`.

  **Verified** on an isolated instance (5199/5198, own DB) behind a temporary `tailscale serve`. From the Mac, the tailnet name and a forged header → 403. Local is unchanged. `remote.enabled: false` → 403. On the iPhone, the SPA, the tasks, the events WS and a live terminal all worked. Wrong-Origin WS upgrades are refused 403. `npm run typecheck` and the web build are clean. Full list in `docs/remote-access.md` § Phase 1.

It was rejected on one fact: **Telegram cannot consume a PTY.** A phone showing escape sequences is not a chat surface, and the phone is half of what this is for — so the PTY version would have meant building the headless version anyway and then owning two mechanisms that both claim to be "the chat", with no safe way to let a live PTY and a `--resume` turn share one session id. One mechanism, two renderers. `envelope.session_id` is the conversation: turn one runs fresh because there is nothing to resume, every turn after carries `--resume`, and the id is kept even from a FAILED turn — claude has already created that session, and dropping it would silently start a second conversation inside one chat.

  **Serial, in SQL.** Two surfaces point at one conversation and two children on one session id is corruption, not a retryable race. `beginChatTurn` is a single conditional `UPDATE … WHERE status IN ('idle','error') RETURNING *`; a chat already `thinking` returns null and the caller refuses 409. A second fence, `chat.concurrency` (default 2), bounds all chats and is deliberately not `orchestrator.concurrency` — a chat owns no task and must never take a worker slot. Everything past the lock must reach `finishChatTurn`, so `completeTurn` wraps its bookkeeping in a try/catch whose only job is releasing the lock when the *recording* fails; a chat left `thinking` refuses every future message. `recoverOnBoot()` clears a lock stranded by a crash and says how many.

  **`spawn`, not `execFile`, and the process group is the reason.** Stopping a turn was verified to *report success and change nothing*: the SIGKILL reached `claude`, but a child it had spawned inherited its stdout, the pipe never reached EOF, the completion callback never fired, and the chat stayed locked for the full timeout. That is not a fixture artifact — a write-mode turn running `npm run build` is exactly it. The child is now spawned `detached` and signalled as `-pid` (SIGTERM, SIGKILL after 5s, matching `SessionManager.kill()`), which also had to become the turn's real timeout, because a timeout that signals the child alone is the kill a live grandchild survives. `execFile` does not forward `detached` to `spawn` at all, which is why this one module differs from `analyze.ts`/`review.ts` and does `maxBuffer` by hand.

  **202 on acceptance, not on the reply.** A turn runs for minutes. `ChatService.send` is two-phase — it resolves once the message is validated, the fence passed, the lock taken and the user message stored, handing back a `done` promise — so every refusal is a real status code and the reply arrives over `/ws/events` as the same `chat.message` frame the phone's turn produces. The first attempt raced the turn against a `setImmediate` to decide when a refusal had stopped being possible; that guess is different on SQLite (sync, microtasks) and Postgres (async I/O), and a route that guesses is a route that is wrong on one driver.

  **Read by default; write from the phone is a config-file decision.** A chat points at a working tree an agent may be mid-task in, so `read` carries the same `--disallowedTools Edit Write NotebookEdit Bash` the analysis and review runs use. `write` is a code-execution surface, and `docs/telegram.md` § What the bot does not do could previously say flatly that the bot reached none. Rather than quietly contradict that, the posture is amended in writing and the switch is `telegram.chat.allowWrite` in `data/config.json` — the file that already holds the bot token, default false, with no way to flip it from the phone. Read-only chats need no opt-in; the web UI can always switch a chat, because the web UI is the laptop that file lives on. The agents' own terminals stay unexposed.

  **Review round 1 corrected three things, two of which the harness structurally could not see.** The fake `claude` recorded argv and printed a canned envelope, which proves what was *asked for* and nothing about what the CLI *does* with it. (1) Write mode was `--permission-mode dontAsk`, and `dontAsk` does not mean "does not need to ask" — it denies anything that would prompt. Against the real CLI a write turn told to create a file replied *"Claude Code is running in 'don't ask mode' … I can't proceed without your explicit approval"* and wrote nothing: a write mode that could not write, shipped with a doc promising the opposite. It is now `--dangerously-skip-permissions`, verified to create the file and run `git status`. No middle setting was added, because `acceptEdits` was measured to run `echo MANGO > file` in `-p` as well — a "safer" option that is not one is worse than no option. (2) `telegram.chat.allowWrite` gated `/mode` but not the send, so a chat switched to write in the browser and left there was reachable from an unlocked handset that never typed `/mode`. The flag is now checked at the send — the only place code executes — and `/chat` will not silently resume a write chat the phone may not use. (3) A turn's child is detached and owns no run row, so a crash left it alive with its pid recorded nowhere; boot recovery then cleared the lock and the next message would have put a second `--resume` on the same session id alongside it, which is the exact corruption the lock exists to prevent. The pid is now on the row (migration 20) and group-killed *before* the lock is cleared. Fixing that exposed a real flaw in the shared `pidLooksLikeOurs`: `ps -o comm=` is a full path on macOS, so matching the whole string meant any binary living under a `claude`-ish directory read as ours — it now matches the basename, which only ever narrows what may be signalled, and the orchestrator's sweep inherits the fix.

  Chat mode on the phone is persisted (`telegram.activeChatId` in `tm_config`, absent from `PUT /api/config` like the other bot-state keys) rather than held in memory beside the flows: a flow that evaporates costs a re-typed title, but a chat mode that evaporated would turn the next message back into an offer to file a task. Buttons take a `c:` namespace parsed before the stateless action codec, for the same reason `w:` and `k:` are — they name a chat either surface can delete, and a stale one must be refused rather than fall through to a codec whose buttons stay valid forever.

- **2026-09-05 — Dispatch intent: `fyi` never wakes a session, and the caps drop to 2/3**: the token audit of 2026-08-31..09-01 (`docs/token-budget.md`) costed what a dispatch actually is. Delivery resumes the target's claude session, and a resume re-writes the WHOLE conversation to cache twice — 395k + 398k tokens on a 400k session, ≈$15 — *before* the agent's first useful token; the reply then Stops into the adversarial reviewer, possibly for another fix round. The two auth tasks `0cb8555a ⇄ a5d9442a` spent 8 dispatches of 4–6.5k chars on status reports and corrections of corrections, and one reply that made **zero code change** cost ~$23 for four minutes. The primitive was right; paying full session-resume price for "FYI, I renamed the field" was not.

  **A dispatch now declares an intent, and that is what decides whether a session may be woken.** `needs_action` (the target must change something) delivers exactly as before, including to a target sitting in `review`. `fyi` (facts, answers, corrections) **never starts a turn**: it stays `pending` and is handed over at the start of the target's next resume for a reason of its own — a review round, Proceed, a `needs_action` dispatch, publish, an unblock — prepended ahead of that turn's dispatch backlog. The field is **required with no default**, deliberately: which one it is can only be judged by the sender, and a default would have made every unthinking caller expensive. `intent` is `tm_dispatches.intent` (migration 18, `NOT NULL DEFAULT 'needs_action'` — the one NOT-NULL form `ALTER ADD COLUMN` accepts in both dialects, and the default that leaves every existing row with the behaviour it was created under).

  **The ride-along lives in `startWorker()`.** The first cut put it in `followUp()`, reasoning that every resume funnels through there — and review round 1 caught the hole (major): `startWorker` is ALSO called directly by the claim loop, `pumpCustomQueue()` and `runNow()`, none of which pass a follow-up. So Enqueue, Retry, Run now and a custom-queue claim would each start a fresh session that never saw the pending `fyi`, do the work without it, land in `review`, and leave the message to surface on some later Proceed — after the work it should have informed; if the task went `done` instead, the next tick would quietly convert it to a note nobody read. The served instruction sheet promises delivery "at the start of the next turn it takes anyway", and only `startWorker` sees every turn. `pendingFyiDispatches(taskId)` now returns the prompt block plus the settle that goes with it, and `startWorker` is the one caller. The delivery loop separately skips any target whose pending dispatches are all `fyi`, which is the actual saving.

  Four details a reviewer should check, each of which was a bug avoided: the backlog is read before the spawn but settled only **after** it succeeds (a worker that never started showed the agent nothing, so the messages stay pending for the next attempt); that settle carries its **own** `try`/`catch`, because bookkeeping must never fail a worker that is already running; the block travels as its own `dispatchNote` argument and is **never concatenated onto `followUp`**, since the publish turn is recognised by `followUp === PUBLISH_INSTRUCTION` by strict identity and appending would have silently demoted every publish turn to an ordinary one; and it is placed **first** in the prompt, never last, because the last thing a resumed agent reads has to stay the instruction it must act on. `buildDispatchNote` words the block as context rather than instruction — an `fyi` that provokes work is exactly the wake-up this split removes.

  **An `fyi` to a task that has finished for good is a note, not a run.** `done`/`published`/`cancelled` settle it `delivered` with the reason and a `task.dispatch` event, before the hold checks, since writing a note needs no agent, no repo lock and no concurrency slot. **`failed` is deliberately excluded** even though it is in `TERMINAL_TASK_STATUSES` — that is why `DISPATCH_TERMINAL_STATUSES` is its own constant: a failed task is the one terminal-looking status a human routinely retries, and the `fyi` should still be waiting when they do.

  **Caps: 5 → 2 per run, 8 → 3 per task pair (both directions).** Both intents count against both — an `fyi` is cheaper, not free, and the ping-pong guard has to bound the conversation rather than just its expensive half. Three exchanges is enough to hand over a contract; past that the pair is arguing and a human should be looking. The numbers are now substituted into the served instruction sheet (`{{dispatchRunCap}}` / `{{dispatchPairCap}}`, the trick `{{taskCreationCap}}` already used) so the doc cannot drift from the constants the way the old hardcoded "5 per session, 8 lifetime" line did.

- **2026-09-03 — Review each diff once; `review.maxRounds` default 1**: the second token audit (2026-08-31..09-01) found 36 adversarial reviews for 17 tasks in two days — ≈$275 of headless `claude -p`, each returning 5–9 findings of which 1–2 were actionable, and each actionable round resuming a 300–500k-token session (≈$15 of warm-up before the first useful token). The cause was structural, not prompt quality: `reviewWorkerChange` diffs `git diff HEAD`, which carries EVERY uncommitted change in the repo, so a Stop that changed nothing — a dispatch reply, an answered question, a follow-up that only talked — still presented a fat non-empty diff and paid for a full run that re-judged work already judged. The fix is identity, not heuristics: `workerDiff(repo)` returns the diff plus its **sha256, hashed before the 60k prompt truncation** (two changes identical in their first 60k must still compare unequal), and the hash is stored on the task (`tm_tasks.review_diff_hash`, migration 17, both drivers). An unchanged hash means there is nothing new to judge, so the previous verdict stands, the task simply stays in `review`, and no process is spawned. Default `review.maxRounds` went 2 → **1** (still 0–5 in Config; `feature.analysisMaxRounds` is a separate plan-review budget and stays at 2).

  Judgement calls worth recording: (a) **no dispatch special-case** — requirement 3 ("don't review a dispatch-reply turn") is not a branch anywhere; the hash IS the test, which covers dispatch replies, answered questions, human follow-ups and publish re-entries with one rule instead of four, and cannot drift as new resume paths are added. (b) **The skip is audited, not silent**: both `{ skipped: 'unchanged-diff' }` and `{ skipped: 'empty-diff' }` are written as `run.reviewed` rows, so "no review ran" is a decision in the log rather than a gap — the empty-diff case previously returned with no trace at all. (c) The hash is written in the SAME `updateTask` as `reviewSummary`, so a stored hash always has the verdict it belongs to; a review that fails to parse still stamps its hash, because "the reviewer choked on this diff" is not a reason to choke on it again next Stop. (d) The diff is produced ONCE per Stop and handed to the reviewer as a parameter — the old code would otherwise run `git add -N` twice on the same tree. (e) A skip settles the fix loop (`reviewRounds` cleared) exactly as a clean verdict does, so a no-op turn can never burn a round. (f) A skipped round emits no verdict event, so the Telegram review ping arrives bare rather than re-showing the previous badge — that fallback was deliberately removed earlier (a stale "✓ clean" next to live Publish buttons invites shipping on it), and this change does not reintroduce it. (g) The Telegram report excludes skips from "review rounds" and counts them on their own line; `verdictFor` looks PAST a verdict-less row instead of falling through to markdown badge-parsing. (h) Prompt text, model selection and the Fable→Opus xhigh fallback are untouched — the win here is not running the reviewer, not running it differently.

  **Adversarial review round 1 found one major, fixed here: the gate was not single-flight.** A round takes minutes and stamps the hash only when it returns, so a second Stop landing in that window read a null hash and spawned a second reviewer over a byte-identical diff — and the likeliest way to produce one is the exact case this change targets, because `deliverDispatches` holds a target that is `running`/`queued`/`blocked` but not one sitting in `review`: a pending dispatch resumes the task seconds after its Stop, the agent answers without editing, and that Stop races the round already running. `pendingReviews` is now a map of in-flight promises; an overlapping caller is handed the RUNNING round's promise rather than a resolved one, because the stop-hook route releases its custom-queue hold in a `.finally` on the return value and that hold has to outlive the real round. The late Stop is remembered (`reviewRecheck`), not dropped — its turn may have edited something — so one more pass runs when the round settles: free when the hash is unchanged, a real review when it is not, and skipped entirely if a fix round has already moved the task back to `running`. The same review flagged a possible stale-column clobber from two concurrent `updateTask` calls; that one does not hold and is recorded so it is not "fixed" again — both drivers re-`SELECT` the row inside the same transaction and merge only the defined patch keys (`sqlite.ts#updateTaskSync`, `postgres.ts#updateTaskWith`), so no caller ever writes a snapshot it read minutes earlier.

  **Verified**: `npm run typecheck` clean. Driver-level round-trip (real SQLite, 15 assertions): migration 17 applies and is recorded, a new task's hash is null, `updateTask` persists it, an unrelated patch does not clobber it, and the list mapper carries it. - **2026-08-25 — The Board says what each agent is doing right now**: a running row said `running` and nothing else, so the only way to know whether an agent was reading files, waiting, or writing the wrong thing was to open its terminal. Every task row now carries a dimmed mono caption under the title — the live narration line — with a pulsing accent dot.

  **The line comes from the transcript, not the PTY.** Extracting it from the terminal stream was the obvious route and was rejected: the CLI renders through Ink, which repaints its bottom region with cursor moves and erase-line sequences, so "the last line on screen" is only recoverable by emulating a terminal (a headless xterm per session) and every heuristic short of that is a guess against a repainting frame. The transcript already carries exactly the two things the terminal prints — the tool the agent invoked and the text it said — as structured records, which is why `stats.ts` already reads it. `describeTool` renders a `tool_use` the way the terminal narrates it (Bash → the agent's own `description`, falling back to `$ command`; Read/Write/Edit → basename; `Task` → `Subagent · <description>`; `mcp__server__tool` → the tool alone), and the last renderable block of an assistant record wins, so a message that says something and then calls a tool shows the tool — the same order the terminal prints. Sidechain records are skipped: a subagent's turns are not this session's narration, and the parent's `Subagent · …` line already says one is running.

  **It is a live signal, not history — so nothing is persisted.** No column, no migration, no write per tool call. `RunActivity` rides a new `run.activity` `ServerEvent` and lives in an in-memory map; `GET /api/runs/activity` is the snapshot a fresh page or a WS reconnect starts from. `text: null` is the server saying "this run is no longer live", which the client turns into a delete — so a task that lands in `review` drops its line instead of freezing on whatever the agent last did.

  **The watcher pulls the live-run set rather than being pushed at.** Wiring `track`/`stop` into the spawn and Stop paths would have been less code, but the transcript path only exists once the `SessionStart` hook's curl lands, and a hook that fails (or a server restarted mid-run) would leave the Board permanently blank with no way back. Re-reading `listRuns({status:'running'})` every 4s is self-healing, and it is gated on `sessions.liveCount() > 0 || tails.size > 0` so an idle server never issues the query. Tailing is incremental and bounded — first read seeks to the last 512KiB (a resumed run shares the earlier session's entire transcript, and only the newest line matters), truncation resets the offset, an over-large jump re-seeks, and a half-flushed trailing line is carried to the next read; a mid-line seek simply fails to parse and is dropped, which is the correct outcome. Unchanged text emits nothing, so a stalled agent costs zero traffic.


- **2026-08-26 — Task groups: a tree is one nameable, colourable, filterable thing** (`docs/grouping.md`): parent/child links existed but nothing made the *tree* addressable — a child knew its parent and no more, so the Board nested exactly one level (`withChildren` walked roots + direct children) and a split's pieces could not be filtered, named or coloured together. `tm_tasks` now carries `group_id` (root ancestor; a task with no parent is its own group, so the column is never null) and `group_path` (ancestor ids root-first, `/rootId/midId/` — the literal path to the first parent), plus root-row-only `group_name` and `group_color`.

  **Denormalized rather than recursive.** The board wants a whole tree per query and it has to run on both drivers — better-sqlite3 is sync-only, Postgres is a second dialect — so `group_id` answers "the tree" with an indexed equality and the path answers "the ancestors" and "the subtree" (a `LIKE` prefix range) with no join and no CTE. The price is bookkeeping on three write paths, which lives in one file both drivers import verbatim (`storage/group.ts`, same arrangement as `feature-sql.ts`): insert derives the pair from the parent row; a re-parent re-bases the moved node's descendants in one statement and then places the node, in one transaction, refusing a self/descendant parent; a delete promotes orphaned children to roots carrying their own subtrees (so deleting a middle node *splits* a group); and a task that gains a parent drops the group name/colour, since only a root may carry them. The backfill sweeps generation by generation (8 rounds, then "anything left is its own root") instead of `WITH RECURSIVE` — nothing before this migration rejected a 2-cycle, and a recursive CTE over one never terminates.

  **The name lives on the root row, not in a `tm_task_groups` table.** A group has no identity of its own: it is created and destroyed implicitly by parenting, and it always has exactly one row that exists for as long as it does. A side table would need the same create/promote/delete choreography plus its own FK and cleanup to hold two nullable columns. The consequence is stated rather than hidden — deleting a root loses the name, which is correct, because the group it named no longer exists.

  **On the Board.** Rows nest at any depth (indent via `--tm-depth`, children under the deepest ancestor *present in that list*), roots of one group are kept adjacent so a group renders as one bordered block, and the block header says how many of the group's tasks are in *this* section (`2 of 4` when a filter or the drafts cap hides the rest) and filters the board to the group when clicked. A fourth grouping mode, `group: task group`, gives each tree its own section (headers suppressed inside — the section already names it); `recent` stays flat and carries a coloured group chip instead, because it is a lookup list, not a worklist. The task panel shows the ancestor breadcrumb (each crumb opens that task) and, on a root, the name/colour fields.

  **Colour** is seven token slots (`--tm-group-1..7` + `--tm-group-tint`, `-5` hues dark / `-7` light), deliberately excluding teal (the accent — a group must not read as "active") and red (failure). A group's slot is its explicit `group_color`, else one hashed from the group id (FNV-1a), so an untouched group is stably coloured with nothing stored. `board.groupColors` (Config → Board, default on) simply stops setting `--tm-group`; every rule already reads `var(--tm-group, <neutral>)`, so the blocks, names and counts survive with the grey fallback. Grouping is structure; colour is only how it is drawn.

- **2026-08-26 — Repo commands: dev servers and scripts are first-class, and a restart will not kill working agents** (`docs/commands.md`): a registered repo told the app where agents work but gave you no way to run anything there yourself — `pnpm start:dev` lived in another terminal window, and nothing in the app knew whether a dev server was up. `tm_commands` (migration 13) stores a named command line per repo with a `kind` (`task` = one-shot, `service` = long-running), an optional in-repo `cwd` and a launcher order; a scanner reads the repo's `package.json` scripts (root plus `workspaces`/`pnpm-workspace.yaml` packages, `dir/*` only) and offers them in a dropdown, guessing `service` from the script name/body and letting one click correct the guess.

  **Stored as text, spawned as argv.** The command never reaches a shell — it is tokenized and spawned as an args array, the same rule the worker spawn follows, so an *unquoted* `| & ; < > \` $(` is rejected at the API boundary rather than becoming a literal argument that silently does nothing. Quoted operators survive, because `node -e 'a > b'` means a literal `>` to a real shell too. The binary is resolved before spawning — explicit path, then every `node_modules/.bin` up to the repo root, then `PATH` — so a missing `pnpm` is a 400 with a reason instead of a terminal that flashes ENOENT and vanishes, and a repo-local `vite` works with no global install.

  **Runs are in-memory, and get their own PTY pool.** No `tm_runs` row: a PTY dies with the server, so a persisted "running" command could only ever be a lie after a restart — and boot recovery reads that table on the assumption that every row is an agent. `CommandRunner` holds a second `SessionManager` instance, because a dev server alive for hours would otherwise consume the orchestrator's `liveCount()` accounting and the `MAX_LIVE_SESSIONS` cap that agent spawns are checked against. `/ws/terminal/:id` resolves the id against both pools (command ids are `cmd-`-prefixed), so the existing drawer works unchanged. One live run per definition (a second start is a 409, not two dev servers on one port); shutdown and restart kill them deliberately so ports are released; deleting a definition whose run is live *detaches* the run instead of killing it.

  **Restart is refused while agents are working** (user rule): it kills every PTY, and boot recovery then sweeps those tasks to `failed`. `POST /api/server/restart` answers 409 while any non-idle agent session is live, the header button says *Agents working* and is disabled, and `{"force": true}` is the explicit override. Running commands never block it — they are stopped first and the confirm says how many. Testing that path surfaced two bugs that had made the button destructive: the self-restart called `require()` in an ESM module (`require is not defined` — the process exited and never came back), and once fixed it respawned `process.argv`, which under `tsx` is already rewritten to `[node, /abs/index.ts]` — a bare node that dies on the first type annotation.   **Both kinds of agent count** (review round 1): gating on `sessions.liveCount()` alone saw only interactive PTY workers, so a restart still killed an in-flight analysis, adversarial review or feature plan — headless `claude -p` children that own no PTY, and whose run rows boot recovery then sweeps. `server/src/claude/headless.ts` registers every headless child with a label, keyed by the process rather than a run id (a feature analysis runs several children under one run row, and the reviewer has no run row at all); `OrchestratorStatus.headless` carries the count, the registry notifies on change so the header follows without polling, and a forced restart signals those children on the way out instead of leaving them burning tokens for a server that is gone. - **2026-08-27 — Publish ships the work from the agent's own terminal, and git has the last word**: a finished task's code sat uncommitted in the repo; **Mark done** moved a row in the database and nothing else, so "done" and "shipped" were quietly different things. **Publish** (offered on a task in `review`, from the panel and the board row) closes that gap and gives it a status of its own — `published`, terminal alongside `done`, in blue rather than green because *shipped* and *accepted* are different claims.

- **2026-08-27 — The page and the server stop sharing a lifetime: a front door process, and the restart race it exposed**: `npm start` was one process. Fastify served `web/dist` *and* the API on :5175, so the button that restarts the server was being served by the server it restarts. That is only a problem if the restart can fail — and it could.

  **The restart button really did leave nothing running, and the cause was an ordering bug.** `POST /api/server/restart` spawned the replacement 250ms after replying and exited 400ms after *that*, so for those 400ms two processes wanted :5175 and the child was the one that lost. Whenever the child booted in under 400ms it died on `EADDRINUSE` — `stdio: 'ignore'` swallowed the stack trace, the parent exited on schedule, and the port went quiet. It reproduced first try against an isolated copy with an empty database and no repos to recover; on the real install boot recovery is slow enough that the parent usually wins, which is exactly the shape of bug that survives for months. The fix is to make the handoff ordered rather than hopeful: close Fastify and the storage **first** (capped at 4s — a wedged close must not turn a restart into a permanent stop), then spawn, then exit. `listenOrRetry` then retries `EADDRINUSE` for 8s on boot as belt and braces; every other listen error is still fatal on the first try, because a retry loop that hides a real bind failure is worse than a crash.

  **A reverse proxy, not a second origin.** The obvious split — Vite/static on one port, API on another, talking cross-origin — costs a CORS layer *and* a hole in `isAllowedHost`, which pins the `Host` header's port to the server's own and is the DNS-rebinding guard on a server whose terminal WebSocket is a code-execution surface. Nothing about the SPA needed changing either: it addresses `/api/...` relative and builds WS URLs from `location.host`. So `server/src/host.ts` proxies instead, rewriting **`Host`** so the API's allowlist passes and passing **`Origin`** through so the API still judges it — precisely what Vite's `changeOrigin` already does in dev. Verified end to end through the proxy: a good token on `/ws/events` opens and carries events both ways (a client ping is answered, an orchestrator toggle arrives as two frames), while a bad token, a foreign `Origin` and a missing `Origin` each still close 4403, and a forged `Host` still 403s. `node:http` + `node:net`, no new dependency: this is the process that has to still be running when nothing else is.

  **`TM_SUPERVISED=1` exists because two supervisors racing for one port is the same bug again.** Under the front door the API's restart route no longer detaches a replacement — it exits, and the process watching it respawns. A self-respawn there would be a server the front door does not know about and cannot stop, and the front door's own replacement would then lose the bind. One flag, one branch, and the supervised path is deterministic: stop the child, wait for the port to be **free** rather than for a guess, then spawn.

  **The front door adopts rather than fights.** If something is already listening on :5175 — a `npm run dev:server` in another terminal — it is reported `managed: false` and left alone: proxied to, allowed to restart *itself*, but never respawned and never stopped (`/host/stop` answers 409 and says where to stop it instead). Killing or shadowing another terminal's server would be a genuinely surprising thing for a process whose whole job is to be boring.

  **The guard is not restated, it is forwarded.** `/host/stop` and `/host/restart` `GET /api/server/restart-check` and return the API's own `{blocked, error, running, headless, services}` verbatim, because the alternative — a second copy of the "agents are working" wording living in the supervisor — is how two answers drift apart. An API that is not answering cannot be killing anything, so a down server is never blocked. `{"force": true}` overrides both, same as before.

The header now reads `stopped` when the front door answers and says the API is not running, swaps Restart for **Start server**, and puts the last exit or spawn error in the tooltip; `/host/status` is polled every 3s only while the socket is down. A page with no front door in front of it gets `host: null` and no new controls, so `npm run dev:web` alone still works. And `state.tsx` now retries `/api/session` until it succeeds — the bootstrap fetched the token exactly once, so a page loaded while the API was down never opened a socket and never recovered without a reload. "Load the page, start the server second" is an ordinary sequence now.

Verified: a source edit hot-reloads the API without the supervisor counting a restart, and a SIGTERM to the front door leaves zero processes and zero held ports.

  **A last-seen-status memory, primed from storage at start.** A broadcast says "this task changed", not "this task changed status"; without priming, the first event about a pre-existing task — a title edit on something sitting in `review` since before boot — reads as a transition and pings the phone about old news. Same-status broadcasts are content edits and stay silent. Proposals need the inverse guard: accept/reject re-broadcast `proposal.created` as an upsert, so only `pending` is news and each id is announced once.

  **Buttons and the task-3 commands share `actions.ts`, and the codec lives beside the dispatch table.** Each action (complete/publish/proceed/accept/reject/approve-and-start) is ONE function mirroring what the REST route does — transition, broadcasts, follow-on scheduling — with `actor: 'telegram'`. The `callback_data` wire form (`t:done:<id>` etc., Telegram caps it at 64 bytes) is encoded and parsed in the same file so a button cannot exist without its action. Approve-and-start is deliberately one tap: the design doc's phone flow is "approve = POST approve + start", because the visual plan check already happened when the analysis report was read.

  **A callback query is stale in the boot drain and fresh in the poll loop.** It carries no timestamp of its own, and the message it hangs off can be days old — a button on an old notification pressed just now is a live intent, while a press from before a restart must not fire an action on boot (the same rule as typed commands). Task 1's `updateTimestamp()` already refused to date them; the poll loop now exempts them from the staleness check instead of dropping every button press as stale — which is also the bug that made `allowed_updates: ['message']` insufficient: without `callback_query` in that list the buttons could never arrive at all.

  **The button gate is the message gate.** Presser id must be the allowlisted one; when the carrying message survived Telegram's 48h retention its chat must additionally be the owner's private chat; everything else is dropped in silence and counted like any other unauthorized update — no `answerCallbackQuery`, because settling the spinner confirms the bot is alive. Presses are audited (`command: 'button:<kind>'`) BEFORE the toast and the confirmation message, same as commands.

  **`telegram.notify.*` lives in `data/config.json`, and the toggles rewrite only that subtree.** The class switches belong with the bot's config block, and `tm_config` is dumped by `GET /api/config`. `/mute` `/unmute` `/notify` mutate the live object (the notifier reads it at flush time, so a mute lands immediately) and persist by re-reading the file and patching `telegram.notify` alone — serialising the in-memory `BootConfig` back would clobber any hand-edit made since boot, and the one thing this file must never lose to a convenience write is the token. A failed write is reported in the reply and the toggle still holds until restart. The boot "back online" message became the `boot` class of the same system.

  **Queue-drained is a debounced storage check, not an event.** No component knows "the queue just emptied"; the notifier arms itself when it sees queued/running work, and any settling event schedules a 5s re-count of `queued` + `running` rows. Fires once per drain (the armed flag settles even while muted, or unmuting would replay old news). Usage is the one poll in the module — a 60s `usageSnapshot()` tick comparing consecutive snapshots for threshold crossings (50/80/95) and a known `resetsAt` passing; thresholds re-arm automatically because the comparison is against the previous snapshot, not a high-water mark.

  **Review round 2** found two majors in the review-entry ping, both fixed. The fix is ground truth, not prediction: the orchestrator now tracks in-flight rounds in a `pendingReviews` set (added synchronously when `reviewCompletedRun` is fired, cleared in its `finally`) behind `isReviewPending()`, and the notifier defers the entry ping while one is pending — retried each minute, capped at 30, so a round that produces no verdict event still yields a late ping rather than none; the verdict itself prompt-flushes the parked record on arrival. The stale-badge fallback was deleted outright. The review flush now shows `task.error` (and suppresses the redundant old `resultSummary` when it does).

- **2026-09-02 — Telegram red button: destructive commands are nonce-gated, rate-limited and answered twice (`docs/telegram.md` § Emergency controls)**: task 4 of the bot group. `/killall` (stop the queue → cancel pending dispatches → pause running features → cancel queued → kill every live run → stop the headless children), `/off` as the soft stop, `/restart` through the front door. New module `server/src/telegram/emergency.ts`; the confirm state and the rate limiter hang off `TelegramBot`, the execution branch lives in `bot.ts` next to the other callback branches.

  **A confirm window is consumed, and that one property is the whole safety argument.** The reviewer's two questions were "can a stale or duplicated update fire a kill twice" and "what happens if the server restarts mid-confirm", and both are answered by `take()` removing the window rather than reading it. Telegram redelivers an update whose offset was not advanced, and a double-tap can arrive as two `callback_query` updates; the second visit finds an empty store. A restart is the same shape from the other side — the store is in memory, so it dies with the process, and the boot drain independently treats a `callback_query` as undatable and therefore stale, so a press from before a restart is discarded rather than replayed. The harness drives all three: a replayed press, the identical update twice in one batch, and a pre-restart nonce against a freshly constructed bot.

  **The nonce is the only thing on the wire; the window's KIND is held server-side.** A captured `k:go:<nonce>` therefore cannot be re-pointed at a different action, and a nonce armed for `/killall` cannot fire a `/restart`. The `k:` namespace is parsed *before* the stateless action codec for the same reason `w:` is — these expire, and an expired button must be refused rather than fall through to something still valid a week later. The action codec parses by lookup in a wire map that has no `k:` entry, so the three codecs cannot collide; there is now a comment on that map saying the namespace is taken.

  **Rate-limited at ARM, recorded at EXECUTE.** Two fences: 60s between two executions of the same destructive command (the human-retry fence — on a red button, "did that work?" is exactly the press that kills the session the first one spawned in its place) and 5 destructive executions per 10 minutes across all of them. Checking at the press instead would mean the owner read a list of what was about to die, tapped Confirm, and got a cooldown notice — the worst possible moment to be told no. A `/killall` on an already-quiet machine answers `Nothing to stop` and arms nothing, so it spends neither the one window nor the cooldown; Cancel likewise costs nothing, because it destroyed nothing. The counters stay in memory: persisting them would mean the first `/killall` after a crash is the one that gets refused.

Then every live run of EVERY mode, not just `worker` like `POST /api/orchestrator/stop-and-kill`: the phone's `/kill` listing already shows every mode, and a red button that leaves an analysis burning tokens is a half-button. - **2026-09-06 — A turn stopped by the usage window is a schedule, not a status: `wake_at` + one 30s sweep (`docs/wake.md`)**: when the 5h window runs out mid-turn the CLI prints a banner and the turn stops.   **What changed.** The runner now keeps the StopFailure `error` code on the outcome (`AuxOutcome.code`). `modelUnavailable` is `status === 'failed'` plus a code in `{model_not_found}`, which is the code the CLI emits for a bogus `--model` (measured on 2.1.280). The code is the CLI's own classification, so free text is never classified. A `timeout` or `aborted` outcome never falls back. The three copies (review, feature analysis, reports) became one helper, `withModelFallback` in `claude/aux.ts`. It has one process-wide Fable cache that is set only when a Fable request fails. The feature and report copies used to set it on any model's failure, despite the 2026-09-10 entry saying they already used the `/fable/i` guard.

  **The reason is kept.** The round's error used to be the first 200 characters of the argv echo (task b8c1d9d0, 2026-09-10: `Command failed: claude -p --model claude-opus-5 --effort xhigh --permission-mode dontAsk --disallowedTools … --json-schema {"type":"object","properties"`). Now it is the runner's reason, cut at 500 characters. A session that ends without a hook naming the cause (SessionEnd, or process exit) appends the exit code or signal and `readableTail` of the PTY: ANSI stripped, cursor-forward read as a space, the `Resume this session with:` epilogue dropped, at most 300 characters. That text is the CLI's stderr, which reaches no hook. A timeout reads `timed out after 10 min`, and a deadline under a minute is written in seconds instead of rounding to "0 min".

  **Verified** against the real CLI (2.1.280) with a throwaway harness: an in-memory run store, a real aux `SessionManager`, hook routes forwarding to `aux().hook`, and `reviewWorkerChange` called directly. The review timeout was lowered to 6 s through a temporary constant, since removed.
  - A Fable reviewer that hit the 6 s deadline recorded `model claude-fable-5-1 — timed out after 6 s` and spawned exactly one session.
  - A nonexistent reviewer model hit `model_not_found`, and the round ran on `claude-opus-5-5` (two sessions, the fallback is still intact). The model was not Fable, so the cache was not set.
  - The next Fable review ran on `claude-fable-5-1`.
  - A bad `--resume` recorded `session ended without a result — terminal: No conversation found with session ID: …`.
  - The classifier returned false for `server_error` "Service Unavailable … model", `rate_limit … model`, a `timeout`, and an argv-echo string.

  An unknown `--effort` could not be used to force a failure: the CLI warns and ignores it. `npm run typecheck` is clean.

- **2026-09-24 — Gate the ship on the review: a prompt rule, not a push-blocking hook (`docs/design.md` § Adversarial review, *Review before ship*)**: the review round runs at the worker's Stop. In repos whose CLAUDE.md makes the worker push to `origin/main`, deploy and verify live, the reviewer's blocker was already in production, and the fix round shipped a second commit after the fact.

  **Chosen: a standing rule injected server-side (option 1).** When `shipHeldForReview(task, settings)` holds (`!autoPublish && (task.review ?? review.enabled)`, the same test the Stop hook uses for `reviewState: 'pending'`), every worker turn except the publish turn ends with `SHIP_GATE_RULE`. The rule overrides the repo's CLAUDE.md: no push, no deploy, no production check; leave the change uncommitted if possible; commit locally only where the repo insists. `PUBLISH_INSTRUCTION` gained step 5, which runs the repo's post-push deploy/verify steps only after a successful push. `verifyPublished()` stays the git-side judge.

  **Rejected: a `PreToolUse` Bash hook that long-polls `git push`/deploy until the review passes (option 2).** It is mechanically stronger, but "is this a deploy?" is a regex over arbitrary shell (`vercel`, `aws ecs update-service`, `npm run deploy`, a script that pushes). It would hold a live PTY in a tool call across the very review that needs the worker's Stop to start, so it deadlocks unless the hook denies instead of waits. It would also need a per-turn exemption for the publish turn. Every other worker constraint is a prompt rule. The failure mode of the chosen option is visible and bounded: an agent that ignores it pushes, which is exactly today's behaviour.

  **Unchanged on purpose.** Review-off tasks (Small/Routine presets, `review: false`) get no rule. Auto-publish still skips review, so it gets no rule and keeps the repo's own pushing. Publish is gated on status `review` only, so the human can still ship past a `flagged` verdict.

  **Ordering caveat.** This was meant to follow "Reviewer: review the task's own change, including work the worker already committed", but that task was still a draft when this landed. At the time the reviewer read `git diff HEAD`, so the rule said to leave the change uncommitted rather than just "commit if you want". A worker that commits locally anyway gets an `empty-diff` skip, but it is still not pushed and still waits for the human's Publish. (Superseded 2026-09-24 by "The reviewer reads the task's commits": the rule now allows local commits.)

  **Verified** with `npm run typecheck`, and with a script over `buildWorkerInvocation` that checks the rule is present or absent in 8 cases: fresh with global review on or off, a per-task override each way, auto-publish, a resumed fix round, a resumed publish turn (absent), and a fresh follow-up. The live check in `3 - neko-nest` (a review-on task ends in `review` with unpushed commits, the verdict is recorded, then Publish pushes) needs a server restart onto this code and a real publish to a deploying repo, so it is left for the operator.
