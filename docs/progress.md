### Follow-up: ✓ means "mark done" in review, and the live-session guard is visible (2026-08-25)

- User report: clicking ✓ on a task in **review** answered "previous session is still live — open its terminal or kill it first". Two problems behind one click: (a) after a worker's Stop hook the task sits in `review` with its PTY still attachable, so `enqueue` hits the server's `hasLiveSession()` guard — a 409 by design; (b) on a task in review the check should mean what the slide-over's primary button means there, **Mark done**, not "queue it again".
- ✓ is now status-aware: `review` → `POST /tasks/:id/complete` (tooltip "Mark done", `.quick.affirm` tints it `--tm-status-done` on hover — complete also closes the task's idle sessions server-side); every other status keeps `enqueue` ("Mark as ready"). `CAN_READY` drops `review` accordingly.
- ▶ and the enqueue variant of ✓ now also mirror the server's `hasLiveSession()` guard client-side (any run row of the task still `status: 'running'` — the Stop hook sets `idle`, not the status, and boot recovery flips stale rows to `exited`). They disable with that exact sentence as the tooltip instead of letting the click return a 409. The mark-done variant is deliberately exempt: `complete` is legal with a live session.
- Verified: `npm run typecheck` + `npm run build` clean. Live: a scratch task forced to `review` showed ✓ = "Mark done" (`affirm` class) and clicking it moved the task review → done without opening the slide-over and with no row error; with a synthetic live run row attached, ▶ and ✓ read "Previous session is still live — …" and were disabled on `failed`, while on `review` ▶ stayed disabled and ✓ stayed "Mark done"; `running` rows still read "Already running" / "Cannot enqueue from 'running'".
