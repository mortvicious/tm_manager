# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local web app ("task manager") that collects tasks for registered repos and automates them by spawning Claude Code agents (`claude` CLI) in each repo's directory. Every worker run is a hidden but fully interactive PTY terminal, attachable from the browser via xterm.js over WebSocket. Full design: `docs/design.md`; decision log: `docs/decisions.md`.

## Commands

- `npm install` — installs all workspaces (shared, server, web)
- `npm run dev` — front door (`tsx server/src/host.ts`, which spawns the API as a `tsx watch` child on http://127.0.0.1:5175) + Vite dev server (http://localhost:5173, proxies /api and /ws to the API, /host to the front door). Open 5173.
- `npm run build` — builds the SPA (`web/dist`); the server has no build step
- `npm start` — production mode: the front door serves `web/dist` at http://localhost:5176 and proxies to the API it supervises on 5175
- `npm run dev:server` / `npm run dev:web` / `npm run start:api` — each half alone; `start:api` is the old single-process behaviour
- `npm run typecheck` — tsc --noEmit over both server and web (CI runs this plus `npm run build`)
- `npm run rebuild:restart` — Rebuild & restart from a terminal: build the SPA (staged + swapped), typecheck, restart the API (`-- --force`, `-- --no-typecheck`); through the front door's job when one runs

No test framework yet. Verify with curl against the REST API and the flows in `docs/design.md` § Verification.

## Architecture (big picture)

npm-workspaces monorepo: `shared/` (TS types imported as source by both sides — REST entities and WS protocol), `server/` (Fastify 5), `web/` (React 19 + Vite SPA).

- **Storage** (`server/src/storage/`): one `Storage` interface, two drivers — SQLite (better-sqlite3, default) and Postgres (`pg`, Supabase-compatible). Driver chosen in `server/data/config.json` (file, not DB — the DB choice can't live in the DB). All tables share the fixed `tm_` prefix and dialect-neutral SQL with `?` placeholders (pg driver rewrites to `$n`; never put `?` inside SQL string literals). Multi-step mutations are first-class composite methods (`claimNextQueuedTask`, `acceptProposal`, `resolveChildCompletion`) implemented transactionally per driver — there is deliberately NO generic `transaction(fn)`: better-sqlite3 transactions are sync-only and an async facade would commit before awaited work runs.
- **PTY sessions** (`server/src/pty/session-manager.ts`): in-memory map of runId → node-pty process + 2MiB ring buffer + attached WS clients. Spawn always uses an args array (never a shell string) with cwd = target repo path.
- **Every claude is a terminal — no headless** (`server/src/claude/aux.ts`, `docs/design.md` § PTY sessions): review, plan, plan-review, analysis, compact, report, chat and commit-message runs are interactive `claude` PTYs in a THIRD `SessionManager` pool (the aux pool). They are attachable over `/ws/terminal/:runId`, can be typed into and killed, and are never a worker slot. Each has a `tm_runs` row: `mode 'aux'`, `kind`, `subject_id`, `label` (migration 28). **`task_id` is NULL on aux rows on purpose**, because every worker rule reads `task_id` as "the task's agent". The task, feature, chat, report or repo an aux run is about is in `subject_id`. Hooks go through the same internal routes, which hand `mode = 'aux'` runs to the runner before any worker logic.
  - Completion: Stop / **StopFailure** (`model_not_found` is how an unavailable model shows up, and it feeds the Fable→Opus fallbacks via `modelUnavailable`) / SessionEnd. Process exit is only the backstop.
  - Structured results: the prompt ends with `resultInstruction(schema)`. The fenced ```` ```json ```` block in the Stop hook's `last_assistant_message` is validated by the caller's zod schema (`acceptJson`), and an invalid block gets a correction TYPED into the same session (≤2).
  - After the result is accepted the PTY is killed, and `done` resolves only after the exit. So a chat's next `--resume`, or the worker behind a compaction, never shares a session id with a live process.
  - `aux().stopAll()` / `liveLabels()` / `stoppedSince()` replace the old headless registry for `/killall`, shutdown, the restart guard and `OrchestratorStatus.aux` (was `headless`).
  - Read-only roles keep their `-p` denials verbatim under `dontAsk`. `--tools` only trims schemas: `READ_ONLY_TOOLS`, none for report/commit.
- **Completion detection** (`server/src/claude/worker.ts`): workers run interactive `claude` with lifecycle hooks injected via `--settings` inline JSON; Stop/SessionEnd/Notification hooks curl back to token-guarded `/api/internal/runs/:id/*` routes. First Stop → task `review`, always (`done`/publish are the landing tier's, decided after the verify round). A `UserPromptSubmit` hook (`/prompt` route → `Orchestrator.promptInLiveSession`) moves `review → running` (actor `human`, reason `prompt in live session`) when a prompt is submitted into the task's IDLE live session — only a human types there, since every server turn goes through `followUp` — unless a review round/check stage is open (`verifyOpen`, `pendingReviews`), the task is a loop, or the prompt is a `/` command; it un-idles the session (`markActive` + `idle: false`) so the next Stop lands normally. Notification hook → "needs attention" badge (permission prompts in hidden terminals would otherwise deadlock silently) — only for a PROMPT: the route drops the CLI's non-prompt kinds by `notification_type` against the DENY-list `NON_PROMPT_NOTIFICATIONS` (`claude/notification.ts`: `idle_prompt` — which a non-idled `waiting` park used to turn into 83% of all flags — auth/quota/completion notes); unknown or missing type still flags, the hook deliberately has NO `matcher` (an allow-list would drop a future real prompt type), the aux runner reads `idle_prompt` the same way (text regex only without a type), and `run.attention` carries `data: { type, message }`. The flag is CLEARED when the agent moves on, not only on Stop: `attentionFlagged` stamps the raise time and the activity watcher's `progressed` callback (every new assistant transcript line, not only narration changes) drives `attentionProgress`, which clears on a line NEWER than the flag — an older line is the one that caused the prompt. `run.needs-attention` is broadcast for the clear too, so consumers must read `run.needsAttention` from the event.
- **Transient API errors + retry with context** (`server/src/claude/transient.ts`, `docs/design.md` § Transient API errors / § Retry with context): workers inject `StopFailure` too. The CLI's own `error` code decides, never text:
  - `overloaded`/`server_error` → back off 30 s / 2 min and resume the SAME session (typed `continue` into the live PTY, transcript growth checked after 20 s, else `followUp(…, 'resume')`). 2 per turn, each through `budgetAllows(…, 'transient-resume')`, audited `run.transient-retry`.
  - `rate_limit` → the wake path's alone.
  - Anything else or a third transient → `failed` with the reason, terminal ended.

  It is NOT the rejected auto-retry: never a fresh agent. Retry/Run now keep the error they clear in a `task.retry` row, and a fresh start without a follow-up of a task that had a session gets a `## Previous attempt` block (`retryContext` → `freshHandoff`). `tm_tasks.attempts` (migration 35) counts fresh sessions (`bumpTaskAttempts`, never through `updateTask`).
- **Groups and order** (`docs/grouping.md`): a group is a task tree (`group_id`/`group_path`, no groups table). `tm_tasks.sort_order` (migration 26, DOUBLE PRECISION) is a position among SIBLINGS only — new rows take global max+1, a move writes a midpoint (`keyNextTo`), renumbering the sibling set only when the gap is spent — and it is the global claim's tiebreaker after priority (`MANUAL_CLAIM_ORDER`: group root's key, root first, own key), so the board's `queue order` IS the run order. Every regroup/reorder from the UI goes through `POST /api/tasks/:id/move` (`before|after|into|child|group|ungroup`, storage composite `moveTask`); `into` joins the target's group FLAT. A child may not leave a `blocked` split parent (409, `reparentRefusal`, shared by move and PATCH). Board drag and drop is pointer events on a grip with `data-drop-task`/`data-drop-group` hit-testing (`components/TaskDrag.tsx`) — not the HTML5 API, which is dead on iOS touch.
- **Features** (`docs/features.md`): a per-repo big request that a planning session (aux kind `plan`) decomposes into ordered phases of tasks, a second session (`plan-review`) reviews adversarially (bounded re-analysis rounds), and the human approves visually before any `tm_tasks` row exists. Execution is the normal orchestrator plus one claim-eligibility gate (`storage/feature-sql.ts`, shared verbatim by both drivers and mirrored by a JS twin — edit them together). Standing caps are injected into every generated task description server-side.
- **Repo commands** (`server/src/commands/`, `docs/commands.md`): saved per-repo command lines (dev servers, scripts) run in a SECOND `SessionManager` pool so a long-lived dev server never touches agent concurrency or the PTY cap. Command text is tokenized and spawned as argv (never a shell; unquoted shell operators are rejected at the API). Runs are in-memory only — `tm_runs` means "a claude session" (worker or aux), and boot recovery treats it that way. Restarting the server is refused while any agent session is working. Agents reach them through `/api/agent/commands` (`routes/agent-commands.ts`, `docs/commands.md` § Agent API) instead of their own background shells: start is start-OR-REUSE (a running one is the shared server, never a 409), stop only a run the caller's TASK started (`CommandRun.ownerTaskId`; restart keeps the previous owner), readiness by `waitFor` substrings (never an agent regex), and servers outlive the task.
- **Terminals** (`server/src/shells/runner.ts`, `docs/terminals.md`): plain login shells per repo (`$SHELL -l`, cwd = repo, argv only) from the `/terminals` page — a FOURTH `SessionManager` pool, in-memory `ShellRunner`, ids `sh-<uuid>` on the ordinary `/ws/terminal/:id`. Cap `MAX_SHELL_SESSIONS` (10 open entries, exited included — equal to the pool's own cap, so its error never surfaces); an exited shell stays until closed. Open/close require `Origin`. Killed on restart/shutdown (`stopAll`), never blocking it, reported as `shells` in restart-check; `/killall` leaves them alone like repo commands. Desktop embeds `ShellPane`s (tabs keep every pane mounted; a hidden pane never refits); phones open the drawer for its key row. **Agent shells** (`claude/background-shells.ts`, `routes/background-shells.ts`, docs/terminals.md § Background shells): the page's second view (and the task panel) lists live worker runs' background shells from Stop/SubagentStop `background_tasks`, in memory per run (dropped at run end), enriched from the transcript (launch time, the CLI-reported `…/tasks/<id>.output`) and a 5 s `ps`/`lsof` sweep; broadcast `background-shells`. Watch reads ONLY that reported file (never a request path). Kill (Origin, `shell.killed` audit) re-resolves the pid at kill time — direct child of the run's claude pid, group leader, stdout = the id's `.output` — SIGTERMs the group, ignores the shell and replays a shell-held park (`shellsKilled`).
- **Publish** (`docs/publish.md`): a task in `review` is shipped by reopening ITS OWN claude session (`claude --resume`) and telling it to `git add`/`commit`/`push` — same terminal, no new agent; the `auto-publish` landing tier (see Landing tiers) runs that turn automatically, but only after the checks are green and the review is clean. The landing status is decided by `verifyPublished()` reading git afterwards (clean tree, upstream exists, nothing ahead), never by what the agent reported — anything else drops the task back to `review` with the reason. `published` is terminal: keep `TERMINAL_TASK_STATUSES` (shared), `feature-sql.ts` and its JS twin in lockstep. **Verify gate** (§ The verify gate): `publish()` 409s for EVERY caller while `verifyOpen` (reason `publishGateReason`, shared); over a settled flagged/red verdict a human may publish, but the SPA demotes it from every primary slot and asks first (`confirmPublish` restating `publishCaution`). Auto-publish never hits the gate (`landingReason` needs a settled clean verdict). **Push policy** (§ Push policy, decisions.md 2026-10-26): when `shipHeldForReview` does NOT hold, every worker turn but the publish turn carries the repo's `tm_repos.push_policy` (migration 41) via `shipRule()` — `repo-rules` (default, no rule), `agent-pushes` (push without asking only if every commit in `@{u}..HEAD` has the task's own trailer, else commit locally; never ask), `publish-turn` (never push) — the ship gate wins when it holds; `effectivePushPolicy` clamps external tasks to `repo-rules`; setting `agent-pushes` needs `Origin`. The standing rules promise a review only when `reviewWillRun` (the Stop hook's `pending` test).
- **Dispatch** (`docs/dispatch.md`): agent-to-agent messages between RELATED tasks (one it filed, the one that filed it, own group) — `POST /api/agent/dispatch` queues a message that the orchestrator delivers by resuming the target task's OWN claude session (`followUp` → `claude --resume`), so a backend⇄frontend exchange stays two sessions instead of minting new tasks. `tm_dispatches` is FK-less like `tm_events`; delivery holds while the target is busy, never starts a never-ran draft (enqueue-gate bypass), and runs even with the queue stopped. Every dispatch carries a REQUIRED `intent`: `needs_action` resumes the target as today, `fyi` **never wakes a session** — it stays pending and rides along on the target's next resume for a reason of its own, drained in **`startWorker()`** (the single funnel for every turn — `followUp` covers only resumes, while the claim loop, `pumpCustomQueue` and `runNow` spawn through `startWorker` directly) as a separate `dispatchNote` argument, never concatenated onto `followUp` (the publish turn is `followUp === PUBLISH_INSTRUCTION` by identity); read before the spawn, settled only after it succeeds. An `fyi` to a done/published/cancelled target becomes a note+event, no run; `failed` is excluded from that set on purpose (it gets retried), which is why `DISPATCH_TERMINAL_STATUSES` is not `TERMINAL_TASK_STATUSES`. Caps: 2/run, 3 lifetime per task pair (both directions and both intents — the guard that ends ping-pong), templated into the served instruction sheet so it cannot drift.
- **Custom queue** (`docs/queue.md`): "Add to queue" marks a task (`tm_tasks.custom_queue_at`, also its FIFO position) into a queue that is independent of the global `orchestrator.enabled` switch and serial PER REPO — one task per repo, repos in parallel up to the worker cap (decisions.md 2026-10-22: one repo never waits for another). `pumpCustomQueue()` runs at the top of every scheduling pass before the enabled check and walks one head per repo (`peekCustomQueue(skipRepoIds)` → `claimCustomQueuedTask(id)`); the claim SQL (`storage/queue-sql.ts`, shared verbatim by both drivers) claims a row only while it is the eligible head of ITS repo (no same-repo member holding it), the stop-hook route holds that member's REPO across the review/publish follow-on gap, and the global claims carry `custom_queue_at IS NULL`. Enqueue/retry mean the global queue and clear the mark. **A task in `review` holds its repo only while its automatic review round is open** (`review_state` `pending|reviewing|fixing`, or `check_state` `pending|running` — `docs/checks.md`; the `heldBy` fragment in `queue-sql.ts`, JS twin `customQueueHoldsRepo` in shared — edit together): once the review settles, the task STAYS in `review` with its mark and the next same-repo member starts (decisions.md 2026-09-28). **Stacked tasks** (`docs/queue.md` § Stacked tasks): before that claim the pump commits the tree owner's leftovers locally under ITS `Task:` trailer whenever the owner is not working (review, an Undo'd `queued`/`draft`, failed/cancelled; waits on `running`/`waiting` or an open review round) (`handOffCheckout` → `git.ts` `handoffCommit`; tree owner = newest worker run in the repo, publish runs excluded via `tm_runs.label = 'publish'`), and publish goes in order (`publishPlan` over `unpushedCommits`' trailers vs `UNAPPROVED_STATUSES` peers — `review|running|waiting|blocked|queued|draft`): refused while an unapproved task's commits sit under this one (reason on the row, so auto-publish shows it), PARTIAL — `publishUpToInstruction`, push exactly its last sha, stage nothing, recognised by `isPublishInstruction` — while unapproved work sits on top; `settlePublish` recomputes the plan (`publishedCheck`). **Undo start** (`POST /api/tasks/:id/undo`, `Orchestrator.undoStart`) kills a running turn like cancel but returns the task to the status it had before the turn (the newest `task.transition` into `running` not from `running`/`waiting`); back in `queued` it keeps its place but is HELD (`tm_tasks.queue_held_at`, migration 31) — every claim SQL skips it until Release (`/release`), Run now, Enqueue or Add to queue, and every other `transitionTask` clears the hold.
- **Adversarial review** (`server/src/claude/review.ts`, `docs/design.md` § Adversarial review): a read-only reviewer TERMINAL (aux kind `review`, subject = the task; the live `auto-review` badge opens it) over **the change THIS task made** (`workerDiff(repo, scope)`, scope from `Orchestrator.changeScope`): its commits (found on any ref by the `Task: <id>` trailer every worker turn is told to add (`commitTrailerRule`), else base..HEAD, bounded by the task's last landing, but only when no other task's worker overlapped that window in the repo), listed above the diff, plus the uncommitted `git diff HEAD` (read only while no later task has worked in the checkout). The base is `tm_tasks.base_sha/base_ref/base_at` (migration 29), which is HEAD at the first worker spawn (`ensureBase`) and is never moved by retries or fix rounds. A pre-29 task derives its base from its first run's start. `--ignore-submodules=dirty` and `.claude/worktrees` are excluded on both the `add -N` and every diff: a tracked worktree gitlink renders `-dirty` on every read and defeated the hash gate. The review runs before the change lands in the human queue, with blocker/major findings fed back into the SAME live worker session, bounded by `review.maxRounds` (**default 1**). **Each diff is reviewed at most once**: `workerDiff()` hashes the commit shas + the combined raw diff (sha256, BEFORE the 60k prompt truncation; with no commits it is exactly the old `git diff HEAD` hash) and the hash is stored on the task (`tm_tasks.review_diff_hash`); an unchanged hash means no reviewer session at all — the previous verdict stands and the task stays in `review`. That is what keeps dispatch-reply and other talk-only turns from being reviewed; there is deliberately NO dispatch special-case, the hash is the whole test. `empty-diff` means the task changed nothing: no commits of its own and a clean tree. Both skips are audited as `run.reviewed` rows carrying `skipped: 'unchanged-diff' | 'empty-diff'`, so a review that did not run is a decision in the log, never a gap. **Where the review stands is on the row**: `tm_tasks.review_state` (migration 22, `pending|reviewing|fixing|passed|flagged|skipped|error|null`) is written in the SAME conditional transition that parks the task (`pending` when a review will run, `null` when not — publish turn, review off) and stepped by the round; there is deliberately NO new `TaskStatus` — the SPA renders `review`+pending/reviewing as a synthetic **auto-review** badge and `running`+fixing as **fixing** (`StatusBadge`), like the needs-attention badge. **Who reviews is per task**: `tm_tasks.review_model`/`review_effort` (migration 25) resolve as `task.reviewModel ?? review.model` in `runReviewRound`; only a FABLE unavailability is cached for the Opus fallback, so a per-task Sonnet pick is never silently swapped. **"Unavailable" is StopFailure `model_not_found` and nothing else**: `modelUnavailable` reads the CLI's own code (`AuxOutcome.code`) and never free text. The old regex over the error hit on the `-p` argv echo and on any "Service Unavailable", so every failure fell back and poisoned the cache. A timeout or abort never falls back. The single fallback is `withModelFallback` in `aux.ts`, with one process-wide Fable cache shared by review, plan and report. A failed round's `error` is the real cause: the StopFailure code and text, `timed out after 10 min`, or the exit plus the terminal's last words (`readableTail`), never the argv. Every real round is appended to `tm_tasks.review_rounds` (`ReviewRound`: model, effort, verdict, findings, the reviewer's **summary** of the work, `fixRound`, hash); the loop BUDGET (`Orchestrator.fixRounds`, in memory) is separate from that history on purpose. The reviewer's structured output includes that summary (the human's summary of the work — the worker's own after a fix round is "fixed 1 and 2"), and a fix-round Stop APPENDS to `resultSummary` (`appendFixNote`) rather than overwriting it. **Fix rounds converge** (decisions.md 2026-10-26): a fix round's prompt carries ONLY the previous round's blocker/major findings, numbered, and the reviewer returns `previous[{id,status}]` plus NEW findings with ≤3 minors (`FIX_ROUND_MAX_MINORS`). `mergeFixRound` puts any numbered finding not marked resolved back into `findings` and derives the verdict (`ReviewRound.resolutions`). Each round stores per-file `files` digests (`fileDigests`) + `commits`, so the next round is told what changed over the FULL diff. Both fix messages end with `REVIEW_FIX_SCOPE` (blocker/major only, list the untouched minors; no "minors if quick"). Boot recovery re-runs reviews left `pending|reviewing` (as `forced` — that state is a decision already taken) and settles a stranded `fixing`. **Review now** (`POST /api/tasks/:id/review` → `reviewTask` in `task-actions.ts` → `Orchestrator.reviewNow`; SPA button, Telegram `/review` + 🔍 card button) runs the SAME round on demand for `review|done|blocked|failed`: it bypasses the hash gate by CLEARING `review_diff_hash` in the write that marks `pending` (so a restart's re-run is a real review too), skips the `review.enabled` check, resets the fix budget, and 409s `review already in progress` on the lock (checked and taken synchronously). It never changes status: findings go back to the worker only for `review` + live session, as the automatic round; elsewhere the verdict is just recorded. The requester is memory-only (`requestedReviews`), read synchronously by the Telegram notifier to ping a requested verdict on a non-`review` task. **Review gates the ship** (`docs/decisions.md` 2026-09-24): when `shipHeldForReview(task, settings)` (`landing === 'auto-publish' || (task.review ?? review.enabled)` — the Stop hook's own `pending` test, plus the auto-publish tier, whose publish turn is what ships) holds, every worker turn except the publish turn carries `SHIP_GATE_RULE`, which overrides the repo's CLAUDE.md: no push, no deploy (local commits are fine, because the reviewer reads them). The publish turn (`PUBLISH_INSTRUCTION` step 5) pushes and then runs the repo's deploy/verify steps. Review-off tasks on a lower tier get the repo's push policy instead (see Publish).
- **Resume gate** (`server/src/claude/compact.ts`, `docs/token-budget.md` § The fourth): a `--resume` re-writes the WHOLE conversation to cache twice (≈$15 on a 400k session) before the follow-up turn says a word, so above `agent.resumeContextCap` (default 300k tokens, measured from `RunStats.contextTokens` — the raw last-turn total, a token count whatever the model's window) the session is compacted first in an aux terminal (kind `compact`): `claude --resume <id> -- "/compact <focus>"`, which keeps the session id, so the PTY behind it resumes the same session. Decided in `Orchestrator.resumeHandoff` from `startWorker`, on an IDLE session only — never mid-run. `--autocompact` was rejected: no focus string, and it would govern the whole resumed run. Success is read from a `compact_boundary` in the transcript, never from the turn itself (a compaction that did nothing looks like a clean empty success; the runner settles on the boundary, polled and on SessionStart `source: compact`). A failed compaction goes `fresh` — the non-resume prompt branch with a richer summary (previous last assistant text in full + `git diff --name-only HEAD`) — except for the publish turn, which resumes anyway rather than hand a commit to an agent that did not write it. Every spawn records `handoff: 'resume' | 'compact' | 'fresh'` on `run.started`. The gate turns a millisecond window between "marked running" and "PTY spawned" into a ten-minute one, so two rules guard it: a compaction WE stopped is `aborted`, never `failed` (`aux().stoppedSince` for `/killall` and forced restart, `abortCompaction(taskId)` from `cancel()`, and `compactSession`'s own deadline timer so a timeout is not mistaken for either) and returns an `abort` kind that spawns nothing and parks the task in `review`; and `startWorker` RE-READS the task row after the gate, bailing on anything but `running` and broadcasting the re-read row, never the stale one. A task inside the gate has NO run row, so `recoverOnBoot` sweeps `running` tasks with no `running` run row (→ `review` if they ever had a worker, else `failed`) and `stop()` awaits `drainResumeGates()`; and dispatch delivery FIRES `followUp` instead of awaiting it (`dispatchTurnsInFlight` holds the target), because that await sits inside `maybeSchedule`'s single-flight pass. `activeWorkers()` counts gates and fired dispatch turns as well as live PTYs — `status()` still reports the honest live count.
- **Auto wake-up** (`server/src/claude/limit.ts`, `docs/wake.md`): a turn stopped by the ACCOUNT rather than by its work is parked with the time the 5h window reopens (`tm_tasks.wake_at`, migration 21) and resumed there in its OWN session — `proceed()`, the same call the button makes, so there is one resume path. Detection reads the PTY ring buffer (`sessionTail`), because the limit banner is terminal CHROME: it is never an assistant message, so it reaches neither the transcript nor `lastAssistantText`. ANSI is stripped BEFORE matching (`\x1b[31m5-hour limit` has no word boundary before the `5`, so anchored patterns would never fire on the one surface they exist for), and the LAST banner in the buffer wins. A banner is NEVER enough on its own — those bytes are whatever the terminal displayed, and this repo's own docs contain literal matches — so `assessLimitStall()` requires the banner in the LAST 4k of the tail (400 when the task is still `running`, where acting means killing a live PTY), NO permission dialog at the end of the terminal, AND the account's own live 5h window reading >=90% — which is a veto, not evidence, since >=90% is the normal reading whenever this code can fire. A run flagged `needsAttention` is skipped outright: it is blocked on a HUMAN, is transcript-silent by design, and killing it would discard the answer it is waiting for; no account data means no park, and a rejected banner is audited once per run as `action: 'skipped'`. **The CLI's own StopFailure `rate_limit` code outranks all of that** (decisions.md 2026-10-26): the account cache is written only by the `/usage` panel, which workers never open, so the veto vetoed every banner ever seen. `onStopFailure` remembers the code per run (`rateLimitStops`, in memory; void once the transcript grows >30 s past it), and with it `assessLimitStall(…, { cliRateLimit })` skips the position test and the account veto (the prompt test stays). The reset comes from `error_details`, else a last-screenful banner, else +5 h. A banner WITHOUT the code still needs the old evidence. **The CLI continues first**: since 2.1.234 an interactive session auto-continues at the reset + 30–90 s (`autoContinueAtUsageLimit`, default on), and exiting the PTY cancels that. So a live run with the code and a stated reset is NOT killed. `leaveToCli` sets `wake_at` = reset + 90 s with a `left-to-cli` row, and `wakeDue` holds off (`cliWaitFor`). `cliContinued` (the continuation prompt via `/prompt` — moved as `system`, not `human` — or `quota_auto_resume_fired`, or transcript growth) clears it. `_stale`/`_disabled`, or reset + 90 s + 3 min with nothing moving, is a takeover into the park below. `rateLimitIsWindow` keeps a 429/credits `rate_limit` out. **Streak cap** (CLI continuations count): the park after 3 consecutive wakes hands the task to the human with the reason in `error` (`task.wake` `handed-off`). Consecutive = `resumed` rows newer than the task's newest non-`system`/`orchestrator` transition, so a weekly limit is not woken every 5 h for days. Deliberately NO new `TaskStatus`: `review`/`failed` are already the statuses a resume accepts, and neither the status nor `error` is rewritten by the parker. `resolveWakeAt` takes the LATER of the banner's time and the account's `resets_at` (a premature resume re-buys the whole context, so early is expensive and late is only late), bounded by one window either way. The 30s sweep also catches stalls whose PTY never died, driven from the live RUNS (capped at 10) rather than from every `failed` task ever: there is deliberately no `isIdle` test (`markIdle()` runs only AFTER the stop hook has moved the task out of `running`, so "running and idle" cannot exist and gating on it made the sweep unreachable) — quiet is `transcriptQuietMs()` instead, and a live stall is ENDED at park time (run marked `killed` FIRST so `handleExit` leaves the task alone, PTY killed, task moved to `review`) because `followUp` refuses a `running` task, which is why `running` is not in `WAKE_RESUMABLE_STATUSES`. It wakes ONE per pass, obeys the global switch (except custom-queue members) and the concurrency cap, and clears the mark BEFORE resuming so a refusal is audited once instead of retried forever — the row is the truth and the map is a cache, which is why `startWorker` clearing `wake_at` on every spawn is what makes a human clicking Proceed cancel the wake for free.

A shell the CLI moved to the background after its Bash TIMEOUT never counts (`timedOutAfterMs` on its launching `toolUseResult` in the transcript, judged once per shell at its first Stop by `autoBackgroundedShells` → the run's `ignoredShells`, audited `task.waiting { ignored: 'auto-backgrounded' }`; decisions.md 2026-10-26). **Stop waiting** (`POST /api/tasks/:id/stop-waiting`, Origin; `stopWaitingTask` → `Orchestrator.stopWaiting`; SPA panel + board row + Telegram `t:sw`, offered from `OrchestratorStatus.shellWaits`) lands a park held by shells ALONE: ignores and kills them (`killBackgroundShells`: process group of each direct child of the claude pid whose argv has `eval '<command>'`) and runs the timer's own replay, audited `expired: 'human'`; a child out → 409. Deliberate waits on a filed task are out of scope by design.

## Rules

- Visual changes must resolve to the `--tm-*` tokens defined in `docs/tm-design-tokens.html` (mirrored in `web/src/theme.css`). No hardcoded colors/spacing/fonts outside that token layer (xterm.js needs concrete values — take them from the sheet's terminal tokens).
- Two designs (`docs/glass.md`): **Classic** (`theme.css`) and **Glass**, the iOS Liquid Glass layer in `web/src/glass.css`, picked per device (`html[data-design]`, `src/appearance.ts` + its inline twin in `index.html`). Every Glass rule is scoped to `[data-design='glass']` and its tokens are the Glass blocks in `theme.css`, so Classic keeps rendering unchanged; a new component gets Glass colours and type through the remapped tokens and needs a `glass.css` rule only for a material or motion of its own. Never put `backdrop-filter`/`filter`/`transform` on `.main`, `.header` or `.app`: they hold `position: fixed` overlays, and those properties make an element their containing block. Overlays animate out through `exitGhost` (`src/motion.ts`), not a closing state. On a phone every overlay is a `<Sheet>` (`components/Sheet.tsx`, react-modal-sheet + motion pinned to neko-frontend's versions, `docs/mobile.md` § Sheets): it plays its own exit before `onClose`, its content must live in the library's scroller (no nested scroller, or drag-from-the-top breaks), and in Glass every sheet is Liquid Glass. Glass hides Features and Chat from the PHONE menus only (tab bar, More sheet); the desktop sidebar lists them in both designs, and their routes stay for deep links (decisions.md 2026-10-26).

- Document all work in `docs/` — updating docs is an exit criterion of every phase/change.
- Worker prompts must include the standing caps: max 3 subagents per session; orchestrator concurrency stays at 2.
- Adversarial review of each phase before moving to the next (max 3 agents at a time).
- Agent model is `claude-opus-5-5`; the fable roles (analysis/orchestrator/router-primary/review) are `claude-fable-5-1`. The offered list is `MODEL_OPTIONS` in `shared/` — every dropdown (web config, board, task panel, Telegram `/new`) renders that one array.
