# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local web app ("task manager") that collects tasks for registered repos and automates them by spawning Claude Code agents (`claude` CLI) in each repo's directory. Every worker run is a hidden but fully interactive PTY terminal, attachable from the browser via xterm.js over WebSocket. Full design: `docs/design.md`; decision log: `docs/decisions.md`.

## Commands

- `npm install` — installs all workspaces (shared, server, web)
- `npm run dev` — front door (`tsx server/src/host.ts`, which spawns the API as a `tsx watch` child on http://127.0.0.1:5175) + Vite dev server (http://localhost:5173, proxies /api and /ws to the API, /host to the front door). Open 5173.
- `npm run build` — builds the SPA (`web/dist`); the server has no build step
- `npm start` — production mode: the front door serves `web/dist` at http://localhost:5176 and proxies to the API it supervises on 5175
- `npm run dev:server` / `npm run dev:web` / `npm run start:api` — each half alone; `start:api` is the old single-process behaviour
- `npm run typecheck` — tsc --noEmit over both server and web (CI runs this plus `npm run build`)

No test framework yet. Verify with curl against the REST API and the flows in `docs/design.md` § Verification.

## Architecture (big picture)

npm-workspaces monorepo: `shared/` (TS types imported as source by both sides — REST entities and WS protocol), `server/` (Fastify 5), `web/` (React 19 + Vite SPA).

- **Storage** (`server/src/storage/`): one `Storage` interface, two drivers — SQLite (better-sqlite3, default) and Postgres (`pg`, Supabase-compatible). Driver chosen in `server/data/config.json` (file, not DB — the DB choice can't live in the DB). All tables share the fixed `tm_` prefix and dialect-neutral SQL with `?` placeholders (pg driver rewrites to `$n`; never put `?` inside SQL string literals). Multi-step mutations are first-class composite methods (`claimNextQueuedTask`, `acceptProposal`, `resolveChildCompletion`) implemented transactionally per driver — there is deliberately NO generic `transaction(fn)`: better-sqlite3 transactions are sync-only and an async facade would commit before awaited work runs.
- **PTY sessions** (`server/src/pty/session-manager.ts`): in-memory map of runId → node-pty process + 2MiB ring buffer + attached WS clients. Spawn always uses an args array (never a shell string) with cwd = target repo path.
- **Every claude is a terminal — no headless** (`server/src/claude/aux.ts`, `docs/design.md` § PTY sessions): review, plan, plan-review, analysis, compact, report, chat and commit-message runs are interactive `claude` PTYs in a THIRD `SessionManager` pool (the aux pool). They are attachable over `/ws/terminal/:runId`, can be typed into and killed, and are never a worker slot. Each has a `tm_runs` row: `mode 'aux'`, `kind`, `subject_id`, `label` (migration 28). **`task_id` is NULL on aux rows on purpose**, because every worker rule reads `task_id` as "the task's agent". The task, feature, chat, report or repo an aux run is about is in `subject_id`. Hooks go through the same internal routes, which hand `mode = 'aux'` runs to the runner before any worker logic.
  - Completion: Stop / **StopFailure** (`model_not_found` is how an unavailable model shows up, and it feeds the Fable→Opus fallbacks via `modelUnavailable`) / SessionEnd. Process exit is only the backstop.
  - Structured results: the prompt ends with `resultInstruction(schema)`. The fenced ```` ```json ```` block in the Stop hook's `last_assistant_message` is validated by the caller's zod schema (`acceptJson`), and an invalid block gets a correction TYPED into the same session (≤2).
  - After the result is accepted the PTY is killed, and `done` resolves only after the exit. So a chat's next `--resume`, or the worker behind a compaction, never shares a session id with a live process.
  - `aux().stopAll()` / `liveLabels()` / `stoppedSince()` replace the old headless registry for `/killall`, shutdown, the restart guard and `OrchestratorStatus.aux` (was `headless`).
  - Read-only roles keep their `-p` denials verbatim under `dontAsk`. `--tools` only trims schemas: `READ_ONLY_TOOLS`, none for report/commit.
- **Completion detection** (`server/src/claude/worker.ts`): workers run interactive `claude` with lifecycle hooks injected via `--settings` inline JSON; Stop/SessionEnd/Notification hooks curl back to token-guarded `/api/internal/runs/:id/*` routes. First Stop → task `review` (or `done` if autoComplete). Notification hook → "needs attention" badge (permission prompts in hidden terminals would otherwise deadlock silently). The flag is CLEARED when the agent moves on, not only on Stop: `attentionFlagged` stamps the raise time and the activity watcher's `progressed` callback (every new assistant transcript line, not only narration changes) drives `attentionProgress`, which clears on a line NEWER than the flag — an older line is the one that caused the prompt. `run.needs-attention` is broadcast for the clear too, so consumers must read `run.needsAttention` from the event.
- **Groups and order** (`docs/grouping.md`): a group is a task tree (`group_id`/`group_path`, no groups table). `tm_tasks.sort_order` (migration 26, DOUBLE PRECISION) is a position among SIBLINGS only — new rows take global max+1, a move writes a midpoint (`keyNextTo`), renumbering the sibling set only when the gap is spent — and it is the global claim's tiebreaker after priority (`MANUAL_CLAIM_ORDER`: group root's key, root first, own key), so the board's `queue order` IS the run order. Every regroup/reorder from the UI goes through `POST /api/tasks/:id/move` (`before|after|into|child|group|ungroup`, storage composite `moveTask`); `into` joins the target's group FLAT. A child may not leave a `blocked` split parent (409, `reparentRefusal`, shared by move and PATCH). Board drag and drop is pointer events on a grip with `data-drop-task`/`data-drop-group` hit-testing (`components/TaskDrag.tsx`) — not the HTML5 API, which is dead on iOS touch.
- **Features** (`docs/features.md`): a per-repo big request that a planning session (aux kind `plan`) decomposes into ordered phases of tasks, a second session (`plan-review`) reviews adversarially (bounded re-analysis rounds), and the human approves visually before any `tm_tasks` row exists. Execution is the normal orchestrator plus one claim-eligibility gate (`storage/feature-sql.ts`, shared verbatim by both drivers and mirrored by a JS twin — edit them together). Standing caps are injected into every generated task description server-side.
- **Repo commands** (`server/src/commands/`, `docs/commands.md`): saved per-repo command lines (dev servers, scripts) run in a SECOND `SessionManager` pool so a long-lived dev server never touches agent concurrency or the PTY cap. Command text is tokenized and spawned as argv (never a shell; unquoted shell operators are rejected at the API). Runs are in-memory only — `tm_runs` means "a claude session" (worker or aux), and boot recovery treats it that way. Restarting the server is refused while any agent session is working.
- **Terminals** (`server/src/shells/runner.ts`, `docs/terminals.md`): plain login shells per repo (`$SHELL -l`, cwd = repo, argv only) from the `/terminals` page — a FOURTH `SessionManager` pool, in-memory `ShellRunner`, ids `sh-<uuid>` on the ordinary `/ws/terminal/:id`. Cap `MAX_SHELL_SESSIONS` (10 open entries, exited included — equal to the pool's own cap, so its error never surfaces); an exited shell stays until closed. Open/close require `Origin`. Killed on restart/shutdown (`stopAll`), never blocking it, reported as `shells` in restart-check; `/killall` leaves them alone like repo commands. Desktop embeds `ShellPane`s (tabs keep every pane mounted; a hidden pane never refits); phones open the drawer for its key row.
- **Publish** (`docs/publish.md`): a task in `review` is shipped by reopening ITS OWN claude session (`claude --resume`) and telling it to `git add`/`commit`/`push` — same terminal, no new agent; a per-task `auto_publish` flag runs that turn automatically at the end of the work, bypassing both the human review gate and the adversarial review round. The landing status is decided by `verifyPublished()` reading git afterwards (clean tree, upstream exists, nothing ahead), never by what the agent reported — anything else drops the task back to `review` with the reason. `published` is terminal: keep `TERMINAL_TASK_STATUSES` (shared), `feature-sql.ts` and its JS twin in lockstep.
- **Dispatch** (`docs/dispatch.md`): agent-to-agent messages between RELATED tasks (one it filed, the one that filed it, own group) — `POST /api/agent/dispatch` queues a message that the orchestrator delivers by resuming the target task's OWN claude session (`followUp` → `claude --resume`), so a backend⇄frontend exchange stays two sessions instead of minting new tasks. `tm_dispatches` is FK-less like `tm_events`; delivery holds while the target is busy, never starts a never-ran draft (enqueue-gate bypass), and runs even with the queue stopped. Every dispatch carries a REQUIRED `intent`: `needs_action` resumes the target as today, `fyi` **never wakes a session** — it stays pending and rides along on the target's next resume for a reason of its own, drained in **`startWorker()`** (the single funnel for every turn — `followUp` covers only resumes, while the claim loop, `pumpCustomQueue` and `runNow` spawn through `startWorker` directly) as a separate `dispatchNote` argument, never concatenated onto `followUp` (the publish turn is `followUp === PUBLISH_INSTRUCTION` by identity); read before the spawn, settled only after it succeeds. An `fyi` to a done/published/cancelled target becomes a note+event, no run; `failed` is excluded from that set on purpose (it gets retried), which is why `DISPATCH_TERMINAL_STATUSES` is not `TERMINAL_TASK_STATUSES`. Caps: 2/run, 3 lifetime per task pair (both directions and both intents — the guard that ends ping-pong), templated into the served instruction sheet so it cannot drift.
- **Custom queue** (`docs/queue.md`): "Add to queue" marks a task (`tm_tasks.custom_queue_at`, also its FIFO position) into a queue that is independent of the global `orchestrator.enabled` switch and strictly serial — one task (so one repo) at a time; same-repo tasks wait. `pumpCustomQueue()` runs at the top of every scheduling pass before the enabled check; the claim SQL (`storage/queue-sql.ts`, shared verbatim by both drivers) refuses while any member is `running`, the stop-hook route holds the queue across the review/publish follow-on gap, and the global claims carry `custom_queue_at IS NULL`. Enqueue/retry mean the global queue and clear the mark. **A task in `review` holds its repo only while its automatic review round is open** (`review_state` `pending|reviewing|fixing`; the `heldBy` fragment in `queue-sql.ts`, JS twin `customQueueHoldsRepo` in shared — edit together): once the review settles, the task STAYS in `review` with its mark and the next same-repo member starts (decisions.md 2026-09-28). **Stacked tasks** (`docs/queue.md` § Stacked tasks): before that claim the pump commits the tree owner's leftovers locally under ITS `Task:` trailer whenever the owner is not working (review, an Undo'd `queued`/`draft`, failed/cancelled; waits on `running`/`waiting` or an open review round) (`handOffCheckout` → `git.ts` `handoffCommit`; tree owner = newest worker run in the repo, publish runs excluded via `tm_runs.label = 'publish'`), and publish goes in order (`publishPlan` over `unpushedCommits`' trailers vs `UNAPPROVED_STATUSES` peers — `review|running|waiting|blocked|queued|draft`): refused while an unapproved task's commits sit under this one (reason on the row, so auto-publish shows it), PARTIAL — `publishUpToInstruction`, push exactly its last sha, stage nothing, recognised by `isPublishInstruction` — while unapproved work sits on top; `settlePublish` recomputes the plan (`publishedCheck`). **Undo start** (`POST /api/tasks/:id/undo`, `Orchestrator.undoStart`) kills a running turn like cancel but returns the task to the status it had before the turn (the newest `task.transition` into `running` not from `running`/`waiting`); back in `queued` it keeps its place but is HELD (`tm_tasks.queue_held_at`, migration 31) — every claim SQL skips it until Release (`/release`), Run now, Enqueue or Add to queue, and every other `transitionTask` clears the hold.
- **Adversarial review** (`server/src/claude/review.ts`, `docs/design.md` § Adversarial review): a read-only reviewer TERMINAL (aux kind `review`, subject = the task; the live `auto-review` badge opens it) over **the change THIS task made** (`workerDiff(repo, scope)`, scope from `Orchestrator.changeScope`): its commits (found on any ref by the `Task: <id>` trailer every worker turn is told to add (`commitTrailerRule`), else base..HEAD, bounded by the task's last landing, but only when no other task's worker overlapped that window in the repo), listed above the diff, plus the uncommitted `git diff HEAD` (read only while no later task has worked in the checkout). The base is `tm_tasks.base_sha/base_ref/base_at` (migration 29), which is HEAD at the first worker spawn (`ensureBase`) and is never moved by retries or fix rounds. A pre-29 task derives its base from its first run's start. `--ignore-submodules=dirty` and `.claude/worktrees` are excluded on both the `add -N` and every diff: a tracked worktree gitlink renders `-dirty` on every read and defeated the hash gate. The review runs before the change lands in the human queue, with blocker/major findings fed back into the SAME live worker session, bounded by `review.maxRounds` (**default 1**). **Each diff is reviewed at most once**: `workerDiff()` hashes the commit shas + the combined raw diff (sha256, BEFORE the 60k prompt truncation; with no commits it is exactly the old `git diff HEAD` hash) and the hash is stored on the task (`tm_tasks.review_diff_hash`); an unchanged hash means no reviewer session at all — the previous verdict stands and the task stays in `review`. That is what keeps dispatch-reply and other talk-only turns from being reviewed; there is deliberately NO dispatch special-case, the hash is the whole test. `empty-diff` means the task changed nothing: no commits of its own and a clean tree. Both skips are audited as `run.reviewed` rows carrying `skipped: 'unchanged-diff' | 'empty-diff'`, so a review that did not run is a decision in the log, never a gap. **Where the review stands is on the row**: `tm_tasks.review_state` (migration 22, `pending|reviewing|fixing|passed|flagged|skipped|error|null`) is written in the SAME conditional transition that parks the task (`pending` when a review will run, `null` when not — publish turn, auto-publish, review off) and stepped by the round; there is deliberately NO new `TaskStatus` — the SPA renders `review`+pending/reviewing as a synthetic **auto-review** badge and `running`+fixing as **fixing** (`StatusBadge`), like the needs-attention badge. **Who reviews is per task**: `tm_tasks.review_model`/`review_effort` (migration 25) resolve as `task.reviewModel ?? review.model` in `runReviewRound`; only a FABLE unavailability is cached for the Opus fallback, so a per-task Sonnet pick is never silently swapped. **"Unavailable" is StopFailure `model_not_found` and nothing else**: `modelUnavailable` reads the CLI's own code (`AuxOutcome.code`) and never free text. The old regex over the error hit on the `-p` argv echo and on any "Service Unavailable", so every failure fell back and poisoned the cache. A timeout or abort never falls back. The single fallback is `withModelFallback` in `aux.ts`, with one process-wide Fable cache shared by review, plan and report. A failed round's `error` is the real cause: the StopFailure code and text, `timed out after 10 min`, or the exit plus the terminal's last words (`readableTail`), never the argv. Every real round is appended to `tm_tasks.review_rounds` (`ReviewRound`: model, effort, verdict, findings, the reviewer's **summary** of the work, `fixRound`, hash); the loop BUDGET (`Orchestrator.fixRounds`, in memory) is separate from that history on purpose. The reviewer's structured output includes that summary (the human's summary of the work — the worker's own after a fix round is "fixed 1 and 2"), and a fix-round Stop APPENDS to `resultSummary` (`appendFixNote`) rather than overwriting it. Boot recovery re-runs reviews left `pending|reviewing` (as `forced` — that state is a decision already taken) and settles a stranded `fixing`. **Review now** (`POST /api/tasks/:id/review` → `reviewTask` in `task-actions.ts` → `Orchestrator.reviewNow`; SPA button, Telegram `/review` + 🔍 card button) runs the SAME round on demand for `review|done|blocked|failed`: it bypasses the hash gate by CLEARING `review_diff_hash` in the write that marks `pending` (so a restart's re-run is a real review too), skips the `review.enabled` check, resets the fix budget, and 409s `review already in progress` on the lock (checked and taken synchronously). It never changes status: findings go back to the worker only for `review` + live session, as the automatic round; elsewhere the verdict is just recorded. The requester is memory-only (`requestedReviews`), read synchronously by the Telegram notifier to ping a requested verdict on a non-`review` task. **Review gates the ship** (`docs/decisions.md` 2026-09-24): when `shipHeldForReview(task, settings)` (`!autoPublish && (task.review ?? review.enabled)`, the Stop hook's own `pending` test) holds, every worker turn except the publish turn carries `SHIP_GATE_RULE`, which overrides the repo's CLAUDE.md: no push, no deploy (local commits are fine, because the reviewer reads them). The publish turn (`PUBLISH_INSTRUCTION` step 5) pushes and then runs the repo's deploy/verify steps. Review-off and auto-publish tasks get no rule.
- **Resume gate** (`server/src/claude/compact.ts`, `docs/token-budget.md` § The fourth): a `--resume` re-writes the WHOLE conversation to cache twice (≈$15 on a 400k session) before the follow-up turn says a word, so above `agent.resumeContextCap` (default 300k tokens, measured from `RunStats.contextTokens` — the raw last-turn total, because `contextPct` clamps at 100 against a 200k divisor) the session is compacted first in an aux terminal (kind `compact`): `claude --resume <id> -- "/compact <focus>"`, which keeps the session id, so the PTY behind it resumes the same session. Decided in `Orchestrator.resumeHandoff` from `startWorker`, on an IDLE session only — never mid-run. `--autocompact` was rejected: no focus string, and it would govern the whole resumed run. Success is read from a `compact_boundary` in the transcript, never from the turn itself (a compaction that did nothing looks like a clean empty success; the runner settles on the boundary, polled and on SessionStart `source: compact`). A failed compaction goes `fresh` — the non-resume prompt branch with a richer summary (previous last assistant text in full + `git diff --name-only HEAD`) — except for the publish turn, which resumes anyway rather than hand a commit to an agent that did not write it. Every spawn records `handoff: 'resume' | 'compact' | 'fresh'` on `run.started`. The gate turns a millisecond window between "marked running" and "PTY spawned" into a ten-minute one, so two rules guard it: a compaction WE stopped is `aborted`, never `failed` (`aux().stoppedSince` for `/killall` and forced restart, `abortCompaction(taskId)` from `cancel()`, and `compactSession`'s own deadline timer so a timeout is not mistaken for either) and returns an `abort` kind that spawns nothing and parks the task in `review`; and `startWorker` RE-READS the task row after the gate, bailing on anything but `running` and broadcasting the re-read row, never the stale one. A task inside the gate has NO run row, so `recoverOnBoot` sweeps `running` tasks with no `running` run row (→ `review` if they ever had a worker, else `failed`) and `stop()` awaits `drainResumeGates()`; and dispatch delivery FIRES `followUp` instead of awaiting it (`dispatchTurnsInFlight` holds the target), because that await sits inside `maybeSchedule`'s single-flight pass. `activeWorkers()` counts gates and fired dispatch turns as well as live PTYs — `status()` still reports the honest live count.
- **Auto wake-up** (`server/src/claude/limit.ts`, `docs/wake.md`): a turn stopped by the ACCOUNT rather than by its work is parked with the time the 5h window reopens (`tm_tasks.wake_at`, migration 21) and resumed there in its OWN session — `proceed()`, the same call the button makes, so there is one resume path. Detection reads the PTY ring buffer (`sessionTail`), because the limit banner is terminal CHROME: it is never an assistant message, so it reaches neither the transcript nor `lastAssistantText`. ANSI is stripped BEFORE matching (`\x1b[31m5-hour limit` has no word boundary before the `5`, so anchored patterns would never fire on the one surface they exist for), and the LAST banner in the buffer wins. A banner is NEVER enough on its own — those bytes are whatever the terminal displayed, and this repo's own docs contain literal matches — so `assessLimitStall()` requires the banner in the LAST 4k of the tail (400 when the task is still `running`, where acting means killing a live PTY), NO permission dialog at the end of the terminal, AND the account's own live 5h window reading >=90% — which is a veto, not evidence, since >=90% is the normal reading whenever this code can fire. A run flagged `needsAttention` is skipped outright: it is blocked on a HUMAN, is transcript-silent by design, and killing it would discard the answer it is waiting for; no account data means no park, and a rejected banner is audited once per run as `action: 'skipped'`. Deliberately NO new `TaskStatus`: `review`/`failed` are already the statuses a resume accepts, and neither the status nor `error` is rewritten by the parker. `resolveWakeAt` takes the LATER of the banner's time and the account's `resets_at` (a premature resume re-buys the whole context, so early is expensive and late is only late), bounded by one window either way. The 30s sweep also catches stalls whose PTY never died, driven from the live RUNS (capped at 10) rather than from every `failed` task ever: there is deliberately no `isIdle` test (`markIdle()` runs only AFTER the stop hook has moved the task out of `running`, so "running and idle" cannot exist and gating on it made the sweep unreachable) — quiet is `transcriptQuietMs()` instead, and a live stall is ENDED at park time (run marked `killed` FIRST so `handleExit` leaves the task alone, PTY killed, task moved to `review`) because `followUp` refuses a `running` task, which is why `running` is not in `WAKE_RESUMABLE_STATUSES`. It wakes ONE per pass, obeys the global switch (except custom-queue members) and the concurrency cap, and clears the mark BEFORE resuming so a refusal is audited once instead of retried forever — the row is the truth and the map is a cache, which is why `startWorker` clearing `wake_at` on every spawn is what makes a human clicking Proceed cancel the wake for free.
- **Waiting** (`docs/design.md` § Waiting): the Stop hook fires at the end of EVERY turn, including one the agent ends with a background subagent still running (the CLI re-invokes the session when it returns), so `SubagentStart`/`SubagentStop` hooks are injected beside Stop and the orchestrator tracks each run's children still out (`childrenInFlight`). **The CLI's own `background_tasks` list on the Stop/SubagentStop payload is authoritative** (`runningSubagents()` — `type: 'subagent'` only, never background shells), less ids whose `SubagentStop` was already seen; the hook count is only the fallback for a CLI without the list. A `SubagentStop` for an id that never started is the CLI's own helper agent (`agent_type: ''`, measured) and must NEVER decrement a real child — that is what landed tasks mid-wait. A Stop with children out parks the task in the REAL status `waiting` — session live and NOT idled (it keeps its slot and its repo), `reviewState` null, no review, last words as `resultSummary` — and it returns to `running` on the last child's stop hook or on a transcript line newer than the park (`attentionProgress`, `endWait`); the next Stop lands normally and accepts `['running','waiting']`. On the hook-count fallback only, a Stop on an UNCHANGED children snapshot while still parked is a lost hook: landed, audited `task.waiting { stale: true }` — never a task held forever. `waiting` is a real `TaskStatus` (not a badge) because the row must not read `review`: the reviewer, the review ping, the queue hold and dispatch delivery all key off it. Ripple: queue in-flight list + `CUSTOM_QUEUE_IN_FLIGHT_STATUSES`, dispatch hold list, exit/cancel/kill/boot sweeps, `Record<TaskStatus>` maps in Telegram; `followUp` deliberately does NOT accept it. **Background shells** (`background_tasks` entries `type: 'shell'`, `runningShells()`) hold the park too, but each only for `agent.shellWaitMinutes` (default 30, 0 = never) from the FIRST Stop that listed it (`shellsSeen`) — a dev server and a Lighthouse pass look identical at the Stop, and only the latter re-invokes the session. A shell-held park arms a timer that replays the park's payload through the Stop route (`onShellWaitExpired` → `settleStop(…, replayOf)`): it lands only from `waiting`, only for the park that armed it (`parkedAt`), audited `task.waiting { expired: 'shell-wait' }`; while shells hold it a `SubagentStop` never ends the park. Deliberate waits on a filed task are out of scope by design.
- **Orchestrator** (`server/src/orchestrator.ts`): single-process, event-driven claim loop, max 2 concurrent workers. Boot recovery kills orphaned `claude` pids (after verifying the command line) before failing their tasks.
- **Front door** (`server/src/host.ts`, `docs/host.md`): a SECOND process serves the SPA and reverse-proxies `/api` + `/ws` to the API while supervising it as a child (`/host/status|start|stop|restart`), so the page and the server no longer share a lifetime — the API can stop, crash or restart with the page still up and able to start it again. A proxy, not a second origin, deliberately: the SPA stays same-origin so no CORS layer exists and the `Host`-port equality check in `net.ts` (the DNS-rebinding guard) is untouched — `Host` is rewritten, `Origin` is passed through for the API to judge (except an admitted remote request, see Remote access). `TM_SUPERVISED=1` makes the API's own restart route exit rather than detach a replacement; two supervisors racing for one port is the bug that flag prevents. `/host/stop|restart` never restate the agents-working rule — they forward `GET /api/server/restart-check` verbatim.
- **Telegram bot** (`server/src/telegram/`, `docs/telegram.md`): a phone surface INSIDE the API process that reaches OUT via `getUpdates` long polling on global `fetch` — it registers no route and binds no port, so none of the `Host`/`Origin` guards in `net.ts` cover it. That is why the single-user gate (`from.id === chat.id === telegram.allowedUserId`, private chats only; everything else dropped silently and counted) is the whole authorization model. Secrets live in `server/data/config.json` (`telegram.botToken`), never in `tm_config`, which `GET /api/config` dumps. Handlers call service functions IN-PROCESS, never HTTP back into this server and never the PTY; where a route had assembly inline it moved out — `usageSnapshot()` in `claude/usage.ts`, and the whole task lifecycle (create/edit/enqueue/retry/queue add-remove/unblock/complete/cancel) in **`server/src/task-actions.ts`**, actor-parameterised and called by BOTH `routes/tasks.ts` ('human') and `telegram/actions.ts` ('telegram') — never a second copy. Conversational flows (`telegram/flows.ts`) are ONE at a time, in memory, 10-min timeout, with wizard buttons in a `w:` namespace disjoint from the stateless action codec; free text becomes a draft only behind an explicit confirm button. Long content is never a chat message: `telegram/report.ts` builds ONE self-contained HTML document (`/report 24h|7d|task|feature|group`, the `/digest` daily push, and the feature-plan notification all use it) sent with `sendDocument` — **no Telegraph and no external publishing of any kind**, and the file itself has zero external assets, every visual value a literal from the dark `--tm-*` set. The Russian summary is both the top of the document and the caption on the upload. The review ping waits for `task.reviewState` to settle (a last-seen review-state memory beside the status memory — no polling, no `isReviewPending`), builds its verdict from the row (`reviewClause`), and the attention ping is re-read against the LIVE run at flush. Every action is a `tm_events` row with `actor: 'telegram'` — except dropped updates, which are summarised so unauthenticated traffic cannot write rows at will. **The board** (`telegram/board.ts`, `docs/telegram.md` § The board): `/tasks` and `/now` are ONE message redrawn in place via `editMessageText` (fresh send when the edit fails; `message is not modified` is success), and an action pressed on a board or card redraws THAT message — the surface is read off the pressed message's own keyboard (`l:f:` board 🔄, `l:r:` card 🔄), never remembered server-side. `l:` buttons carry 8-char short ids resolved through `ids.ts` at press time (stale/ambiguous → toast, never a pick), are parsed before the action codec, and are NOT audited — navigation is a read; only the action-codec mutations write rows. Setup is a workbook, not folklore: `docs/telegram.md` **§ Connect** (BotFather, the `/start`-tells-you-your-id trick, config, the Mac-as-a-server `launchd`/`caffeinate`/FileVault checklist, troubleshooting) — keep it in step with the boot lines in `telegram/bot.ts`, since it quotes them verbatim.
- **Chat** (`server/src/chat/service.ts`, `docs/chat.md`): a free-form conversation with claude in a repo's cwd, shared by the SPA (`/chat`) and the phone (`/chat` `/chats` `/endchat` `/mode`) over ONE transcript. Every turn is its own aux terminal (kind `chat`, `claude [--resume <sessionId>] -- <message>`), attachable from the runs list. The phone never sees it: the reply is the Stop hook's `last_assistant_message`, the same text `-p` returned. The PTY lives exactly one turn and is ended before `done` resolves, so a live PTY and the next `--resume` never share a session id. `AskUserQuestion` and plan mode are denied: nobody may be at the terminal. Serial per chat, enforced in SQL by the composite `beginChatTurn` (`idle|error → thinking`, conditional); `chat.concurrency` (default 2) bounds all chats and is deliberately NOT `orchestrator.concurrency` — a chat turn must never take a worker slot. EVERY path past the lock must reach `finishChatTurn` — both windows: `send()` guards the user-message insert and the auto-rename (a storage error there used to strand the chat `thinking` with no child in existence to settle it), and `completeTurn` guards the post-turn bookkeeping; each release is itself `.catch()`-ed. `recoverOnBoot()` clears a lock stranded by a crash.  Mode is `read` by default (`--permission-mode dontAsk` + the same `--disallowedTools Edit Write NotebookEdit Bash` as analyze/review); `write` is `--dangerously-skip-permissions` and NOT `dontAsk` — `dontAsk` denies anything that would prompt, which measured against the real CLI is a write mode that cannot write. There is deliberately no setting between the two (`acceptEdits` was measured to run Bash in `-p` as well). `write` is a code-execution surface, so from the phone it is gated behind `telegram.chat.allowWrite` in `data/config.json` — **enforced at the SEND (`phoneMaySend`), not only at `/mode`**, or a chat switched to write in the browser would be reachable by an unlocked handset that never typed `/mode`; `openChat` also refuses to silently resume a write chat the phone may not use. This is a deliberate, documented amendment to `docs/telegram.md` § What the bot does not do. A turn's pid is persisted (`tm_chats.pid`, migration 20) because a chat owns no run row and the child is detached: `recoverOnBoot()` group-kills the orphan (behind `pidLooksLikeOurs`, which now matches the BASENAME of `ps -o comm=` — a full path meant anything under a `claude`-ish directory read as ours) BEFORE clearing the lock, or the next message would resume the same session id alongside a live orphan. Stop is an abort of the turn's aux session (the runner ends the PTY and the turn settles `stopped`). `POST /api/chats/:id/messages` answers **202 on acceptance**: `send()` is two-phase (resolve on lock taken, `done` promise for the reply), because a turn outlives any HTTP timeout and a route must not have to guess when a refusal stopped being possible. Telegram chat buttons live in a `c:` namespace parsed BEFORE the stateless action codec, like `w:` and `k:`.
- **Questions** (`server/src/questions.ts`, `docs/questions.md`): a worker's `AskUserQuestion` call is carried to the human instead of drawing a dialog in the hidden PTY. `AskUserQuestion` is IN `WORKER_TOOLS`, and a `PreToolUse` hook (matcher `AskUserQuestion`, `timeout` 7 days) POSTs the hook's stdin to `POST /api/internal/runs/:id/question?waitMs=60000` and loops on `{pending}` — this is the ONE hook whose stdout matters (no `>/dev/null || true`): the server answers with the CLI's own decision, `allow` + `updatedInput: { questions, answers }` (answers keyed by question TEXT, multi-select joined with ", "), which is what the dialog would have written into the input, so the tool completes normally. Five consecutive failed attempts (curl error, or a reply that is neither a decision nor `pending`) print `ASK_UNREACHABLE` (a deny telling the agent to decide itself) — silence would let the dialog draw and deadlock; the ONE silent exit is the idle-run 409 (a human at an attached terminal — the CLI's own dialog works there). `case` patterns in that loop carry NO quotes (inside a pattern `"` quotes rather than matches — review round 1). `tm_questions` (migration 23, FK-less, unique `(run_id, tool_use_id)`) with a conditional `answerQuestion` composite; `QuestionService.answer` is called in-process by BOTH `routes/questions.ts` ('human') and `telegram/questions.ts` ('telegram') — first wins, the other gets 409. Idempotent on `tool_use_id`, which is REQUIRED (400 without it); the questions array is handed back VERBATIM, never trimmed; the human answer route refuses a POST without `Origin` (a worker must not curl its own question shut as `human`). Deliberately NO new `TaskStatus` and NO `needs_attention` reuse (that flag clears on transcript progress, which a waiting question never produces): the SPA renders a synthetic `asks you` badge, a global `QuestionModal` (mounted in `App.tsx`, pops on any page) and a header chip. Every end of the wait expires the row — `handleExit` (beside `forgetAttention`), the Stop route, `recoverOnBoot` — and a waiting hook then gets a deny with the note. Telegram buttons are a `q:` namespace parsed BEFORE the action codec; the ping is not coalesced and not gated by notify flags.
- **Reports** (`server/src/reports/`, `docs/reports.md`): pick SEVERAL repos and a date range (`today|3d|week|month|custom`, presets counting back from today INCLUSIVE) and one claude session (aux kind `report`) turns the tasks that FINISHED in that window into the document you hand to the CLIENT — concise markdown, grouped by completion date, one business-language bullet per delivered change, in `ru` or `en` (`ReportLanguage`, a property of the ARTIFACT; the SPA stays English, and BOTH the agent's prose and the chrome the server assembles come from one record per language in `reports/language.ts` so a document is never half-translated). Deliberately NOT `telegram/report.ts`, which is the OPERATOR's ops page and is single-scope and `since`-only. Delivered = `done`+`published` only (`failed`/`cancelled` are in `TERMINAL_TASK_STATUSES` but delivered nothing), and the completion DATE is the `task.transition` audit row, never `updated_at` — a later title fix would silently re-date landed work into the wrong section and the wrong report; days bucket on SERVER-LOCAL time like `routes/stats.ts`. **The server assembles the document; the model only writes prose**: the agent returns `{summary, days:[{date,bullets}]}` against a `--json-schema` and `renderMarkdown` builds the headings around it, so an INVENTED date is dropped and a report with nothing left FAILS rather than emitting an empty heading. An empty window is an ANSWER, not a failure — no agent is spawned. Migration 24 (`tm_reports`, FK-less, `repo_ids` JSON; plus `tm_tasks_updated_idx`), `TaskFilter` gains `updatedUntil` and `repoIds` (disjunctive; an EMPTY array matches NOTHING, never "all repos"). An aux run (subject = the report), so `/killall`, Kill and the restart guard cover it; `MAX_CONCURRENT` 1, never a worker slot; NO built-in tools (`--tools=`) plus the four denials — it only transforms rows this process already read. `POST /api/reports` answers **202** and the document arrives over `/ws/events`; delete aborts the session (an `AbortController`, so even before spawn) BEFORE the row goes, and `recoverReportsOnBoot()` fails what a crash left `running`.
- **Shared spaces** (`server/src/spaces/service.ts`, `docs/shared-spaces.md`): a set of repos on one product (neko: nest + vite + next) shares a knowledge FOLDER outside every repo (`tm_spaces.path`, validated neither inside nor containing a repo) and a LEDGER of cross-repo `request`/`note` rows (`tm_shared_notes`, migration 30, FK-less). A repo is in at most one space. Every worker turn in a member repo gets `TM_SHARED_DIR` + `--add-dir=<folder>` (`=` form: the flag is variadic) + `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`, so the CLI loads the folder's GENERATED `CLAUDE.md` (`writeSharedMemory`: rules + a COPY of `INDEX.md` — `@` imports in an add-dir CLAUDE.md are not followed, measured — refreshed every spawn; a CLAUDE.md without the `tm:shared-memory` marker is the user's and is left alone) as memory, and, via `startWorker` → `sharedContext()`, a prompt block (never on the publish turn): a fresh session gets it at the TOP of the prompt as "read before you plan" (step 1: read what INDEX.md points to + `repos/<name>.md` via `repoPage`; the plan names what was read) plus the OPEN requests addressed to its repo — mid-prompt it was read past (task d474e1e1); a resume gets only open requests updated after the resumed run started (none → no block). `filed` is a claim on a task and the task is the truth — `reconcileFiled` runs on every read (task done/published → `done`, cancelled/deleted → `open`), and the prompt path reads `open`+`filed` so a cancelled filing reopens there too. `POST /api/agent/shared/notes/:id/file` is the one agent path that files into its OWN repo without the same-repo draft rule: only for a request addressed to the caller's repo, single-winner (`open→filed` conditional write), and the task goes into the CUSTOM queue, where an agent-created member (`created_by_run` set) is held by `CUSTOM_QUEUE_HEAD_WHERE` while its FILER (`created_by_run`'s task, same repo) is running/waiting/blocked/failed or `review` with an open review round — the filer idles in `review` during its round, which `repoBusy` does not see (review round 1); a SETTLED review no longer holds it (2026-09-28) — or while any task in the repo holds it the same way (NOT merely sitting in review: that starved filings, round 2); the SPA twin is `customQueueBlocker`; that hold is why skipping the draft rule is safe; human space writes need `Origin`, and a repo registered into/around a space folder is refused (`spaceConflictForRepo`, re-checked per spawn); creation cap, depth cap, `agent.allowEnqueue` and the agent ceiling still apply. The depth cap is `agent.maxSpawnDepth` (default 6, was a hard-coded 2), shared by `/api/agent/tasks` via `routes/agent-caps.ts`. The server rewrites the folder's `README.md` on space changes and mirrors the ledger to `REQUESTS.md` on note changes; `.tm/import.json` seeds the ledger once. SPA page `/shared`; Telegram `/shared` is read-only.
- **Remote access** (`server/src/remote.ts`, `docs/remote-access.md`): the phone reaches the production front door ONLY through `tailscale serve` on the tailnet (never Funnel, never the Vite dev server). The gate is in the FRONT DOOR because its proxy rewrites `Host`, after which the API cannot tell remote from local. **Remote-ness is the LISTENER, never the Host**: serve forwards the client's Host verbatim (a `Host: 127.0.0.1:5176` through serve looked local and got the session token, review round 1), so serve points ONLY at a dedicated loopback listener `remote.port` (5177) where EVERY request is gated, and the main listener 403s anything `looksProxied` (`X-Forwarded-*`/`Tailscale-*`, the tripwire for serve misrouted to 5176). On the remote listener a request needs `Host` EXACTLY `remote.hostname` (port-less or `:443` — never a `.ts.net` suffix; anything else incl. loopback names is refused), `remote.enabled`, a loopback TCP peer, an allowlisted `Tailscale-User-Login` (stamped by tailscaled, which strips client copies; a tagged node like the Mac itself gets none), and Origin exactly `https://<hostname>` on writes and WS; `/host/*` included. Admitted requests have every `tailscale-*` header stripped and the verified Origin REWRITTEN to the front door's loopback origin, so the API and `net.ts` stay loopback/LAN-only with no remote code path (decisions.md 2026-09-29). `remote` lives in `data/config.json` and refuses to boot with LAN mode. First request per login per front-door boot → one `remote.login` `tm_events` row via `POST /api/host/remote-login`, guarded by the per-boot secret in `data/host.token`. A forged header from a local process is out of scope (loopback already has everything).
- **Web Push** (`server/src/push/`, `docs/push.md`): the Home Screen PWA (iOS 16.4+, over the tailnet's HTTPS or localhost — never LAN http) gets system notifications with the Telegram notifier's triggers and re-checks (`PushNotifier`, 5s per-task coalescing, re-read at flush; questions immediate), independent of the bot, with the kinds chosen PER DEVICE from ONE list (`PUSH_KINDS` in shared). Protocol on `node:crypto` only (`webpush.ts`: RFC 8291 aes128gcm, checked against the RFC's test vector; RFC 8292 VAPID). The VAPID pair is generated on first boot into `data/config.json` `push` (a secret — never `tm_config`) and binds every subscription, so never regenerate it casually. `tm_push_devices` (migration 32, SQL shared in `storage/push-sql.ts`); 404/410/Apple `BadDeviceToken` delete the row. Subscribe/patch/delete/test routes require `Origin` (a worker's curl has none) and endpoints must be a browser vendor's push service (otherwise the server becomes a request forwarder). `web/public/sw.js` is push-only: NO fetch handler, NO cache. iOS must show a banner for every push, so settle/"never mind" is never pushed — the open app closes stale question banners (`PushBridge`, which also routes taps and the general `?task=<id>` deep link).
- **Security** (`SECURITY.md`): server binds 127.0.0.1 only (the front door too, against its own port) unless LAN mode is explicitly on; WS upgrades validate Origin and require the per-boot session token. Remote use is the tailnet via `tailscale serve` + the gate only — never public. Never weaken these.

## Rules

- Visual changes must resolve to the `--tm-*` tokens defined in `docs/tm-design-tokens.html` (mirrored in `web/src/theme.css`). No hardcoded colors/spacing/fonts outside that token layer (xterm.js needs concrete values — take them from the sheet's terminal tokens).
- Two designs (`docs/glass.md`): **Classic** (`theme.css`) and **Glass**, the iOS Liquid Glass layer in `web/src/glass.css`, picked per device (`html[data-design]`, `src/appearance.ts` + its inline twin in `index.html`). Every Glass rule is scoped to `[data-design='glass']` and its tokens are the Glass blocks in `theme.css`, so Classic keeps rendering unchanged; a new component gets Glass colours and type through the remapped tokens and needs a `glass.css` rule only for a material or motion of its own. Never put `backdrop-filter`/`filter`/`transform` on `.main`, `.header` or `.app`: they hold `position: fixed` overlays, and those properties make an element their containing block. Overlays animate out through `exitGhost` (`src/motion.ts`), not a closing state. Glass hides Features and Chat from the menus only; their routes stay for deep links.

- Document all work in `docs/` — updating docs is an exit criterion of every phase/change.
- Worker prompts must include the standing caps: max 3 subagents per session; orchestrator concurrency stays at 2.
- Adversarial review of each phase before moving to the next (max 3 agents at a time).
- Agent model is `claude-opus-5-5`; the fable roles (analysis/orchestrator/router-primary/review) are `claude-fable-5-1`. The offered list is `MODEL_OPTIONS` in `shared/` — every dropdown (web config, board, task panel, Telegram `/new`) renders that one array. Analysis runs in a read-only aux terminal with write tools disallowed.
